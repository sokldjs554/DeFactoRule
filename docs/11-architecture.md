# 아키텍처 재편 — 왜 스크립트 모음을 걷어냈는가

## 무엇이 문제였나

Phase 1~2 를 지나는 동안 코드는 `scripts/` 아래 평평한 파일 18개로 자랐다.
동작에는 문제가 없었다. 문제는 **경계가 없다는 것** 자체였다.

- `evaluate.py` 가 점수 계산·파일 입출력·라벨 집합·CLI 를 한꺼번에 들고 있었다.
  다른 채점 스크립트 네 개가 전부 `from evaluate import ...` 로 그것을 가져다 썼다.
  채점 하네스가 사실상 공용 라이브러리였다.
- 레코드 키(`key_of`)가 채점 모듈 안에 있었다. gold 와 예측을 맞추는 기준이
  채점기 안에 숨어 있으면, 키가 어긋나도 예외가 아니라 **매칭 건수 감소**로
  나타난다. 실제로 30건 예측을 170건 gold 로 재면서 커버리지 17.6%를 놓쳤다.
- LLM 호출부와 채점부가 같은 평면에 있어, 명세 §9 가 요구한
  "LLM 이 하는 일 / 결정론적 코드가 하는 일" 분리가 **코드로 표현되지 않았다.**
  문서에만 있는 분리는 지켜지는지 확인할 방법이 없다.

## 계층

```
app/
  core/            공용 입출력과 레코드 키. 도메인을 모른다.
  domain/          라벨 체계, 판정 지침, 기저율. 무엇을 판단하는가.
  extraction/      PDF → 사례 → 질의·회답 쌍. 전 과정 결정론적.
  rules/           결정론적 기준선. LLM 없이 어디까지 되는가.
  retrieval/       근거 검색. **아직 비어 있다.**
  agents/          LLM 호출. 의미 해석과 후보 생성만 맡는다.
  evaluation/      채점·통계·오류 분석.
  infrastructure/  외부 시스템과의 경계.
  api/             서비스 진입점.

scripts/           얇은 CLI 진입점. 각 파일은 sys.path 를 얹고 main() 을 부른다.
```

의존 방향은 위에서 아래로만 흐른다. **`agents` 는 `evaluation` 을 임포트하지
않는다.** 그 선을 지키려고 `base_rates` 를 `evaluation` 이 아니라 `domain` 에
두었다 — 기저율은 라벨 분포에 관한 도메인 사실이고, 분류기와 채점기가 모두
읽는다. `evaluation` 에 두면 LLM 계층이 채점 계층에 의존하게 된다.

`retrieval/` 은 비어 있는 채로 둔다. 현재 파이프라인은 질의–회답 쌍 하나를
통째로 모델에 넘기므로 검색 단계가 없다. 안 만든 것을 안 만들었다고 말하는
편이, 빈 디렉터리를 감추는 것보다 낫다.

`scripts/` 의 이름은 하나도 바꾸지 않았다. 문서와 지금까지의 실행 기록에 적힌
명령이 그대로 돌아간다.

## 테스트

이전에는 `tests/regression/` 하나에 25개가 몰려 있었다. 명세 §14 는 네 갈래를
요구하고, 그 구분에는 실질적인 이유가 있다.

| 갈래 | 무엇을 지키는가 | 개수 |
|---|---|---|
| `unit` | 순수 함수의 불변조건. 파일도 네트워크도 건드리지 않는다 | 34 |
| `integration` | CLI 진입점이 실제로 실행되는가 | 4 |
| `evaluation` | 지표가 바닥선 아래로 내려가지 않았는가 | 1 |
| `regression` | 서식·산출물이 조용히 망가지지 않았는가 | 20 |

25개 → **59개**. 늘어난 34개는 대부분 **여태 테스트가 하나도 없던 모듈**의
것이다: 매크로 F1 계산, 레코드 키, 라벨 체계, 규칙 기준선.

`integration` 이 따로 필요한 이유가 이번에 분명해졌다. 단위 테스트는 임포트가
성립하는 세계에서만 돈다. 사용자는 `python scripts/evaluate.py` 로 실행하고,
그때 `sys.path[0]` 은 `scripts/` 다 — 진입점이 저장소 루트를 얹지 않으면
`app` 이 보이지 않는다. 단위 테스트로는 절대 잡히지 않는 고장이다.

## 함께 발견한 것 — CI 는 처음부터 돌지 않았다

`.github/workflows/ci.yml` 이 `requirements-collect.txt` 를 설치하고 있었다.
**그런 파일은 저장소에 없다.** 의존성 설치 단계에서 죽었으므로 린트도 테스트도
한 번도 실행된 적이 없다. 파일 이름이 초기 설계의 잔재로 남았고, 워크플로가
빨간불이어도 로컬에서 테스트가 통과하니 눈치채지 못했다.

바로잡으면서 두 가지를 함께 고쳤다.

- 린트 범위가 `scripts tests` 였다 → `.` 로 넓혔다. `app/` 이 통째로 빠져 있었다.
- Python **3.9 와 3.11 을 함께** 돌린다. 이 프로젝트는 실행 문턱을 낮추려고
  3.9 문법으로 내려왔는데(`StrEnum` 하나로 실행이 막힌 적이 있다), 그 약속을
  지키는지 확인하는 장치가 없었다.

## 남은 것

`app/api` 와 `app/retrieval` 은 골격만 있다. `infrastructure` 도 아직 비어
있고 Anthropic 클라이언트는 `agents/classifier.py` 안에 들어 있다 — 외부
경계를 따로 떼는 것은 API 계층을 만들 때 함께 한다.
