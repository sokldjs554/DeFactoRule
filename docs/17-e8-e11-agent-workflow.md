# E8~E11a — Agent Workflow 의 각 부분은 값어치를 하는가

> 새 API 호출 **0회**. 기존 예측·규칙·유사도 기계를 재사용했다.
> 재현: `python3 scripts/agent.py experiment`

## 사전 등록한 것과, 그것이 틀렸던 곳

설계서에 주 종점을 **함정 구간(TRAP) 정확도**로 못 박았다. 그리고 이렇게 적었다.

> Wilson 구간으로 `0/15` 는 [0, 0.20], `4/15` 는 [0.11, 0.52].
> **4/15 이상이어야 하한이 0 을 넘는다.**

**틀렸다.** 계산하지 않고 쓴 숫자다. 실제로는 이렇다.

| | 95% CI | 하한 > 0 |
|---|---|---|
| 0/15 | [0.000, 0.204] | ✗ |
| **1/15** | [0.012, 0.298] | **✓** |
| 4/15 | [0.109, 0.520] | ✓ |

즉 사전 등록한 기준은 **15건 중 1건만 맞혀도 통과**하는 약한 기준이었다.
기준을 바꾸지 않는다 — 결과를 보고 문턱을 옮기는 것이 조작이다. 대신 그것이
약한 기준이었다는 사실을 여기 적는다.

## 무엇을 비교했나

다섯 변형을 **한 코드 경로**로 만들었다(`Policy`). 다섯 벌을 따로 쓰면 반드시
갈라진다.

| 변형 | 무엇인가 |
|---|---|
| `naive` | top-1 선례의 라벨을 그대로. 기권 없음 |
| `always-precedent` | 선례가 있으면 무조건 선례 경로. Router 없음 |
| `router` | 전체 |
| `router-noabstain` | Router 는 쓰되 기권하지 않음 |
| `router-novalidate` | Router 는 쓰되 검증하지 않음 |

**`naive` 가 E5 의 `neighbor` 모델과 170/170 일치**하는 것을 확인했다. 독립
구현 둘이 같은 답을 내므로, 기준선이 같은 것임을 말할 수 있다.

## 결과

```
test 170건 · 함정 구간 15건 · 선례 풀 dev 85건 · 새 API 호출 0회

변형                    커버리지   답한 것 정확도   매크로 F1
naive                   100.0%        0.724      0.538
always-precedent         51.2%        0.839      0.593
router                   54.1%        0.837      0.609
router-noabstain         98.2%        0.749      0.476
router-novalidate        54.1%        0.837      0.609
```

### 주 종점 — 그리고 왜 그것이 이 실험을 못 재는가

```
변형                   맞힘  틀림  기권    정확도   95% CI
naive                    0   15    0    0.000   [0.000, 0.204]
always-precedent         1   14    0    0.067   [0.012, 0.298]
router                   2    5    8    0.133   [0.037, 0.379]
router-noabstain         2   13    0    0.133   [0.037, 0.379]
```

주 종점만 보면 Router 0.133 vs naive 0.000 이고, **구간이 크게 겹친다.**
15건으로는 가를 수 없다.

그런데 **분해가 다른 이야기를 한다.**

> `naive` 는 함정 15건에서 **15건 전부 틀린다.**
> `router` 는 **5건 틀리고 8건 기권한다.**

틀린 답 15 → 5. 그 차이는 정확도에 나타나지 않는다 — 맞히지 않고 **멈춘 것**
이기 때문이다. 주 종점을 이렇게 잡은 것이 설계의 실수였고, 실수를 그대로 두고
분해를 함께 보고한다.

### 기권이 정당했는가 — Router 는 과하게 기권한다

```
변형                 커버리지   기권   정당    비율   95% CI
always-precedent      51.2%    83    35   0.422  [0.321, 0.529]
router                54.1%    78    28   0.359  [0.261, 0.470]
router-noabstain      98.2%     3     3   1.000  [0.438, 1.000]
```

`router` 가 기권한 78건 중 **답했어도 맞았을 것이 50건(64%)** 이다. 기권이
위험을 낮추기는 하지만 값싸게 사지 않는다. 이것이 이 워크플로의 가장 분명한
약점이다.

### E10 — 기권은 실제로 값어치가 있다

`router` 와 `router-noabstain` 은 경로 선택이 같고 기권만 다르다.

| | 커버리지 | 답한 것 정확도 | 매크로 F1 | 함정에서 틀림 |
|---|---|---|---|---|
| `router-noabstain` | 98.2% | 0.749 | 0.476 | 13/15 |
| `router` | 54.1% | 0.837 | **0.609** | **5/15** |

같은 라우팅에서 기권만 켰는데 함정 오답이 13 → 5 로 준다.

### E11a — 결정론 검증은 **아무것도 바꾸지 않는다**

`router-novalidate` 와 `router` 의 모든 수치가 **완전히 같다.**

이유는 분명하다. 지금 배선에서 결정은 근거의 라벨에서 나오고 인용은 원문에서
잘라 낸다. 그러므로 V1(형식) · V2(근거 실재) · V3(인용 대조) · V5(근거 없는
주장)는 **구성상 참**이고 발화할 수 없다. V4 는 dev 에서 2건, test 에서 1건
발화했고 결정을 막지는 않았다.

검사를 지우지 않는다 — 모델이 결정이나 인용을 내놓는 경로(V3+ LLM
적용가능성 검증)가 붙는 순간 셋 다 발화 가능해지고, 그때 없으면 지어낸 인용이
그대로 나간다. 다만 **지금은 값어치가 0 이라는 사실을 그대로 적는다.**

각각이 살아 있다는 것은 합성 상태로 일부러 실패시켜 확인했다
(`tests/unit/test_validator.py`).

### E8 — 위험-커버리지에서는 개선이 없다

```
AURC        naive 0.215 · router 0.236 · sector 0.124

  naive − sector    +0.092  [+0.041, +0.145]  p(Holm) 0.000  유의
  router − sector   +0.113  [+0.050, +0.175]  p(Holm) 0.000  유의
  naive − router    −0.021  [−0.073, +0.030]  p(Holm) 0.413  판정 보류
```

**Router 는 naive 보다 AURC 가 낫지 않다.** 그리고 기존 `sector`(기저율을
알려 준 LLM)보다 유의하게 나쁘다. Agent 는 LLM 을 전혀 쓰지 않으므로 그 격차는
놀랍지 않지만, 그렇다고 감출 일도 아니다.

**이 수치는 하마터면 반대로 나올 뻔했다.** 기권을 `predicted: null` 로
내보내던 판에서는 `naive − router = −0.270 (유의)` 였다 — 하네스가 기권 78건을
전부 오답으로 셌기 때문이다. **기권을 보여주려고 만든 지표가 기권을 벌하고
있었다.** 평가용 레코드에만 "굳이 답한다면" 라벨을 담아 고쳤다(EV-24).
판정이 뒤집힌다: 유의 → 판정 보류.

## 완료 기준 대비

| | 요구 | 결과 |
|---|---|---|
| 1 | 검색 결과를 무조건 믿지 않는다 | ✅ 함정 15건 중 8건 기권 · `조치` 14건에서 선례 경로 **0건** |
| 2 | 선례/규칙 경로를 구분한다 | ✅ A 48 · B 44 · C 78, `route_reason` 에 R번호 |
| 3 | 근거 부족 시 기권한다 | ✅ fixture 9종 통과 · 사유 코드 6종 |
| 4 | 잘못된 선례를 탐지한다 | **△** 하한 0.037 로 사전 기준은 넘지만 기준 자체가 약했다. 실질은 오답 15 → 5 |
| 5 | evidence 추적 가능 | ✅ 답한 건 전부 `evidence_used` 비어 있지 않음 |
| 6 | 기존 평가 체계와 연결 | ✅ 예측 파일 형식이 같아 `evaluate` · `risk_coverage` · `comparison` 을 그대로 씀 |
| 7 | 실제 업무 관점의 개선 | **✗** AURC 개선 없음(판정 보류). 과잉 기권(정당 36%)이 원인 |

**7번을 못 넘었다.** 그것이 지금의 결론이고, 그대로 적는다.

## 결론 — 무엇이라고 말할 수 있고 무엇은 말할 수 없는가

**말할 수 없는 것**: "Router 가 더 잘 맞힌다."

전체 위험-커버리지에서 개선이 없다(AURC 0.215 → 0.236, 판정 보류). 기존 LLM
판정기(`sector` 0.124)보다는 유의하게 나쁘다. 커버리지를 46% 포기하고 얻은
정확도 상승(0.724 → 0.837)은 **쉬운 것만 골라 답한 결과**이므로 그 자체로는
개선의 증거가 아니다.

**말할 수 있는 것**:

> 표면적으로 위험한 선례에서 **무리하게 답하는 오류를 줄이는 대신 커버리지를
> 크게 희생하는 보수적 라우팅 동작**이 확인되었다. 함정 구간에서 오답이
> 15건에서 5건으로 줄었고, 그 감소분은 전부 기권으로 옮겨 갔다. `조치` 14건
> 에서는 선례 경로를 **한 번도** 고르지 않았다 — E5 가 실측한 앵커링 7.1% 가
> 요구하는 그대로다.
>
> **다음 과제는 선례의 실제 적용 가능성을 판단하여 과잉 기권을 줄이는 것이다.**

이 문장이 지금 이 프로젝트가 데이터로 받칠 수 있는 전부다. 그 이상은 적지
않는다.

## 방법론에서 배운 것 — EV-24

이 절을 숨기지 않고 남긴다. **평가 하네스의 인코딩 하나가 결론을 뒤집었다.**

```
기권을 predicted: null 로 내보내던 판
  naive − router = −0.270  [−0.346, −0.196]  p(Holm) 0.000   유의

평가용 레코드에만 "굳이 답한다면" 라벨을 담은 뒤
  naive − router = −0.021  [−0.073, +0.030]  p(Holm) 0.413   판정 보류
```

원인은 단순하다. 위험-커버리지 하네스는 커버리지 100% 지점에서 모든 예측을
채점하는데, `null` 은 어떤 라벨과도 같지 않으므로 **기권 78건이 전부 오답**이
됐다. 그래서 커버리지 100%의 위험이 54.7%로 부풀었고, AURC 가 그만큼 나빠졌다.

**기권을 보여주려고 만든 지표가 기권을 벌하고 있었다.**

배운 것은 셋이다.

1. **서비스가 내는 값과 평가가 읽는 값은 다를 수 있다.** 서비스는 기권 시
   아무것도 내놓지 않아야 하고(`decision = None`), 평가는 "굳이 답한다면"
   무엇인지를 알아야 곡선을 그릴 수 있다(`provisional`). 둘을 한 필드로
   합치면 반드시 한쪽이 망가진다.
2. **유의한 결과일수록 인코딩을 의심해야 한다.** −0.270 은 크고 깔끔한 효과로
   보였다. 크고 깔끔할수록 "그럴 리가 있나" 를 먼저 물어야 했다.
3. **곡선의 양 끝을 눈으로 봐야 한다.** 커버리지 100% 지점의 위험 54.7%는
   답한 것 정확도 0.837 과 앞뒤가 맞지 않는다. 그 불일치가 유일한 단서였다.

## 다음에 무엇을 해야 하는가

수치가 가리키는 곳은 하나다 — **과잉 기권**. 78건 기권 중 50건은 답했어도
맞았다. 기권을 줄이려면 지금 C 로 가는 경로에 쓸 근거가 더 있어야 하고,
그 자리가 바로 설계서가 V3+ 로 남겨 둔 **LLM 적용가능성 검증**이다.
E11b 는 그래서 선택 항목이 아니라 다음 단계가 된다.
