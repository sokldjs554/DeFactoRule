## 0. 먼저 — "legacy 문턱" 은 한 덩어리가 아니다

여섯 개를 뭉뚱그려 오염이라고 부르면, **다시 뽑을 수 있는 것**과 **애초에 뽑은
적이 없는 것**을 같은 문제로 취급하게 된다. 성격부터 가른다.

| 성격 | 뜻 | 해당 |
|---|---|---|
| **학습된 것** | 데이터에서 계산된다. split 이 바뀌면 다시 뽑아야 한다 | `trap_risk` · E6 규칙 · `RISK_CEILING` · 기저율 |
| **구조적인 것** | 자료구조가 값을 정한다. 데이터가 아니라 top-k 가 정한다 | `MIN_AGREEMENT` |
| **임의의 것** | 사람이 골랐고 데이터가 고르지 않았다. **다시 뽑을 절차 자체가 없다** | `MIN_MARGIN` · `MAX_YEAR_GAP` · keyword 어휘 |
| **고르고 나서 검증한 것** | 값은 먼저 정했고, 데이터는 그것을 **정당화**만 했다 | `DOUBT` · `TRUST` |

마지막 칸이 이 감사의 핵심이다. `app/domain/similarity.py` 는 문턱을
**최적화한 적이 없다** — 둥근 값을 고르고 "dev LOO 구간이 갈린다" 로 정당화했다.
그러면 "clean dev 에서 다시 유도" 라는 말은 **정당화를 다시 통과시키는 것**이지
새 값을 뽑는 것이 아니다.

## A. 파라미터 — legacy 값과 clean dev 재계산 값

### A.0 한눈에

| 파라미터 | 성격 | 재유도 가능? | legacy | clean dev | 차이 | Router 출력 영향 |
|---|---|---|---|---|---|---|
| `DOUBT` | 고르고 검증 | 절차는 통과하나 **값을 좁히지 못한다** | 0.15 | 0.15 유지 가능 | 0 | **있다** — 무감구간 ±0.004 |
| `TRUST` | 고르고 검증 | 같음 | 0.60 | 0.60 유지 가능 | 0 | 약간 — 무감구간 (0.522, 0.609) |
| `RISK_CEILING` | 학습 | **가능** | 0.20 | **0.18** | −0.02 | **없다** — 무감구간 (0.054, 0.400) |
| `MIN_AGREEMENT` | 구조 | 해당 없음 | 0.60 | — | — | 없다 — 무감구간 (0.500, 0.667) |
| `MIN_MARGIN` | 임의 | 절차 없음 | 0.02 | — | — | 없다 — R9 가 가려져 있다 |
| `MAX_YEAR_GAP` | 임의 | 절차 없음 | 5 | — | — | 없다 — **구조적으로 도달 불가** |
| keyword 어휘 | 임의(수작업) | **불가** — 스크립트가 없다 | 정규식 2개 | — | — | baseline 전용. Router 미사용 |
| 기저율 표 | 학습 | **가능** | n=85 | **n=87** | 비조치 +4.2%p | **LLM 프롬프트에 들어간다** |

"무감구간" 은 **관측된 신호를 그대로 두고 문턱만 움직였을 때 출력이 한 건도
바뀌지 않는 범위**다. 이미 돌아간 실행의 신호 분포에서 잰 것이고, 새 값을
적용한 것이 아니다.

### A.1 `DOUBT` · `TRUST` — 절차가 값을 좁히지 못한다

문서화된 절차는 "후보 문턱에서 dev LOO 구간표를 만들고, 믿음 구간의 Wilson
상한이 못믿음 구간의 하한보다 낮으면 통과" 다. 격자
(`DOUBT` 0.05~0.50 × `TRUST` 0.30~0.90, 0.01 단위)를 전부 돌렸다.

    후보 2,806쌍 중 trust > doubt 인 것 2,575쌍
    legacy dev 에서 통과   2,575 / 2,575
    clean  dev 에서 통과   2,575 / 2,575      두 집합은 **완전히 같다**

**하나도 걸러지지 않는다.** 이유는 유사도 분포에 있다.

    clean dev 87건   문턱 아래 40 · 가운데 10 · 믿음 위 37
    legacy dev 85건  문턱 아래 48 · 가운데  5 · 믿음 위 32

양 끝에 몰려 있고 가운데가 비어 있어서, 문턱을 그 빈 구간 어디에 두든 같은 행이
같은 편에 남는다. 그러므로 **"clean dev 에서 다시 유도했더니 0.15/0.60 이
나왔다" 고 말할 수 없다.** 말할 수 있는 것은 이것뿐이다 —
**0.15/0.60 은 clean dev 에서도 정당화를 통과한다.**

    clean dev 구간표 @ 0.15 / 0.60
      trust   n 37 · 오답 2 · 0.054 [0.015, 0.177]
      middle  n 10 · 오답 4 · 0.400 [0.168, 0.687]
      doubt   n 40 · 오답 22 · 0.550 [0.398, 0.693]     상한 0.177 < 하한 0.398

문턱을 움직였을 때 실제로 무엇이 바뀌는가는 별개다.

    clean dev  이웃값 사이  DOUBT (0.1469, 0.2014) · TRUST (0.2988, 0.8109)
    clean test 이웃값 사이  DOUBT (0.1470, 0.1540) · TRUST (0.5216, 0.6089)

**`DOUBT` 는 민감하다.** clean test 에 0.15 로부터 0.004 안쪽에 놓인 행이
양쪽에 있다. 조금만 움직여도 그 행들의 `evidence_count` 가 바뀌고 R2/R3/R8 이
갈린다. `TRUST` 는 (0.52, 0.61) 밖으로 나가야 무엇이 바뀐다.

정리하면 — **다시 뽑을 근거는 없고, 함부로 움직일 여유도 없다.**

### A.2 `RISK_CEILING` — 값은 달라지지만 출력은 같다

절차가 명확한 유일한 문턱이다: **믿음 구간 오류율의 Wilson 95% 상한**을 소수
둘째 자리로 올린다.

    legacy dev  상한 0.201  ->  0.20   (지금 실린 값)
    clean  dev  상한 0.177  ->  0.18

그런데 Router 가 이 값과 비교하는 `trap_risk` 는 **구간표에서 조회한 세 개**뿐이다.

    관측된 trap_risk  {0.054, 0.400, 0.550}
    무감구간          (0.054, 0.400)

0.20 도 0.18 도 그 안에 있다. **바꿔도 Router 출력은 한 건도 바뀌지 않는다.**
재유도해야 할 학습 파라미터이지만, 재유도의 실익은 0 이다.

### A.3 `MIN_AGREEMENT` — 데이터가 정한 값이 아니다

`TOP_K = 3` 이므로 `label_agreement` 가 가질 수 있는 값은 유한하다.

    관측값 {0.333, 0.500, 0.667, 1.000}
    무감구간 (0.500, 0.667)   0.60 은 그 한가운데다

"상위 근거의 **과반**" 이라는 정의가 값을 정한다. dev 를 다시 봐도 2/3 는
2/3 다. **재유도 대상이 아니다.**

### A.4 `MIN_MARGIN` — 조건은 걸리는데 줄이 가려져 있다

    관측 margin 이 0.02 미만인 것        129 / 168
    그중 R9 조건(근거 2건 이상 · 결론 갈림)까지 맞는 것   6건
    실제 R9 발화                          **0회**

6건이 어디서 잡혔는지 보면 이유가 나온다.

    220041 · 220049 · 230075 · 240016   ->  **R1** (규칙 충돌이 먼저 걸렸다)
    230094 · 240006                     ->  **R6** (출처가 갈렸다)

**R9 는 도달 불가능한 것이 아니라 앞줄에 가려져 있다.** `MIN_MARGIN` 을
(0.018, 0.047) 안에서 움직여도 이 6건은 여전히 R1·R6 에서 잡힌다.
`R4` 를 지웠던 것과 성격이 다르다 — R4 는 도달 자체가 불가능했다.

### A.5 `MAX_YEAR_GAP` — 구조적으로 도달할 수 없다

    코퍼스 연도       2022 · 2023 · 2024 · 2025   (폭 4년)
    관측 recency_gap  최소 -2 · 최대 3 · 초과 0건 / 60건
    조건              gap > 5

**최대 가능한 간극이 3이므로 `> 5` 는 어떤 데이터에서도 참이 될 수 없다.**
`docs/24` 가 "R7 0회" 라고만 적은 것을 여기서 확정한다 — 표본이 작아서가
아니라 **연도 폭보다 문턱이 크다.** 코퍼스가 2021년 이전으로 넓어지지 않는
한 R7 은 죽은 줄이다.

### A.6 `R10` 도 같은 종류다

R10 은 마지막 폴백이다. 거기 닿으려면 `trap_risk ≤ RISK_CEILING` 이면서
`top_similarity < TRUST` 여야 한다. 그런데 지금 구간표에서 `RISK_CEILING`
아래인 구간은 **`trust` 하나뿐**이고, 그 구간은 정의상 `top_similarity ≥ TRUST`
다. 그러므로 R8 이 항상 먼저 잡는다.

**R10 은 데이터가 아니라 구간표의 모양 때문에 도달 불가능하다.** 3구간 표를
쓰는 한 계속 그렇다. `router.py` 가 이미 적어 둔 "지금 보정에서 R5 와 R8 은
사실상 같은 것을 본다" 의 필연적 귀결이다.

### A.7 keyword 어휘 — 다시 뽑을 절차가 없다

`app/rules/nonaction.py` 의 정규식 두 개는 **사람이 legacy dev 85건을 읽고
뽑았다.** 스크립트가 없으므로 기계적으로 재생성할 수 없다. 두 dev 에서의
성적만 나란히 둔다.

| 정규식 | legacy dev | clean dev |
|---|---|---|
| `망연계\|망분리\|VDI\|…` → 조치 | 피복 6 · 정밀 0.500 | 피복 9 · 정밀 0.444 |
| `적용 여부\|해당 여부…시행세칙` → 기타 | 피복 2 · 정밀 0.500 | 피복 2 · 정밀 1.000 |

표본이 2~9건이라 **어느 쪽도 신뢰구간이 [0.19, 0.81] 수준**이다. 이 어휘는
기준선 전용이고 Router 는 쓰지 않는다.

### A.8 기저율 표 — **B-2b 가 실제로 건드리는 유일한 자산**

`data/eval/dev_base_rates.json` 은 **LLM 프롬프트로 들어간다**
(`app/agents/classifier.py`). 지금 실린 것은 **n=85, legacy dev** 다.

| | 실린 것 (legacy dev 85) | clean dev 87 이라면 |

| 비조치 | 0.682 | **0.724** (+4.2%p) |

## B. clean E6 `sector` 규칙 — 왜 발화하지 않는가

### B.1 두 스키마

**E6 규칙 스키마** (`app/rules/induction.py`)

    Atom(kind, value)     kind ∈ {ngram, sector, length}
    Atom.holds(row)       ngram  -> value in squeeze(row["request"])
                          sector -> (row["sector"] or "미분류") == value
                          length -> length_bucket(row["request"]) == value
    Rule.fires(row)       **행 전체**를 받는다

**Router 의 매칭 스키마** (`app/agents/workflow.py`)

    rule_matches(rule, request: str)     **문자열 하나**만 받는다
      ngram  -> value in squeeze(text)
      length -> length_bucket(request) == value
      그 밖  -> return False          <- 예외가 아니라 조용한 False

호출부는 `_match_rules(state)` 이고 `state.request` 만 넘긴다. 그리고
`AgentState` 의 필드는 `request` 와 `request_key(source, page, serial, pair_index)`
뿐이다 — **`sector` 는 상태에 실려 있지도 않다.**

### B.2 `sector` 값의 실제 표현

값 자체는 멀쩡하다. `공통`·`전자금융`·`보험`·`상호저축은행업`·`여신전문금융업`·
`은행`·`자본시장`·`가상자산` 8종이고, `canonical_sector()` 로 정규화돼 있으며,
clean test 168건 중 빈 값은 0건이다. **문자열이 안 맞아서 실패하는 것이 아니다.**

주목할 것은 **출처**다. `sector` 는 요청문에서 나오지 않는다.
`casebook.page_sector_map()` 이 **사례집의 업권 구분 페이지**를 찾아 이후 본문
페이지에 상속시킨 값이다. 즉 **문서 편집 구조에서 온 메타데이터**이고, 아직
사례집에 실리지 않은 새 질의에는 존재하지 않는다.

### B.3 판정 — **B(계약 불일치)가 주, C(구현 결함)가 종**

| | 판정 | 근거 |
|---|---|---|
| A. 유도 표현 문제 | **부분적으로 맞다** | `sector` 는 요청문의 성질이 아니라 문서 편집 메타데이터다. 추론 시점에 있을지 없을지가 정해지지 않았는데 유도기가 그것을 캔다 |
| **B. 스키마–매처 계약 불일치** | **주 원인** | 유도기는 **행**에 대한 조건을 낸다. Router 의 매처는 **요청문 문자열**만 받는다. 두 계약이 애초에 다르다 |
| C. 단순 구현 버그 | **종 원인** | 모르는 종류를 `return False` 로 조용히 넘긴다. `raise` 였다면 규칙 파일을 바꾼 그날 터졌을 것이다 |
| D. 설계 한계 | **아니다** | `sector` 는 데이터에 있고 상태에 실어 나를 수 있다. 막힌 것이 아니라 이어져 있지 않다 |

**한 문장으로**: 유도기는 행 단위 조건을 내보내고 Router 는 문자열 단위 조건만
받는데, 그 불일치를 알려 줄 장치가 없어서 **조용히 규칙 하나가 사라졌다.**

### B.4 영향 범위 — 규칙 1개

    clean  E6   조건 13개 = ngram 12 + **sector 1**      못 읽는 규칙 **1 / 11** (8번)
    legacy E6   조건 12개 = ngram 10 + length 2          못 읽는 규칙 **0 / 11**

`length` 는 양쪽 다 읽는다. **문제가 되는 종류는 `sector` 하나뿐**이고,
legacy 규칙에는 그 종류가 없었기 때문에 지금까지 드러나지 않았다.
`docs/24 §6.1` 의 수치가 그 간극이다 — 유도기 의미로 22회 발화, Router 안에서 0회.

| `RISK_CEILING` | ❌ legacy 0.20 그대로. clean 값은 0.18 이지만 **출력 영향 0** |
| **기저율 표** | ❌ **legacy dev 85건 그대로. 이것이 LLM 프롬프트로 들어간다** |
| `MAJORITY` 라벨 (`비조치`) | 두 dev 모두 최빈이므로 값이 같다 — 재생성해도 동일 |
| Router `fallback` | dev 인자에서 그때그때 계산된다 — clean dev 를 주면 이미 clean |

### C.3 다시 뽑을 절차가 아예 없는 것

임의 상수와 구조 상수다. "clean 에서 재유도" 라는 말이 성립하지 않는다.

    MIN_AGREEMENT 0.60 · MIN_MARGIN 0.02 · MAX_YEAR_GAP 5
    TOP_K 3(router) / 5(workflow) · HIGH_MARGIN 0.30 · MEDIUM_MARGIN 0.10
    validator HIGH_PRECISION 0.95
    유도기 하이퍼  MIN_DF 4 · MAX_DF_RATIO 0.60 · MIN_SUPPORT 4 ·
                  MIN_PRECISION 0.80 · MAX_DEPTH 3 · BEAM 12
    keyword 어휘 (수작업)
    DOUBT 0.15 · TRUST 0.60   — 고르고 나서 검증한 것. §A.1

### C.4 54건은 성적에 유리하게 작용하지 않았다

`docs/24` 가 낸 예측 파일을 **legacy dev 에 있던 54건 / 처음 보는 114건**으로
쪼갰다. 새 파라미터를 적용한 것이 아니라 이미 나온 결과를 나눈 것이다.
오염이 이득이 됐다면 앞쪽 무리에서 성적이 좋아야 한다.

| 모델 | legacy dev 에 있던 54 | 처음 보는 114 | 차이 |
|---|---|---|---|
| keyword (legacy dev 산 어휘) | 0.704 [0.572, 0.809] | 0.737 [0.649, 0.809] | **−3.3%p** |
| neighbor (legacy 자산 없음) | 0.704 [0.572, 0.809] | 0.614 [0.522, 0.698] | +9.0%p |
| agent-router | 0.821 (답변 28) | 0.837 (답변 49) | −1.6%p |

**legacy 어휘를 쓰는 모델(keyword)은 오히려 그 54건에서 못했다.** 반대로
legacy 자산을 하나도 안 쓰는 neighbor 가 54건에서 잘했다 — 그것은 오염이 아니라
**구성 차이**다.

    54건    비조치 37(68.5%) · 기타 13 · 조치  4   문턱 위 19(35.2%)   함정  2( 3.7%)
    114건   비조치 84(73.7%) · 기타 20 · 조치 10   문턱 위 41(36.0%)   함정 10( 8.8%)

54건 쪽은 함정 비율이 절반 이하다. neighbor 가 잘한 이유가 여기 있다.

**결론.** 54건 겹침은 분할 결함이 아니고, **결정론 계층에서는 측정 가능한
이득으로 나타나지 않았다.** 그러나 이것은 결정론 계층에 대한 이야기다 —
§A.8 의 기저율 표는 아직 검증되지 않았고, 그것은 B-2b 의 문제다.

## D. B-2b 를 진행할 수 있는 최소 조건

수치가 아니라 **자산의 출처**에 걸린 조건이다.

### D.1 반드시 먼저 해야 하는 것 — 하나

    (1) 기저율 표를 clean dev 87건에서 재생성한다.
        지금 것은 legacy dev 85건이고, clean test 168건 중 54건의 정답이
        그 안에 집계돼 있으며, 그 표는 프롬프트로 들어간다.
        새 파일로 낸다 (`dev_base_rates_clean.json`) — legacy 를 덮지 않는다.
        기존 probe 는 `source == "dev"` 만 보므로 **어느 dev 인지 확인하는
        검사를 함께 둔다.**

이것을 하지 않으면 B-2b 의 수치는 "선례 풀은 깨끗하고 프롬프트는 오염된"
혼합 상태에서 나온다.

> **처리했다 — [docs/26](26-clean-base-rate-provenance.md).** `dev_base_rates_clean.json`
> 을 만들고 행 지문으로 출처를 검증했다. 이어서 (가)+(나) 배선도 적용했다 —
> `--base-rates` 로 표를 고르고, `load_validated` 가 이름표가 아니라 지문을
> 대조한다. **기본값은 legacy 표이므로 기존 명령은 그대로 돈다.**

### D.2 해도 되고 안 해도 되는 것 — 근거와 함께

    (2) RISK_CEILING 0.20 -> 0.18       출력 영향 0. **미루어도 된다**
    (3) DOUBT / TRUST                   재유도할 절차가 없다. 지금 값을 유지하고
                                        "clean dev 에서도 정당화를 통과했다" 로
                                        기록한다. **바꾸지 않는 쪽을 권한다**
    (4) rule_matches 의 sector 맹점      Router 를 바꾸면 R1 이 다시 움직이고
                                        B-2a 수치가 무효가 된다. **B-2b 뒤로**
    (5) R7 · R9 · R10                   죽은 줄 정리. 성능과 무관. **뒤로**
    (6) keyword 어휘                    기준선 전용 · Router 미사용. **그대로**

### D.3 B-2b 결과를 읽을 때 함께 적어야 할 단서

    · Router 의 규칙 경로는 clean 규칙 11개 중 10개만 쓴다 (8번이 죽어 있다)
    · R7 · R9 · R10 은 발화하지 않는다 — 결정 표는 사실상 7줄짜리다
    · DOUBT 0.15 는 clean test 에서 ±0.004 안에 이웃이 있다. 민감한 문턱이다
    · 조치 14건 중 13건이 기권이므로, 소수 클래스 지표는 LLM 이 붙어도
      표본이 생기지 않을 수 있다
