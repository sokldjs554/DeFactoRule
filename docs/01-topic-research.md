## 4. 최종 3개 상세 분석

### 후보 1 — `AuthorityGrid` : 위임전결 권한표 정합성 감사 시스템 ★최종 추천

#### Problem
기업의 **위임전결규정(직무권한규정)** 은 "무슨 업무를, 얼마까지, 누가 결재하는가"를 정의하는 표다. 수십~수백 행의 별표로 되어 있고, 조직개편·규정개정·특례 신설이 수십 년간 누적된다. 그 결과 표에는 아무도 모르는 논리적 결함이 조용히 쌓인다.

- 3천만원 계약은 팀장 전결, 5천만원 이상은 본부장 전결 — 그런데 **3천만~5천만원 구간의 결재권자가 없다**
- 별표 1은 "구매 5천만원 = 본부장", 별표 3은 "동일 건 = 팀장" — **동일 사안에 두 결재권자**
- 팀장 한도 1억, 그 상위 실장 한도 5천만원 — **위계 역전**
- 특정 경로에서 **기안자와 전결권자가 동일인**이 될 수 있음 (직무분리 위반)
- "다만 긴급한 경우 1단계 하향 전결할 수 있다"는 단서조항이 상위 규정 한도를 **초과**

이건 감사·컴플라이언스 실무의 실제 고통이다. 미국 기준으로 보면 SOX 404가 결재권한을 최상위 내부통제로 다루며, 승인권한 관련 결함은 감사 지적의 단골 항목이다. 한국은 내부회계관리제도·금융회사 내부통제기준이 같은 위치에 있다.

#### Existing Approach
감사팀이 규정집 PDF를 열어 **엑셀에 옮겨 적고 눈으로 대조**한다. 별표가 5개, 각 100행, 금액 구간이 6개면 조합은 수천 개다. 사실상 전수검사가 불가능해서 **문제가 터진 뒤에야** 발견한다. 조직개편이 있으면 처음부터 다시 한다.

#### Why Existing AI Is Not Enough
이게 이 프로젝트의 핵심 논거다.

1. **RAG는 질문에 답하는 도구지, 전수 성질을 증명하는 도구가 아니다.** "5천만원 계약은 누가 결재?"는 검색으로 답한다. 그러나 "이 표 전체에 구멍이 있는가?"는 검색 문제가 아니다. 답이 문서 어딘가에 **없다는 사실**을 증명해야 한다. 벡터 검색은 부재를 증명하지 못한다.
2. **LLM은 구간 산술과 전수 조합에서 신뢰할 수 없다.** "3천만 초과 5천만 이하"와 "5천만 미만"의 경계 중복/누락을 수백 행에 걸쳐 일관되게 처리하지 못한다. 이건 LLM의 약점이 아니라 **애초에 LLM이 할 일이 아니다**.
3. **결함이 자연어 단서조항에 숨는다.** 표만 파싱하면 안 되고, "다만 ~인 경우 제외한다" 같은 단서를 조건으로 살려야 한다. 여기는 규칙 기반 파서가 못 하고 LLM이 필요한 자리다.

즉 **LLM이 필요한 곳과 필요 없는 곳이 명확히 갈리는 문제**다. 이 분리를 설계로 보여주는 것이 포트폴리오의 핵심 가치다.

#### Core Idea
> 권한표를 "문서"가 아니라 **실행 가능한 술어(predicate)의 집합**으로 재정의하고, 규칙 공간의 결함을 **결정론적으로 증명**한다. LLM은 자연어→술어 번역만 담당한다.

```python
class AuthorityPredicate(BaseModel):
    source: SpanRef              # 별표 N, 행 M, 셀 좌표 — 모든 판정은 원문으로 되돌아간다
    task: TaskCode               # 계층적 업무 코드 (구매 > 물품 > 소모품)
    amount: Interval | None      # 원 단위로 정규화된 [lo, hi) — 개구간/폐구간 명시
    conditions: list[Condition]  # 단서조항의 구조화 결과
    approver: PositionRef        # 조직도 그래프의 노드
    concurrence: list[PositionRef]
    doc_version: VersionRef
```

이후는 **순수 Python**이다. 구간 대수로 업무×금액 격자를 스윕하고, 조직도 DAG로 위계를 검사하고, 제약 solver로 충돌을 찾는다. 여기엔 LLM이 개입하지 않는다 — 그래서 **결과가 재현 가능하고 반증 가능**하다.

#### AI Workflow
```
입력   기관 위임전결규정 (HWP/PDF/HTML) + 조직도 + 상위 규정
  ↓
분석   문서 구조 파싱 → 별표 식별 → 다단 헤더/병합셀 복원 → 셀 그래프
  ↓
추출   [LLM] 셀 + 인접 단서조항 → AuthorityPredicate 후보 (스키마 강제)
  ↓
검색   교차참조 해소: "별표 3에 따른다", 상위 규정 한도, 직위 별칭 정규화
  ↓
추론   [결정론] 구간 대수 스윕 · 조직도 DAG · SoD 경로 탐색 · 제약 충돌 검사
  ↓
검증   Validator: 모든 결함이 원문 span으로 역추적되는가 / 술어가 원문과 모순 없는가
  ↓
결과   결함 리포트 + 권한 커버리지 히트맵 + 근거 원문 하이라이트
```

**판단 유보 경로**: 정규화 신뢰도가 임계 이하인 조항은 결함 판정을 내리지 않고 **human review 큐**로 보낸다. 이 abstention 자체를 지표로 측정한다.

#### Data
| 출처 | 내용 | 근거 |
|---|---|---|
| 국가법령정보센터 **행정규칙** | "○○부 위임전결규정" 다수 — 별표에 업무·금액·전결권자 표 포함 | law.go.kr에서 부처별로 공개 확인 |
| 법제처 Open API | 행정규칙 본문·별표·개정 이력 프로그램 수집 | 공공누리 개방 |
| 공공기관 규정집 | 기관 홈페이지 공개 위임전결규정 (예: 한국석유공사 등) | 웹 공개 확인 |
| **Mutation 생성** | 정상 표에 10종 결함을 프로그램으로 주입 → **정답 라벨 자동 생성** | 자체 구현 |

> **평가셋 설계의 결정적 장점**: 결함 주입 방식이면 정답이 프로그램으로 만들어진다. 신입 포트폴리오에서 가장 흔한 실패("평가셋을 손으로 50개 만들고 끝")를 구조적으로 회피한다. 동시에 **실제 공개 규정에서 사람이 찾아낸 진짜 결함**을 별도 held-out으로 유지해 인위성 반박에 대비한다.

#### Evaluation
프로젝트 특유의 신규 지표를 포함한다.

| 지표 | 정의 | 왜 필요한가 |
|---|---|---|
| **ACR** (Authority Coverage Ratio) | 업무×금액 공간 중 유효 전결권자가 **정확히 1명**으로 결정되는 비율 | 이 프로젝트의 목적함수 그 자체 |
| **SELR** (Silent Exception Loss Rate) ★ | 원문에 존재하는 단서·예외 조건 중 술어 변환 후 **소실된 비율** | 신규 지표. 추출 파이프라인의 "조용한 손실"을 정면으로 측정. 정확도가 높아 보이는데 실제로는 예외가 통째로 사라진 상황을 잡는다 |
| **NF** (Normalization Fidelity) | 원문 조항 → 술어 변환의 의미 보존률 (인간 라벨 대비) | LLM 구간의 품질을 분리 측정 |
| GDR / FGR | Gap Detection Rate / False Gap Rate | 검출력과 오탐의 트레이드오프 |
| **DAR** (Defect Attribution Rate) | 검출 결함을 **원문 span까지 정확히** 지목한 비율 | 감사 실무에서 근거 없는 지적은 무가치 |
| Abstention Precision | 판단 유보한 건이 실제로 판단 불가였던 비율 | "언제 판단하면 안 되는가"의 정량화 |

#### Failure Cases (초기 taxonomy, 30종 이상 구축 예정)
- **파싱군**: 병합셀 / 다단 헤더 / 세로 병합 / 페이지 분할 표 / HWP 중첩 표 / 이미지로 삽입된 표 / 각주 본문 분리
- **정규화군**: 금액 단위 혼용(천원·백만원·억) / "이하 vs 미만" 경계 / 한글 수사("일억원") / 상한 없는 구간 / 단서조항 누락 / 직위 별칭("본부장"="사업본부장")
- **논리군**: 업무 계층 코드 오분류 / 중복 판정 실패 / 조직도 노드 결측 / 순환 위임
- **검색군**: 상위 규정 미검색 / 개정 버전 혼동 / 교차참조 해소 실패
- **LLM군**: 근거 없는 추론 / 과도한 확신 / 환각 직위 생성 / 애매한 표현의 임의 확정

#### Portfolio Value
면접에서 이렇게 말할 수 있다.

> "저는 챗봇을 만들지 않았습니다. 기업 내부통제 문서에는 사람이 전수검사할 수 없는 논리적 공백이 쌓이는데, 이걸 자동으로 **증명**하는 시스템을 만들었습니다. 핵심 설계 판단은 **LLM에게 무엇을 시키지 않을 것인가**였습니다. 구간 산술과 조합 검사는 결정론 코드로 분리하고, LLM은 표와 단서조항을 술어로 번역하는 데만 썼습니다. 그리고 그 번역 품질을 별도 지표(SELR)로 측정했습니다."

애자일소다 DS팀이 하는 일 — "업무 목적/처리 절차/판단 기준을 AI Agent Workflow로 구체화" — 과 문자 그대로 같은 작업이다. 결재 권한은 **판단 기준의 순수한 형태**다.

#### Potential Objections
| 공격 | 대응 |
|---|---|
| "표가 정규화돼 있으면 엑셀 수식으로 되잖아요?" | 맞다. 문제는 **정규화가 안 돼 있다는 것**이다. 기관마다 표 형식이 다르고, 결함의 상당수가 자연어 단서조항에 숨는다. 그래서 LLM이 필요하고, 그 지점을 SELR로 측정했다. |
| "결함 주입 데이터는 인위적 아닌가요?" | 주입 데이터는 개발·회귀용이고, **실제 공개 규정에서 수동 발견한 진짜 결함**을 held-out으로 분리 보고한다. 두 분포의 성능 차이도 함께 공개한다. |
| "공공기관 규정을 기업 업무라고 볼 수 있나요?" | 구조가 동일하다. 금융회사 내부통제기준·내부회계관리제도의 전결 체계도 같은 형태다. 공개 데이터로 재현 가능한 프록시를 택한 것이며, 이 선택 자체가 데이터 전략이다. |
| "LLM 없이 규칙 파서로 하면?" | 실험 E2에 baseline으로 포함한다. 형식이 통일된 표에서는 규칙 파서가 이긴다는 결과가 나와도 그대로 보고한다. |

#### 3-Month Feasibility
가능하다. 병목은 **표 파싱 품질**이고, 이건 알려진 문제라 도구(pdfplumber, HWP 변환, 필요시 VLM)로 접근 가능하다. Solver 부분은 순수 알고리즘이라 예측 가능하다. 평가셋이 자동 생성되므로 실험 반복 비용이 낮다.

### 후보 2 — `LoopClosure` : 감사 지적 → 개선조치 → 규정 반영 폐루프 검증

#### Problem
감사에서 "규정 제○조가 미비하니 개선하라"는 지적이 나온다. 피감기관은 "개선하겠다"고 답한다. 그리고 **실제로 규정이 바뀌었는지는 아무도 끝까지 확인하지 않는다.** 확인하더라도 "개정했다"는 사실만 볼 뿐, **개정 내용이 지적 사항을 실제로 해소했는지**는 판단하지 않는다. 형식적 이행(제목만 바꿈)과 실질적 이행을 구분하는 것이 문제의 핵심이다.

#### Existing Approach
감사 담당자가 지적사항 목록과 개정 규정을 수작업 대조. 지적은 수천 건, 규정 개정은 수만 건. 매칭 자체가 노동이다.

#### Why Existing AI Is Not Enough
- 문서 3종(지적서 · 조치계획 · 개정 규정)이 **서로 다른 어휘**를 쓴다. 지적서는 "내부통제 미흡", 규정은 "제12조 제2항 신설". 의미 매칭이 필요하다.
- 시간축이 있다. 지적 → 조치 → 개정은 순서가 있고, 그 사이 다른 개정이 끼어든다.
- 핵심 판단은 "개정이 있었나"(검색)가 아니라 **"이 개정이 저 지적을 해소하는가"**(함의 판정)다. RAG로는 전자만 된다.

#### Core Idea
> 지적사항을 **"해소 조건(resolution condition)"** 으로 형식화하고, 이후 규정 개정 이력을 시간순으로 재생하면서 각 개정이 그 조건을 만족시키는지 판정한다. 미해소 상태로 남은 지적을 **"열린 루프"** 로 자동 추적한다.

#### AI Workflow
```
입력  감사 지적서 + 처분요구 + 조치결과 + 대상 기관 규정 개정 이력
  ↓
분석  [LLM] 지적사항 → 해소 조건 구조화 (무엇이, 어떻게 바뀌어야 하는가)
  ↓
검색  해당 기관·규정의 지적 이후 개정분 전수 수집 (시점 필터)
  ↓
추론  [LLM] 개정 delta ↔ 해소 조건 함의 판정 (해소/부분해소/무관/역행)
  ↓
검증  [결정론] 시간 순서 검증 · 조문 존재 검증 · 근거 span 필수
  ↓
결과  열린 루프 목록 + 폐루프 타임라인 + 형식적 이행 의심 건
```

#### Data
감사원 감사결과 공개 자료(처분요구·조치결과)와 법제처 행정규칙 개정 이력. 양쪽 다 공개다. 다만 **기관·규정 단위 매칭 키가 없어** 전처리 부담이 크다.

#### Evaluation
- **Loop Closure Accuracy**: 해소/미해소 판정 정확도
- **Formal Compliance Detection Rate** ★신규: 형식적으로만 이행한 건을 잡아내는 비율
- Temporal Ordering Accuracy: 시간 순서 오류율
- Unsupported Claim Rate: 근거 없는 해소 판정 비율

#### Failure Cases
지적-규정 매칭 실패 / 동명이인 기관 / 개정 delta 추출 오류 / 부분 해소의 경계 판단 / 지적서의 모호한 표현 / 조치계획과 실제 개정의 시차

#### Portfolio Value
"AI가 답을 만드는" 프로젝트가 아니라 **"AI가 이행 여부를 감시하는"** 프로젝트다. 문제의식이 성숙해 보인다.

#### Potential Objections
"해소 여부 정답 라벨을 어떻게 만드나?" — 가장 아픈 지점이다. 감사원 후속 감사에서 재지적된 건을 **약한 라벨(미해소)** 로 쓸 수 있으나 커버리지가 낮다. 결국 상당량의 수동 라벨링이 필요하고, 이것이 3개월 일정의 최대 위험이다.

#### 3-Month Feasibility
**중간 위험.** 데이터 매칭과 라벨링에 예상보다 시간이 든다. 범위를 1~2개 기관으로 좁히면 가능.

### 후보 3 — `DeFactoRule` : 예외 승인 이력에서 문서에 없는 판단 기준 역추출

#### Problem
어떤 조직이든 규정에는 "원칙"만 적혀 있고, 실제 판단은 **예외 승인 이력에 축적된 암묵 기준**을 따른다. "이런 조건이면 예외를 허용해준다"는 규칙이 문서 어디에도 없이 관행으로 존재한다. 담당자가 바뀌면 이 기준이 사라지고, 판단이 흔들린다.

#### Existing Approach
경력자의 머릿속. 인수인계 문서에는 "케이스 바이 케이스"라고 적힌다.

#### Why Existing AI Is Not Enough
RAG는 **문서에 적힌 것**만 찾는다. 이 문제의 정답은 문서에 없다. 사례 집합에서 **귀납**해야 하며, 그 결과가 실제 판단을 예측하는지로 검증해야 한다. 생성이 아니라 **규칙 발견**이다.

#### Core Idea
> 승인/거부 사례 코퍼스에서 LLM이 판단 요인 후보를 생성하고, 그 후보들을 **해석 가능한 규칙 학습기**로 압축한 뒤, held-out 사례에 대한 **예측 정확도로 규칙의 진위를 검증**한다. "LLM이 그럴듯한 이유를 말했다"가 아니라 "그 규칙이 실제 판단을 맞힌다"로 판정한다.

#### AI Workflow
```
입력  승인/거부 사례 문서 (신청 내용 + 결과 + 부가조건)
  ↓
분석  [LLM] 사례 → 구조화 피처 (신청 유형, 규모, 사유 범주, 부가조건)
  ↓
추론  [ML] 해석 가능 규칙 학습 (decision rule set) → 후보 규칙 도출
  ↓
검증  [결정론] held-out 예측 정확도 · 규칙 커버리지 · 규정 본문과의 모순 검사
  ↓
결과  "문서에 없는 사실상 규칙" 목록 + 각 규칙의 근거 사례 + 신뢰구간
```

#### Data
금융위 **비조치의견서 / 법령해석 회신사례**, **혁신금융서비스 지정(규제 특례) 공고** 등 공개된 "예외 판단" 코퍼스. 신청 내용·결정·부가조건이 함께 공개된다.

#### Evaluation
- **Rule Predictive Accuracy** ★: 도출 규칙의 held-out 예측 정확도 (규칙의 진위 검증)
- Rule Coverage / Rule Count (간결성)
- **Undocumented Rule Rate** ★신규: 도출 규칙 중 원 규정 본문에 명시되지 않은 비율 = "암묵성"의 정량화
- Contradiction Rate: 명시 규정과 충돌하는 규칙 비율

#### Failure Cases
사례 수 부족 / 클래스 불균형(대부분 승인) / 피처 추출 시 결정적 정보 누락 / 상관을 인과로 오독 / 시기별 정책 변화를 규칙으로 착각 / LLM이 사후 합리화한 이유 생성

#### Portfolio Value
LLM + 전통 ML을 **각자 잘하는 일에 배치**한 사례. 애자일소다가 원래 강화학습·의사결정 최적화 회사라는 점과도 결이 맞는다.

#### Potential Objections
"이건 그냥 분류 모델 아닌가요?" — 목적이 예측이 아니라 **규칙의 명시화**다. 정확도는 규칙이 진짜인지 검증하는 수단이지 목표가 아니다. 다만 이 구분을 설명하는 데 성공해야 한다.

#### 3-Month Feasibility
**중간 위험.** 사례 수가 충분한지가 관건. 초기 2주 안에 데이터 규모를 확인하고 아니면 접어야 한다.

## 5. 최종 추천: 후보 1 `AuthorityGrid`

### 5-1. 선정 이유

| 판단 기준 (지시사항 20항) | 판정 |
|---|---|
| "LLM RAG chatbot"으로 검색하면 비슷한 게 수십 개 나오는가? | **NO** — 유형 자체가 다르다 |
| 제목만 보면 한 번 더 설명해야 할 만큼 독특한가? | **YES** — "권한표 정합성 감사"는 설명이 필요하다 |
| 설명을 들으면 실제 기업에서 충분히 발생할 문제인가? | **YES** — 내부통제 감사의 상시 이슈 |
| 정량적으로 실험·평가할 수 있는가? | **YES** — 결함 주입으로 정답 자동 생성 |

후보 2·3 대비 결정적 우위는 **평가셋 생성 전략**이다. 후보 2는 해소 여부 라벨을, 후보 3은 충분한 사례 수를 사람 손에 의존한다. 후보 1만 **정답이 프로그램으로 만들어진다.** 3개월이라는 제약 아래에서 이 차이는 결정적이다. 실험을 5개가 아니라 50개 돌릴 수 있다.

### 5-2. 왜 이 주제가 흔하지 않은가

1. **"부재의 증명"은 생성형 AI 포트폴리오의 사각지대다.** 대부분의 프로젝트는 "질문 → 답변"이다. 이 프로젝트는 "규칙 집합 → 그 집합의 성질"이다. 출력이 답변이 아니라 **증명**이다.
2. **결재 권한은 지루해 보인다.** 그래서 아무도 안 한다. 그런데 감사·컴플라이언스 실무에서는 최우선 통제 항목이다. "재미없어 보이는데 중요한 문제"는 희소성과 현실성을 동시에 만족하는 드문 영역이다.
3. **LLM을 줄이는 것이 성과인 프로젝트다.** 대부분의 포트폴리오는 LLM을 더 쓰는 방향으로 간다. 이 프로젝트는 **LLM의 책임 범위를 좁히는 것 자체가 설계 성과**다. 이 역방향 사고는 흉내내기 어렵다.

### 5-3. 기존에 흔히 보이는 주제와 무엇이 다른가

| 흔한 프로젝트 | AuthorityGrid |
|---|---|
| 입력: 사용자 질문 | 입력: 문서 전체 |
| 출력: 자연어 답변 | 출력: 결함 목록 + 원문 span + 증명 근거 |
| 성공: 답이 맞다 | 성공: 있는 결함을 다 찾고, 없는 결함을 만들지 않는다 |
| 평가: 사람이 만든 QA셋 | 평가: 결함 주입으로 자동 생성 + 실제 결함 held-out |
| LLM 역할: 전부 | LLM 역할: 자연어→술어 번역만 |
| 실패: 답이 틀림 | 실패: **조용한 손실** (단서조항이 사라져도 답은 그럴듯함) → SELR로 측정 |
| UI: 채팅창 | UI: 권한 커버리지 히트맵 |

## 10. [추가] 후보 3 `DeFactoRule` 확정 및 데이터 생존 게이트 결과

주제가 후보 3으로 확정되어, 보고서 §4에서 "초기 2주 내 확인 후 아니면 접는다"고 명시한 데이터 게이트를 즉시 실행했다.

### 10-1. 게이트 결과 — 조건부 통과

| 항목 | 결과 | 판정 |
|---|---|---|
| 법령해석 회신사례 | 1,560건 (2015~2019 사례집 기준, 이후 누적分 추가) | ✅ 충분 |
| 비조치의견서 | 361건 (동 기간) | ✅ 충분 |
| 통합 조회 | 금융규제·법령해석포털 (better.fsc.go.kr) | ✅ 공개 |
| 혁신금융서비스 부가조건 | 건별로 **구체적 수치까지 공개** (예: 계모임 최대 3개, 구좌당 월 20만원, 1인당 50만원, 지정기간 2년) | ✅ 우수 |
| **미지정·반려 사례** | **공개되지 않음** | ❌ **치명적** |

보고서 §4에서 실패 케이스로 적어둔 "클래스 불균형 — 대부분 승인"이 **현실로 확인**됐다. 혁신금융서비스는 지정된 건만 공표되고 반려·미지정 건은 공개되지 않는다. 원래 설계했던 "승인 vs 거부" 이진 라벨을 만들 수 없다.

### 10-2. 설계 변경 — 타겟 재정의

> **"승인되는가?"** (데이터 없음) → **"어떤 부가조건이, 어느 수준으로 붙는가?"** (데이터 풍부)

혁신금융서비스는 전부 지정되지만 **부가조건이 서로 다르다.** 그리고 그 부가조건을 결정하는 기준은 어디에도 공표된 적이 없다. 이것이야말로 이 프로젝트가 찾으려던 **사실상의 심사 기준**이다.

```
입력   신청 서비스 특성 (업권, 서비스 유형, 취급 자산, 대상 고객,
       규모, 특례를 요청한 규제 조항)
  ↓
출력   부가조건 벡터 (한도 금액, 인원·건수 제한, 지정 기간,
       소비자보호 장치 유형, 보고 의무)
  ↓
질문   무엇이 이 한도를 결정했는가?
```

**이 재정의가 원래 설계보다 강한 이유:**

1. **클래스 불균형이 사라진다** — 모두 지정되지만 조건이 다르므로 라벨이 자연스럽게 분포한다
2. **정량 평가가 훨씬 풍부해진다** — 다중 라벨 + **수치 예측**(한도 금액, 기간)이므로 구간 예측·MAE·순위 상관까지 쓸 수 있다. 이진 정확도 하나보다 실험 설계 여지가 크다
3. **서사가 그대로 유지된다** — "규제당국이 공표한 적 없는 판단 기준을 데이터에서 복원한다"는 문제의식이 오히려 더 선명해진다

### 10-3. 이원 트랙 구성

데이터를 확인한 결과, 서로 성격이 다른 두 코퍼스를 모두 쓸 수 있다.

| 트랙 | 코퍼스 | 라벨 구조 | 설계 |
|---|---|---|---|
| **Track A** | 법령해석 회신사례 + 비조치의견서 (~1,900건+) | 회신 결론이 "해당한다 / 해당하지 않는다", "비조치 / 조치가능"으로 갈림 → **이진** | 원래 설계 그대로 사용 가능 |
| **Track B** | 혁신금융서비스 지정 + 부가조건 | 다중 라벨 + 수치 → **재정의 설계** | §10-2 |

Track A가 살아 있으므로 프로젝트는 성립한다. Track B는 더 독창적이며, 두 트랙을 함께 다루면 "같은 규제기관의 판단 기준을 두 각도에서 복원한다"는 구성이 된다.

### 10-4. 신규 평가 지표 추가

| 지표 | 정의 | 왜 새로운가 |
|---|---|---|
| **Discretion Residual** ★ | 부가조건 중 신청 특성으로 **설명되지 않는 잔차 비율** = 재량의 크기 | 규제 판단에서 "규칙으로 환원되는 부분"과 "재량으로 남는 부분"을 분리 정량화한다. 규칙을 찾는 데 실패한 영역을 실패가 아니라 **측정 대상**으로 전환하는 지표 |
| **URR** (Undocumented Rule Rate) | 도출 규칙 중 원 규정 본문에 명시되지 않은 비율 | 암묵성의 정량화 (기존) |
| Rule Predictive Accuracy | held-out 예측 정확도 — 규칙의 진위 검증 | 기존 |
| Condition Level MAE | 수치형 부가조건(한도·기간) 예측 오차 | Track B 신설 |

`Discretion Residual`은 면접에서 특히 강하다. "규칙을 다 못 찾았습니다"가 아니라 "판단의 몇 %가 규칙으로 환원되고 몇 %가 재량인지를 측정했습니다"가 되기 때문이다.

### 10-5. 환경 제약 — 반드시 알아야 할 것

본 개발 세션의 컨테이너는 네트워크 egress 정책상 다음 도메인에 접근할 수 없다.

```
better.fsc.go.kr    EGRESS_BLOCKED   (법령해석·비조치의견서 포털)
www.data.go.kr      EGRESS_BLOCKED   (공공데이터포털)
```

따라서 **데이터 수집 단계는 로컬 환경에서 수행해야 한다.** 수집 스크립트는 이 세션에서 작성할 수 있으나 실행은 로컬에서 한다. 수집된 데이터를 저장소에 커밋하면 이후 전처리·모델링·평가는 이 세션에서 계속 진행할 수 있다.

### 10-6. 수정된 3개월 로드맵 (변경분만)

| 주차 | 변경 내용 |
|---|---|
| W1 | Track A / Track B 코퍼스 규모 실측 — **로컬 수집 필요**. Track B 지정 건수가 200건 미만이면 Track A 단독으로 축소 |
| W2 | 게이트: Track A ≥ 800건 파싱 성공 **또는** Track B ≥ 150건 부가조건 구조화 성공. 둘 다 미달이면 후보 1(AuthorityGrid)로 전환 |

| W8–9 | 규칙 학습기를 이진 분류 → **다중 라벨 + 수치 회귀** 혼합으로 변경 |
| W11 | 실험에 `Discretion Residual` 측정 추가 |
