# 사안 무리 단위 분할 — 설계와 실행

발단은 [docs/22](22-split-leakage-audit.md) 다 — test 27건이 dev 에 요청문이
같은 선례를 갖는다. 그것을 고치는 설계이고, 뒤이어 실제로 적용한 기록이다.

**§1~§6 은 설계다.** 파일을 하나도 쓰지 않은 시뮬레이션 수치이므로 그렇게 읽어야
한다. **§7 부터가 실측이다** — Phase A 에서 clean split 을 실제로 만들었고
(`*_clean.jsonl`), Phase B-1 에서 그 dev 로 보정표와 규칙을 다시 뽑았다
(`*_clean.json`). **legacy 분할·산출물은 전 구간에서 손대지 않았다.**

전 구간 API 0회 · E1~E11b 재실행 0회 · clean test 평가 0회.

## 1. 지금 분할이 왜 새는가

`app/evaluation/gold_nonaction.py::build()` 가 전부다.

```python
labeled.sort(key=lambda r: (r["source"], r["page"], r["serial"] or ""))
dev  = [x for i, x in enumerate(items) if i % 3 == 0]
test = [x for i, x in enumerate(items) if i % 3 != 0]
```

난수가 없어 재현은 완벽하다. 새는 이유는 다른 데 있다.

**분할 단위가 `행` 이다.** 그런데 평가 독립성이 요구하는 단위는 `사안` 이다.
같은 사안이 여러 행으로 들어와 있으면 — 부동산PF 규제유예처럼 기한을 갱신하며
해마다 다시 실리는 요청이 그렇다 — **3주기로 자르는 순간 같은 사안이 dev 와
test 로 갈린다.**

    27건 중 분할 정렬에서 거리 1 인 쌍   4건
    거리 3 이하                        7건

정렬 키가 `(사례집, 쪽, 일련번호)` 라 **같은 사례집의 가까운 쪽에 실린 중복은
서로 몇 칸 안 떨어진다.** 3주기로 자르면 그런 쌍은 거의 반드시 갈린다. 연도를
넘는 중복(거리 62~136)은 정렬로는 안 붙지만 3주기가 사실상 무작위라 절반 이상
갈린다.

**중복 제거 단계가 파이프라인 어디에도 없다.** 무작위 분할의 사고가 아니라
**무엇이 같은 사안인지 정의하지 않은** 사고다.

### 곁가지 — 행 식별키도 부족하다

시뮬레이션 중에 확인했다. 일련번호 `230014` 가 **같은 사례집 61쪽과 67쪽에
두 번** 있다(둘 다 `기타`). 그러므로 행의 식별키는 `serial` 하나가 아니라
**`(source, page, serial)`** 이어야 한다. 지금 코드도 정렬에는 셋을 쓰지만,
분석·조회 코드 여러 곳이 `serial` 만으로 행을 찾는다. 재분할 때 함께 고친다.

## 2. 무리를 어느 수준에서 묶을 것인가

후보 다섯을 **전부 계산해서** 비교했다(라벨 있는 255건 전체).

| 정의 | 무리 수 | 1건 무리 | 최대 크기 | **27쌍 포착** | 지금 분할을 가로지르는 무리 |
|---|---|---|---|---|---|
| G1 요청문 원문 exact | 229 | 211 | 4 | 10/27 | 9 |
| G2 정규화 후 exact | 209 | 187 | 6 | 26/27 | 14 |
| **G3 G2 + 날짜·일련번호 정규화** | **193** | **164** | **6** | **27/27** | **18** |
| G4 G3 + 숫자·비율 정규화 | 193 | 164 | 6 | 27/27 | 18 |
| G5 사건 family (유사도 ≥ `TRUST`) | 177 | 146 | 6 | 27/27 | 21 |

**G3 을 채택한다.** 근거 셋.

- **G1·G2 로는 부족하다.** 원문 비교는 27쌍 중 10쌍밖에 못 잡고, 공백·글머리만
  정규화해도 1쌍이 남는다. 남는 그 1쌍이 `250058/240090` 인데 **요청문 안에
  기한이 적혀 있어서**(’26.6.30. vs ’25.6.30.) 날짜를 정규화해야 붙는다.
- **G4 는 G3 과 완전히 같다.** 숫자·비율을 더 정규화해도 무리가 하나도 안
  늘었다. **효과가 0 인 규칙은 넣지 않는다.**
- **G5 는 과하게 묶는다.** 유사도 0.60 은 "닮았다" 는 뜻이지 "같은 사안" 이
  아니다. G3 보다 16개 무리를 더 합치는데, 그 안에는 **이 프로젝트가 일부러
  남겨 둔 어려운 표면유사 쌍**이 섞인다. `220049`(0.738)처럼 결론이 갈리는
  쌍까지 한 무리로 묶으면 **TRAP 구간을 스스로 지우게 된다.**

### 27건의 A/B/C 를 각각 어떻게 다루는가

| 분류 | 건수 | 처리 | 왜 |
|---|---|---|---|
| **A** 동일 기록 중복 | 3 | **한 무리로 묶어 한쪽에만 둔다. 행은 지우지 않는다** | 신청인 필드가 없어 "중복 게재" 인지 "동일 문구의 별개 의견서" 인지 못 가린다. 확신 없는 상태에서 데이터를 버리지 않는다. 대신 `dup_group` 표시만 남겨 나중에 판단할 수 있게 한다 |
| **B** 시간적 변형 | 23 | **한 무리로 묶어 한쪽에만 둔다** | 각 연장은 실재하는 별개 결정이므로 지우면 이 코퍼스의 가장 큰 사안 무리가 사라진다. 무리째 dev 에 있으면 연장 계열이 온전한 선례로 남고, test 는 그 계열을 아예 못 본다 |
| **C** 독립 사건·동일 요청 | 1 | **한 무리로 묶는다** | 사건은 별개지만 **요청문이 같으면 시험 문제가 유출된 것**이다. 사건의 독립성보다 **평가의 독립성**을 앞세운다 |

**셋 다 같은 처리로 수렴한다.** 분류가 달라도 시스템이 보는 것은 요청문뿐이기
때문이다. 분류는 "고치는 법" 이 아니라 "무엇을 잃는지" 를 알기 위해 필요했다.

## 3. 분할 규칙

```
1. key(r)  = normalize( 요청문 − 일련번호 표기 − 날짜 표기 )
             normalize = 불가시문자·글머리기호·각주표지·공백 제거 (기존 함수)
2. 무리     = key 가 같은 행의 집합
3. stratum = 그 무리에 들어 있는 **가장 희소한 라벨**   (조치 < 기타 < 비조치)
4. 정렬     = stratum 안에서 무리의 첫 (source, page, serial)
5. 배정     = 정렬 순서로 i % 3 == 0 이면 dev, 아니면 test
6. 불변식   = 한 무리는 반드시 한쪽에만 있다
```

**난수를 쓰지 않는다.** 같은 입력이면 같은 결과다 — 지금 분할이 잘한 유일한
점이고 그대로 가져간다. 바뀌는 것은 **자르는 단위**뿐이다.

**층화를 넣은 이유는 계산해서 확인했다.**

    층화 없음   dev 87 / test 168   ·  test `조치` **13**
    층화 있음   dev 86 / test 169   ·  test `조치` **14**  ← 지금과 같다

`조치` 는 255건 중 22건뿐이라 무리 하나가 어긋나면 비율이 흔들린다. 층화는
**가장 희소한 라벨을 먼저 고르게 배분**해 그것을 막는다. 이 프로젝트의 모든
소수 클래스 수치가 그 14건 위에 있으므로, 그 수를 지키는 것이 옳다.

## 4. 분포가 어떻게 달라지는가 (시뮬레이션)

**같은 코드로 현재 분할도 재서 나란히 놓았다** — 다른 코드로 잰 값을 비교하는
것은 이 저장소가 실패 패턴으로 등록한 `mismatched-sample` 이다.

| | 현재 분할 | 무리 분할(층화) |
|---|---|---|
| dev / test | 85 / 170 | 86 / 169 |
| **잔여 유사도 ≥ 0.99 쌍** | **27** | **0** |
| dev·test 가 공유하는 무리 | 18 | **0** |
| 문턱 위 선례를 갖는 test | 87 (51.2%) | 65 (38.5%) |
| **TRAP 순응** | **72** | **50** |
| **TRAP 함정** | **15** | **15** |
| 선례 없음 | 83 | 104 |

**순응 구간이 크게 주는데 함정 구간은 거의 그대로다.** 이것이 이 설계의 가장
중요한 관측이다 — 누수는 **거의 전부 순응 구간을 부풀리고 있었다.**
[docs/22](22-split-leakage-audit.md) 에서 27쌍 중 26쌍이 라벨까지 같다고 센 것과
맞는다.

> **[실측으로 정정]** 위 표는 무리를 `serial` 로 정렬해 돌린 시뮬레이션이다.
> 실제 구현은 행 식별키를 `(source, page, serial)` 로 바꿨고(§1 곁가지),
> 그 때문에 3주기 경계에 걸리는 무리가 달라져 결과가 조금 옮겨졌다.
> **실측은 순응 48 · 함정 12 · 선례없음 108 이다**(예상 50 · 15 · 104).
> 함정이 15 에서 12 로 줄었으므로 "함정은 그대로" 라는 예상은 정확히는
> 맞지 않았다. 다만 방향은 같다 — 순응 −24 · 함정 −3. 실측 전체는 §7 에 있다.

### 라벨별

| 라벨 | 전체(255) | 현재 test | 새 test | 문턱 위 선례 보유 (현재 → 새) |
|---|---|---|---|---|
| 비조치 | 184 | 126 | 122 | 70/126 → 50/122 |
| 기타 | 49 | 30 | 33 | 16/30 → 13/33 |
| **조치** | **22** | **14** | **14** | **1/14 → 2/14** |

### 연도별

    dev   2022 16 · 2023 26 · 2024 29 · 2025 15
    test  2022 33 · 2023 49 · 2024 50 · 2025 37

현재(dev 17/25/26/17 · test 32/50/53/35)와 큰 차이가 없다. 무리가 연도를
가로지르는 경우가 있어 미세하게 이동한다.

### `조치 = 0` 문제 — **이 재분할로 고쳐지지 않는다**

`조치 = 0` 이라는 말이 세 군데에서 나왔는데, 뜻이 다르므로 구분해 적는다.

    ① applicability 사정거리 22건에 `조치` 0건        (docs/19)
    ② Temporal 3정책 교집합 39건에 `조치` 0건          (docs/21)
    ③ test 전체의 `조치`                              14건 — 0이 아니다

**①·② 는 "선례가 붙는 `조치` 사건이 거의 없다" 는 같은 사실의 두 얼굴이다.**
새 분할에서도 문턱 위 선례를 갖는 `조치` 는 **14건 중 2건**이다(현재 1건).
1 → 2 는 개선이라 부를 수 없다.

**이것은 분할의 문제가 아니라 코퍼스의 성질이다.** E5 에서 이미 확인했다 —
`조치` 는 닮은 선례를 거의 갖지 못한다. 재분할로도, 시간 필터로도, 검색기
교체로도 좋아지지 않는다. **이 프로젝트에서 가장 비싼 오류 구간은 선례로
풀리는 문제가 아니다.** 그 사실을 여기 다시 못 박는다.

### R1/R5/R6 경로 분포 — **지금은 계산할 수 없다**

Router 는 `trap_risk` 를 보고, 그 보정표는 **dev 에 묶여 있다**(dev
leave-one-out). dev 가 바뀌면 보정표부터 다시 만들어야 하고, 그것은 곧
재실행이다. 그러므로 **구조적 예상만 적고 수치는 쓰지 않는다.**

    R5 (표면만 닮음)   문턱 위 선례가 87 → 65 로 주므로 **발화가 줄 것이다**
    R2 (근거 없음)     선례 없음이 83 → 104 로 늘므로 **발화가 늘 것이다**
    R1 (규칙 충돌)     규칙은 dev 에서 유도되므로 dev 가 바뀌면 규칙도 바뀐다.
                       방향을 예상하지 않는다
    R6 (다출처 불일치)  선례 풀이 줄면 상위 근거의 출처 다양성이 줄어
                       **발화가 줄 것이다**

**전부 예상이다. 재분할 후 측정해야 한다.**

## 5. 평가에 미치는 영향 — legacy 와 clean 을 나눈다

**새 분할을 적용하면 E1~E11b 를 전부 다시 재야 한다.** dev 가 바뀌면 선례 풀·
유도 규칙·`trap_risk` 보정·TRAP 파티션이 전부 바뀌기 때문이다.

기존 결과를 **지우지 않는다.**

    legacy evaluation   지금까지의 E1~E11b. 행 단위 분할 위에서 잰 값
                        experiments/results/*.json 은 그대로 두고 표시만 붙인다
    clean evaluation    무리 단위 분할 위에서 다시 잰 값. 새 파일로 남긴다

**두 결과를 직접 비교하지 않는다.** test 가 170 → 169 이고 **구성원이 다르다.**

    두 분할 모두에서 test 인 건    107 (비조치 79 · 기타 21 · 조치 7)
    현재 test 에만 있는 건          63
    새 test 에만 있는 건            61

*(일련번호 기준. `230014` 중복 때문에 ±1 오차가 있다 — §1 곁가지)*

비교하려면 **107건 교집합에서만** 하고, 그 사실과 크기를 함께 적는다. 표본이
다른데 "전후 성능이 좋아졌다/나빠졌다" 로 쓰지 않는다.

**그리고 clean 쪽 수치가 legacy 보다 낮게 나오는 것이 정상이다.** 공짜로
맞히던 27건이 사라지기 때문이다. **낮아진 것이 나빠진 것이 아니다** — 원래
그만큼이 실력이 아니었던 것이다. 이 문장을 미리 적어 두는 이유는, 수치가
떨어졌을 때 그것을 회귀로 오해하지 않기 위해서다.

## 6. Temporal 과의 순서

```
무리 단위 분할
  → clean evaluation set 확정
  → Temporal 정책(T-serial / T-strict) 재평가
  → 필요하면 Temporal filter 적용
  → E1~E11b 재실행
```

**이 순서를 고정한다.** [docs/21](21-temporal-policy-impact.md) 의 T-serial /
T-strict 수치는 **현재(누수가 있는) 분할 위에서 잰 것**이므로 재분할 뒤에
달라진다. 그러므로 지금 그 수치로 정책을 고르지 않는다 — **참고자료로만
유지한다.**

한 가지 더. 무리 분할은 **같은 사안의 시간적 변형을 통째로 한쪽에 몰아 넣는다.**
그러면 test 는 그 계열의 과거 선례를 아예 못 보게 되므로, **Temporal 필터가
막을 미래 선례 자체가 줄어든다.** 두 처방이 겹치는 부분이 있다는 뜻이고,
그 크기는 재분할 후에야 잴 수 있다.

## 이 설계가 지금보다 더 독립적인 이유

한 문장으로 — **자르는 단위를 행에서 사안으로 올렸기 때문이다.**

지금 분할은 "같은 사안이 여러 행일 수 있다" 는 사실을 모르는 채 3주기로
잘랐다. 그래서 27건에서 시험 문제가 참고서에 실렸다. 무리 분할은 **한 무리가
양쪽에 놓일 수 없다는 것을 불변식으로** 두므로, 그 사고가 **구조적으로**
일어나지 않는다.

시뮬레이션이 그것을 확인한다 — **dev·test 가 공유하는 무리 0개, 잔여 유사도
≥ 0.99 쌍 0건.** 우연히 0 이 된 것이 아니라 정의상 0 이다.

다만 **0.99 미만의 누수까지 없앤 것은 아니다.** 요청문이 다르면서 사실상 같은
사안인 경우는 G3 로 안 묶인다. 그것을 잡으려면 G5 같은 유사도 기반 묶음이
필요한데, 그러면 이 프로젝트가 일부러 남겨 둔 어려운 표면유사 쌍까지 지운다.
**여기서 멈추는 것이 옳다고 보지만, 멈춘 자리를 적어 둔다.**

## 7. Phase A 실측 — 실제로 만든 clean split

설계만 하고 멈췄던 것을 실제로 적용했다. 산출물은 **새 파일**이고 legacy 는
그대로 두었다.

    data/eval/nonaction_dev_clean.jsonl    87건
    data/eval/nonaction_test_clean.jsonl  168건
    구현: app/evaluation/group_split.py · scripts/group_split.py
    legacy: nonaction_dev.jsonl · nonaction_test.jsonl — **손대지 않았다**

### 예상과 실측

| 항목 | 설계 예상 | **실측** | 비고 |
|---|---|---|---|
| dev / test | 86 / 169 | **87 / 168** | 정렬키가 `serial` → `(source,page,serial)` 로 바뀐 결과 |
| 무리 수 | 193 | **193** | 일치 |
| 양쪽에 걸친 무리 | 0 | **0** | 불변식 성립 |
| 유사도 ≥ 0.99 교차쌍 | 0 | **0** | legacy 27 → 0 |
| test `조치` | 14 | **14** | 일치 |
| TRAP 순응 | 50 | **48** | |
| TRAP 함정 | 15 | **12** | 예상과 다르다 |
| 선례 없음 | 104 | **108** | |
| 문턱 위 선례 보유 | 65 | **60** (35.7%) | |

**차이의 원인은 하나다.** 설계 시뮬레이션은 무리를 `serial` 로 정렬했고, 구현은
지시받은 대로 `(source, page, serial)` 로 정렬한다. 정렬이 바뀌면 `i % 3` 경계에
걸리는 무리가 달라지고, 무리 크기가 1~6 이라 몇 건이 반대편으로 옮겨간다.
**예상이 틀린 것을 지우지 않고 적어 둔다.**

    dev   비조치 63 · 기타 16 · 조치  8    2022 16 · 2023 28 · 2024 27 · 2025 16
    test  비조치 121 · 기타 33 · 조치 14   2022 33 · 2023 47 · 2024 52 · 2025 36

Router 의 전제가 새 dev 에서도 서는지 확인했다(메모리에서만 계산, 파일은
쓰지 않았다).

    clean dev 87건 · LOO · 전체 오류율 0.322
    믿음 구간 상한 0.177  <  못믿음 구간 하한 0.398   — **겹치지 않는다**

legacy 에서 0.062 vs 0.500 이던 것이 좁혀졌지만 **여전히 분리된다.** 누수가
믿음 구간의 오류율을 낮춰 보이게 하고 있었다는 뜻이다. R5·R8 의 근거는
살아 있다.

### 경로 분포 (clean dev 보정 + legacy E6 규칙)

    R1 44 · R2 42 · R3 36 · R5 25 · R6 2 · R7 0 · R8 19 · R9 0 · R10 0
    경로  A 19 · B 59 · C 90        기권 90 / 168

**두 가지를 단서로 남긴다.**

- **E6 규칙은 아직 legacy 다.** 규칙은 dev 에서 유도되므로 clean dev 로 다시
  뽑아야 하고, 그것은 Phase B 의 일이다. 그러므로 **R1(규칙 충돌) 44 는 아직
  clean 수치가 아니다.**
- **R10 이 0회다.** R10 은 "남은 경우 선례를 쓰되 Validator 가 본다" 는
  마지막 줄인데 한 번도 발화하지 않았다. 이 저장소는 발화하지 않는 줄을 지운
  적이 있다(R4). **Phase B 에서 확인할 항목으로 적어 둔다** — 지금은 Router 를
  건드리지 않는다.

### `230014` 는 어떻게 갈렸나

같은 사례집 61쪽·67쪽의 두 행이고 **요청문이 서로 다르다** — 그러므로 무리
키도 다르고, 61쪽은 dev, 67쪽은 test 로 갔다. **행 식별키를
`(source, page, serial)` 로 두었기에 가능한 처리**다. `serial` 만 썼다면 둘 중
하나가 조용히 사라지거나 덮어써졌을 것이다.

행 식별키 중복 0건 · legacy 255행이 clean 255행으로 **집합까지 동일**하게
보존됐다(지운 행 없음).

### 결정성

`split()` 을 다시 돌려 dev·test 의 행 순서까지 동일함을 확인했다. 난수는
쓰지 않는다.

## 8. Phase B-1 — clean dev 로 보정표와 규칙을 다시 뽑는다

Phase A 는 **분할만** 했다. Router 가 쓰는 두 산출물(`trap_risk`·E6 규칙)은
둘 다 **dev 에서 유도되는 것**이므로, dev 가 바뀌면 다시 뽑아야 한다.

**절차는 legacy 와 글자 그대로 같다.** 입력 파일만 바꿨다. 새로운 보정 방식도,
새로운 문턱도 만들지 않았다.

    python3 scripts/calibrate.py    --dev data/eval/nonaction_dev_clean.jsonl \
                                    --output experiments/results/trap_risk_clean.json
    python3 scripts/induce_rules.py --dev data/eval/nonaction_dev_clean.jsonl \
                                    --report experiments/results/e6_rules_clean.json

    legacy: trap_risk.json · e6_rules.json — **손대지 않았다**
    production Router 는 아직 legacy 를 읽는다 (`scripts/agent.py` 기본값)

`--test` 를 붙이지 않았다. 이 단계에서 clean test 를 여는 것은 금지돼 있다.
그래서 `induce_rules.py` 의 `--test` 를 선택 인자로 바꿨고, 없으면 전이 측정을
건너뛰고 `test_support`·`test_precision` 을 **`null` 로 남긴다.** 기존 호출은
전부 `--test` 를 주므로 동작이 달라지지 않는다.

### 8.1 보정 — clean dev 87건 · LOO

R5·R8 의 전제가 clean dev 에서도 선다.

    기타    legacy n 18 · 0.611 [0.386, 0.797]    clean n 16 · 0.688 [0.444, 0.858]

**어느 쪽이 좋다고 읽지 않는다.** 두 표는 서로 다른 dev 87건과 85건에서 나온

신뢰구간이 전부 크게 겹친다는 사실도 그대로 적는다 — 예컨대 doubt 는

차이는 구분되지 않는다.

### 8.3 문턱은 다시 뽑지 않았다 — **미해결로 남긴다**

`DOUBT = 0.15` · `TRUST = 0.60` 은 **legacy dev 에서** 정한 값이다. 이번에
clean dev 로 재유도하지 않고 **그대로 물려받았다.** 그러므로 8.1 의 구간
경계는 clean 데이터가 고른 경계가 아니라 legacy 가 고른 경계다.

지금 바꾸지 않는 이유는 두 가지다. 첫째, 이 단계의 지시는 "동일한 절차로 다시
계산" 이고 문턱 재유도는 새 절차다. 둘째, 문턱은 `app/domain/similarity.py`
한 곳에서만 정해지고 그것을 바꾸면 production Router 가 즉시 바뀐다.
**결정할 사항으로 남겨 둔다.**

### 8.4 E6 규칙 — clean dev 에서 다시 유도

설정(n-gram 길이·min_df·최소 피복 4·최소 정밀도 0.8·최대 깊이 3·빔 12)은
legacy 와 **완전히 동일**하다. 규칙 수도 11개로 같고, 라벨 구성도 같다
(비조치 7 · 기타 3 · 조치 1).

     1  비조치  피복 22  정밀 1.00  본문에 '에따른' AND '제1항'
     2  비조치  피복 10  정밀 1.00  본문에 '’24.' 포함
     3  비조치  피복  9  정밀 1.00  본문에 '조치를' 포함
     4  비조치  피복  7  정밀 1.00  본문에 '<별표' 포함
     5  비조치  피복  4  정밀 1.00  본문에 '□가상자산사업자가' 포함
     6  기타    피복  4  정밀 1.00  본문에 '서비스' AND '□금융회사'

**11개 중 살아남은 규칙은 1개다.**

    공유         본문에 '<별표' 포함 -> 비조치   (dev 피복 5 -> 7, 정밀 0.80 -> 1.00)
    legacy 전용  10개

dev 를 85건에서 87건으로 바꿨을 뿐인데 규칙 집합이 거의 완전히 갈라졌다.
**이 규칙들이 dev 표본에 매우 민감하다는 뜻이다.** legacy 규칙의 test 정밀도가
좋아 보였던 것도 test 에 같은 사안이 실려 있었기 때문일 수 있다 — 그러나
그것은 clean test 를 평가해야 알 수 있는 것이고, 여기서 단정하지 않는다.

### 8.5 기본 라벨이 바뀐 것은 **4건이 정한 것이다**

기본 라벨은 "어떤 규칙에도 걸리지 않고 남은 행" 의 최빈 라벨이다.

    legacy  규칙이 덮은 것 71 / 85   남은 14건 = 비조치 6 · 기타 5 · 조치 3  -> 비조치
    clean   규칙이 덮은 것 83 / 87   남은  4건 = 기타 2 · 비조치 1 · 조치 1  -> 기타

**비조치 -> 기타 의 근거는 2 대 1 대 1 이다.** 도메인이 달라졌다는 신호로 읽지
않는다. 남은 표본이 4건이면 최빈값은 거의 아무 뜻이 없다.

덮은 비율이 83.5% -> 95.4% 로 올라간 것도 **자기 dev 에 대한 적합**이고
일반화가 아니다. 전이는 `test_*` 가 null 이라 아직 모른다.

### 8.6 clean 규칙에서 눈에 걸리는 두 가지

**(1) 날짜가 예측 변수로 들어왔다.**

    2  비조치  피복 10  정밀 1.00  본문에 '’24.' 포함

`’24.` 은 연도 표기다. 사안의 성질이 아니라 **문서가 언제 실렸는가**를 보고
`비조치` 를 맞히고 있다. 2024년 문서에 `비조치` 가 몰려 있으면 dev 에서는
정밀도 1.00 이 나오지만, 이것은 규제 판단의 근거가 아니라 코퍼스의 표기 흔적이다.
`docs/21` 의 temporal 논의와 같은 종류의 문제다.

**(2) 본문이 아니라 메타데이터를 본다.**

    8  기타  피복 6  정밀 1.00  업권이 '공통'

`업권` 은 사례집이 붙여 둔 분류다. 규칙이 맞기는 하지만 "왜 기타인가" 를
설명하지 않는다.

둘 다 **지금 고치지 않는다.** 유도기의 원자(atom) 목록을 손대는 것은 절차
변경이고, 이 단계는 "동일한 절차로 다시 계산" 이다. **결정할 사항으로 적어
둔다.**
