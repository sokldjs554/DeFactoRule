## 2. 어떤 과정에서 dev/test 로 갈라졌는가

`app/evaluation/gold_nonaction.py` 의 `build()` 가 전부다.

```python
labeled.sort(key=lambda r: (r["source"], r["page"], r["serial"] or ""))
dev  = [x for i, x in enumerate(items) if i % DEV_EVERY == 0]   # DEV_EVERY = 3
test = [x for i, x in enumerate(items) if i % DEV_EVERY != 0]
```

**정렬 후 3의 배수 인덱스만 dev.** 난수가 없어 재현은 완벽하다. 문제는 다른
데 있다.

- **중복 제거 단계가 파이프라인 어디에도 없다.** 같은 요청문이 여러 기록으로
  들어와도 그대로 남는다.
- 정렬 키가 `(사례집, 쪽, 일련번호)` 이므로 **같은 사례집에서 가까운 쪽에
  실린 중복은 서로 몇 칸 안 떨어진다.** 27건 중 **거리 1 이 4건, 거리 ≤3 이
  7건**이다. 3칸 주기로 자르면 그런 쌍은 높은 확률로 dev·test 로 갈린다.
- 연도를 넘는 중복(거리 62~136)은 정렬로는 붙지 않지만, 3주기 분할이 무작위와
  같아서 절반 이상이 갈린다.

**이것은 무작위 분할의 사고가 아니라 결정론적 분할의 사고다.** 난수를 없앤 것은
옳았지만, **무엇이 같은 사안인지 정의하지 않은 채 행 단위로 잘랐다.**

## 3. 같은 요청에 라벨이 갈리는 것은 중복인가 판단 변동인가

라벨이 갈리는 쌍은 **1건뿐**이다.

    240006 (test, 비조치)   ←   230094 (dev, 기타)   유사도 1.0000

둘 다 「여신전문금융회사 PF대주단협의회 운영협약」 의결을 거친 사업장 여신의
자산건전성 분류 기준을 한시 준용해 달라는 **같은 요청**이고, 회신은 기한만
다르다(2024.3.31. vs 2024.1.24.).

**중복 데이터가 아니라 서로 다른 시점의 별개 회신이다.** 다만 **라벨이 왜
갈렸는지는 이 데이터로 가릴 수 없다.** 두 읽기가 다 가능하다.

    ① 실제 판단 변동      연장 여부·조건이 달라져 체크박스가 달리 표시됐다
    ② 체크박스 표기 차이   같은 성격의 회신인데 담당자가 다르게 표시했다

라벨의 출처가 **인쇄된 체크박스**라는 것이 이 프로젝트 라벨의 강점인데,
같은 사안에서 표기가 갈린 실례가 나온 것이다. **어느 쪽인지 단정하지 않는다.**

나머지 26건은 라벨이 같다.

## 4. 같은 원문 사례가 여러 번 들어갔는가 · 중복의 성질

**여러 번 들어갔다.**

    회신까지 글자 그대로 같은 쌍            3건 (분류 A)
    dev 선례 풀 자체의 중복 그룹             8개 (그중 라벨이 갈리는 그룹 1개)

**중복의 성질** — 단순 문자열 중복이 아니라 대부분 정규화 수준의 중복이다.

    요청문이 원문 그대로 동일                10 / 27
    정규화(공백·글머리·불가시문자) 후 동일     26 / 27
    날짜까지 정규화하면 동일                 **27 / 27**

즉 **27건 전부가 "같은 요청문"** 이다. 원문 비교만으로는 10건밖에 안 잡히고,
날짜를 정규화해야 전부 드러난다.

## 5. 요약

### ① 진짜 leakage 건수 — **27건 전부**

분류가 A 든 B 든 C 든, **시스템이 보는 것은 요청문뿐이다.** 회신 쪽은 순환
차단을 위해 입력에 넣지 않는다. 그런데 요청문은 27/27 이 동일하다.
**그러므로 검색 기반 방법에게는 27건이 전부 구분 불가능한 중복이고, 유사도
1.0 의 선례에 라벨이 붙어 딸려 온다.**

    27 / 170  =  test 의 15.9%

"A 만 진짜 누수" 라고 좁게 세면 3건이지만, **누수의 정의를 "정답이 공짜로
따라오는가" 로 두면 27건 전부다.** 이 문서는 뒤의 정의를 쓴다.

### ② 독립 사건으로 볼 수 있는 건수 — **24건** (B 23 + C 1)

사건으로서는 별개다. 규제 유예의 각 연장은 실제로 내려진 별개의 결정이고,
`250047` 은 신청인이 다른 별개 판단이다. **사건이 별개라는 것과 평가에서
분리돼야 한다는 것은 다른 문제다** — 요청문이 같으면 시험 문제가 이미 유출된
것이기 때문이다.

### ③ 판단 불가 건수 — **0건**

27건 모두 본문을 읽어 분류했다. 다만 A 3건에서 "같은 의견서의 중복 게재" 인지
"동일 문구의 별개 의견서" 인지는 **신청인 필드가 없어 가릴 수 없다.** 분류
자체(기록으로서 중복)는 확정이다.

### ④ 현재 E1~E11b 평가에 미치는 잠재적 영향

**재계산하지 않았다.** 구조적으로 말할 수 있는 것만 적는다.

- 영향 범위의 상한은 **27건(15.9%)** 이다.
- 그중 **26건은 선례와 라벨이 같다.** 최근접 선례를 따르는 방법은 그 26건을
  근거 없이 맞힌다. `조치` 는 0건이므로 소수 클래스 수치에는 영향이 없다.
- **TRAP 지표의 파티션이 흔들린다.** TRAP 은 최근접 선례의 라벨 일치로 구간을
  가르는데, 26건이 "일치" 쪽으로 들어가 **순응 구간을 부풀린다.** 유일하게
  라벨이 갈린 `240006` 은 함정 구간으로 들어간다.
- E1~E4·E7 의 LLM 판정기는 선례를 쓰지 않으므로 이 경로의 영향이 없다.
  **영향은 검색·선례를 쓰는 계열(E5·E6·E8~E11b)에 몰린다.**

**얼마나 달라지는지는 수치로 말하지 않는다.** 재평가 단계의 몫이다.

### ⑤ 평가셋을 재구성해야 하는가 — **필요하다. 다만 "다시 나누기" 가 아니다**

행을 지우는 것은 답이 아니다. 24건은 실재하는 별개 결정이고, 지우면
**부동산PF 규제유예라는 이 코퍼스의 가장 큰 사안 무리가 통째로 사라진다.**

필요한 것은 **분할 단위를 행에서 사안 무리로 올리는 것**이다.

    무리 짓기   요청문을 정규화(공백·글머리·불가시문자 + **날짜**)해 같은 것끼리 묶는다
                27/27 이 이 정규화에서 붙는다
    분할        무리 전체를 dev 또는 test 한쪽으로만 보낸다 (무리 단위 분할)
    기록        무리 크기 분포와, 분할로 옮겨진 건수를 남긴다

이 변경은 **dev/test 의 크기와 구성을 바꾸므로 E1~E11b 를 전부 다시 재야
한다.** 그러므로 지금 하지 않는다 — 하려면 그 비용을 알고 시작해야 한다.

그리고 [docs/21](21-temporal-policy-impact.md) 의 시간 정책 수치도 이
재구성 뒤에 다시 재야 한다. **순서가 있다: 분할이 먼저다.**

**같은 문제가 입력끼리의 관계에서 다시 나왔다** — 시험 문제와 참고서에 같은
문항이 들어가 있는 것이다. 라벨 누출은 막았는데 **사안 누출은 보지 않았다.**

`split-discipline` 범주의 사례이고, 등록 여부는 다음 단계에서 정한다.
