# 최종 업무 Agent Workflow 설계

**이 문서는 설계만 한다. 코드는 없다.** 여기 적힌 것 중 구현된 것은
"현재 자산" 으로 표시한 것뿐이고, 나머지는 전부 **설계 목표**다. 구현했다고
주장하지 않는다.

기준이 되는 사건은 하나다 — **AG-13**(`surface-match-as-evidence`). E11b 실측
`220049` 에서 모델은 원문에 실재하는 문장을 인용했지만 그 문장은 **두 요청에
똑같이 있는 문장**이었고, 결론을 가른 구절은 건드리지 않았다. 인용이 원문에
있다는 것만으로 근거가 되지 않는다는 뜻이다. 이 문서의 설계는 대부분 그
한 문장에서 나온다.

---

## 0. Agent 의 업무 단위 — 한 문장

> **금융회사가 제출한 규제 예외 요청 한 건에 대해, 인용된 규정과 과거
> 회신 선례를 검토하여 "이 선례가 이 요청에 적용되는가" 를 결정적 조건
> 단위로 대조하고, 근거가 충분하면 결론(비조치/조치/기타)을, 충분하지
> 않으면 추가정보 요청 또는 담당자 이관을 내놓는다. 모든 결론에는 그것을
> 뒤집을 수 있었던 조건과 그 조건의 출처가 붙는다.**

이 문장에서 의도적으로 뺀 것이 있다.

- "승인/반려" 라고 쓰지 않았다. 이 데이터의 라벨은 `비조치`/`조치`/`기타`
  이고 `기타` 는 반려가 아니다(소관 아님·이미 허용됨·요건 미비 등이 섞여
  있다). 없는 의미를 라벨에 씌우지 않는다.
- "정확히 맞힌다" 를 목표로 쓰지 않았다. E1~E11b 에서 반복해서 확인한 것은
  **맞히는 것보다 언제 답하지 말아야 하는지가 이 업무의 값어치**라는 것이다.

### 데이터가 진짜 무엇인지 먼저 적는다

이 저장소의 자료는 **접수 대기 중인 예외 승인 요청 큐가 아니라, 이미 회신이
끝나 공개된 사례집**이다. 그러므로 "실제 업무 요청을 받는다" 는 설계는
사례집의 `요청대상행위` 를 **접수 시점의 요청서로 간주**해 재생하는 것이다.
이 치환을 문서 앞에 적어 두지 않으면 이후의 모든 평가가 과장된다.

    비조치 사례      259건 (요청대상행위 · 판단 · 판단이유)
    라벨             dev 85 / test 170  — 인쇄된 체크박스에서 나온다(순환 없음)
    법령해석         836건 (질의요지 · 회답 · 이유) — **라벨 없음**
    질의–회답 쌍     1,122건
    유도 규칙        11개 (E6, dev 에서 학습 · 명시 규정이 아니다)

## 1. 지금 무엇이 없는지 — 설계의 전제

**명시 규정 원문이 저장소에 없다.** 이것이 이 설계의 가장 큰 제약이다.

    조문(제N조)이 언급된 사례      218 / 259
    그 조문의 **원문**             없음

인용은 대부분 `판단이유` 안에 있다. 그런데 `판단이유` 는 **회신문의 답변
쪽**이다. 판단해야 할 사건의 `판단이유` 를 근거로 쓰면 정답을 보고 답하는
것이고, 이 프로젝트가 W1 게이트부터 막아 온 순환 그 자체다.

그래서 "Explicit Rule Retrieval"(2단계)은 다음 셋 중 하나로만 성립한다.

| 안 | 무엇을 색인하나 | 순환 | 비용 |
|---|---|---|---|
| A. 인용 색인 | **dev 선례의** `판단이유` 에서 조문 인용만 뽑아 색인 | 없음 (dev 만) | 0 |
| B. 법령 원문 | 국가법령정보센터에서 인용된 조문 원문을 수집 | 없음 | 새 데이터 |
| C. 안 함 | 2단계를 비우고 선례만 쓴다 | 없음 | 0 |

**설계는 A 를 기본으로 하고, B 를 조건부로 둔다.** A 는 "이 조문이 걸린
과거 사건들" 이라는 축을 공짜로 만든다 — 그것만으로도 선례 검색이 문자
유사도 하나에 의존하는 현재 구조가 깨진다. B 가 필요한 이유와 규모는 §12 에
적는다. C 는 현재 상태이고, AG-13 은 C 에서 났다.

## 2. Workflow 11단계

각 단계에 Input / Output / 책임 주체 / 실패 조건 / 진행 조건을 적는다.
**책임 주체**는 셋 중 하나로만 표기한다 — `LLM` · `Retriever` · `결정론`.

### S1. Request Structuring

| | |
|---|---|
| **Input** | 요청 원문 (`요청대상행위`) |
| **Output** | `structured_request` — 요청 행위 · 대상 · 인용 조문 · 조건절 목록 · 요청 유형 |
| **주체** | **LLM**(의미 추출) + **결정론**(조문 표기 정규화 · 스키마 검증) |
| **실패 조건** | 스키마 위반 · 요청 행위가 비어 있음 · 인용 조문 표기가 정규형으로 안 떨어짐 |
| **진행 조건** | 스키마 통과 AND 요청 행위 1개 이상 |

조건절을 여기서 뽑는 것이 S5(결정적 조건)의 전제다. 지금 워크플로는 이
단계가 아예 없고 원문을 그대로 n-gram 에 넣는다 — AG-13 의 먼 원인이다.

**누출 차단(현재 자산 재사용):** `요청대상행위` 에 결론 낱말이 남아 있으면
모델은 읽기만 하면 된다. 기존 `LEAK` 마스킹과 그 회귀 검사를 그대로 건다.

### S2. Explicit Rule Retrieval

| | |
|---|---|
| **Input** | `structured_request.인용조문`, 요청 행위 |
| **Output** | `explicit_rules[]` — 조문 식별자 · (원문 또는 인용 맥락) · 출처 · 근거 강도 |
| **주체** | **Retriever** |
| **실패 조건** | 인용 조문이 색인에 없음 · 정규화 실패 |
| **진행 조건** | 항상 진행 (0건이어도 S3 로 간다 — 규정이 안 걸리는 요청이 있다) |

§1 의 안 A 기준으로, 여기서 나오는 것은 **"이 조문이 걸렸던 과거 사건들"**
이지 조문 원문이 아니다. 그 사실을 `근거 강도` 에 명시적으로 담는다.
안 B 를 채택하면 같은 자리에 원문이 들어오고 강도가 올라간다.

### S3. Precedent Retrieval

| | |
|---|---|
| **Input** | `structured_request`, 요청 원문 |
| **Output** | `precedent_candidates[]` — 선례 · 유사도 · 검색기(L/D/H) · 조문 겹침 |
| **주체** | **Retriever** |
| **실패 조건** | 후보 0건 · 유사도 전부 `DOUBT` 미만 |
| **진행 조건** | 항상 진행 (0건이면 S7 이 그것을 근거 없음으로 다룬다) |

**현재 자산 그대로.** L(문자 4-gram IDF)·D(LSA)·H(RRF) 세 검색기와 비교
결과(E8)가 이미 있다. 여기에 S2 의 **조문 겹침**을 세 번째 축으로 더한다 —
문자 유사도만으로 뽑으면 `240047` 처럼 공유 각주가 순위를 만든다.

### S4. De Facto Rule Candidate

| | |
|---|---|
| **Input** | `precedent_candidates`, dev 라벨 |
| **Output** | `de_facto_rule_candidates[]` — 조건 → 결론 · dev 지지도 · dev 정밀도 |
| **주체** | **결정론**(규칙 유도) |
| **실패 조건** | 지지도가 클래스 문턱 미만 · 규칙끼리 반대 결론 |
| **진행 조건** | 항상 진행 |

**현재 자산 그대로** — E6 유도 규칙 11개. 다만 E6 가 남긴 경고를 설계에
새긴다: **`조치` 규칙의 dev→test 전이가 100%→20% 였다.** 그러므로 de facto
rule 은 **단독 결론 근거로 쓰지 않고 S6 의 대조 축으로만 쓴다.**

### S5. Deciding-Factor Analysis ★ 새 단계

이 단계가 이 설계의 핵심이다. **§3 에서 따로 다룬다.**

### S6. Conflict Check

| | |
|---|---|
| **Input** | `explicit_rules`, `de_facto_rule_candidates`, `precedent_candidates`, `deciding_factors` |
| **Output** | `conflicts[]` — 종류 · 관련 근거 id · 심각도 |
| **주체** | **결정론** |
| **실패 조건** | 없음 (검출만 한다) |
| **진행 조건** | 항상 진행 |

검출하는 충돌 네 가지.

    C1  선례끼리 반대 결론          (현재 opposition guard 가 보는 것)
    C2  규칙끼리 반대 결론          (현재 R1)
    C3  명시 규정과 선례가 어긋남    ← 새로 생긴다. 규정이 우선한다
    C4  결정적 조건이 서로 반대를 가리킴  ← S5 가 생겨야 볼 수 있다
    C5  같은 조건인데 시점에 따라 결론이 다름 ← §3.6 A4. `240023` 이 실례

C3 는 지금 볼 수 없다. S2 가 없기 때문이다. **근거의 위계를 명시한다** —
명시 규정 > 선례 > de facto rule. AG-12 에서 배운 것(약한 근거가 강한 근거를
덮으면 안 된다)을 위계로 못 박는다.

### S7. Decision / Abstention / Human Handoff

| | |
|---|---|
| **Input** | 위 전부 |
| **Output** | 잠정 결론 + 경로 + 발화한 결정 표의 줄 |
| **주체** | **결정론** (결정 표) |
| **실패 조건** | 어느 줄도 발화하지 않음 = 표가 불완전 |
| **진행 조건** | 항상 S8 로 (기권도 검증을 지난다) |

**현재 자산 확장.** Router 결정 표 R1~R10 을 그대로 두고 줄을 더한다. 원칙
셋은 유지한다 — (1) LLM 은 경로를 고르지 않는다, (2) 발화한 줄 번호를
`route_reason` 에 남긴다, (3) 죽은 줄은 지운다(R4 를 그렇게 지웠다).

### S8. Evidence Validation

| | |
|---|---|
| **Input** | 잠정 결론과 그에 붙은 근거 |
| **Output** | `validation[]` — 검사별 통과 여부 · 폐기된 근거 |
| **주체** | **결정론** |
| **실패 조건** | 차단 검사 불통과 → S7 로 되돌아가 기권 |
| **진행 조건** | 차단 검사 전부 통과 |

현재 V1~V6 에 **V7 을 더한다 — 결정적 조건 접지**(§8). V7 은 하나가 아니라
세 갈래(V7-a/b/c)이고, `applicability_basis` 에 따라 다른 것이 걸린다. E11a 에서 확인한
불편한 사실도 함께 남긴다: 현재 배선에서 V1·V2·V3·V5 는 **구성상 참**이라
아무것도 막지 못했다(값어치 0). V7 은 그 자리를 메우기 위한 검사이고,
**만들자마자 값어치를 재서 0 이면 그렇게 적는다.**

### S9. Final Decision

| | |
|---|---|
| **Input** | 검증을 통과한 잠정 결론 |
| **Output** | `decision` 또는 `abstention` 또는 `human_handoff` + 신뢰도 |
| **주체** | **결정론** (최종 안전 게이트) |
| **실패 조건** | 근거 없는 결론 · 신뢰도와 근거 강도 불일치 |
| **진행 조건** | — (종점) |

최종 안전 게이트가 마지막으로 보는 것: 결론이 있으면 근거가 있는가, 근거가
`selected_evidence` 안에 실재하는가, 결정적 조건이 하나 이상 붙어 있는가.

### S10. Execution Trace

| | |
|---|---|
| **Input** | 모든 단계의 입출력 |
| **Output** | `execution_trace[]` — 단계 · 요약 · 결정에 영향을 준 값 |
| **주체** | **결정론** |
| **실패 조건** | 단계가 흔적 없이 지나감 |
| **진행 조건** | — |

**현재 자산 그대로.** 소요 시간처럼 실행마다 달라지는 값은 넣지 않는다 —
넣으면 두 실행의 trace 를 비교할 수 없고 회귀 테스트가 못 쓴다.

### S11. Evaluation / Audit

| | |
|---|---|
| **Input** | 예측 레코드 + trace |
| **Output** | 축별 지표 (§10) |
| **주체** | **결정론** |
| **실패 조건** | 표본 불일치 · 기권을 오답으로 인코딩 |
| **진행 조건** | — |

EV-24 를 여기 못 박는다: 기권은 `predicted: null` 이 아니라 `provisional` +
`abstained` 로 나간다. 그러지 않으면 **기권을 보여주려고 만든 지표가 기권을
벌한다.**

## 3. S5 — Deciding-Factor Analysis (AG-13 이 요구한 단계)

### 무엇이 잘못됐는가

E11b 의 applicability 는 두 요청문을 통째로 주고 "차이가 결론을 바꿀
만한가" 를 물었다. 모델은 **둘을 나란히 읽고 닮은 곳을 찾는** 일을 했고,
`220049` 에서 닮은 문장을 찾아 그것을 근거로 냈다. 질문의 형태가 그 답을
유도했다.

### 무엇으로 바꾸는가

**"닮았는가" 를 묻지 않는다. "조건이 어떻게 갈리는가" 를 묻는다.** 출력은
문장이 아니라 **조건 집합**이고, 그 집합이 원문의 실제 차이를 덮는지는
결정론이 검사한다.

S5 는 반쪽 둘로 되어 있다. **이 경계가 이 단계의 전부다.**

    LLM 부분     조건을 찾아 관계별로 나누고, 무엇이 결정적인지 주장한다
    결정론 부분   그 주장이 원문의 실제 차이를 덮는지 검사하고, basis 를 계산한다

**LLM 은 `applicability_basis` 를 채우지 않는다.** basis 는 결정론이 §3.4 의
규칙으로 산출한다. 모델이 스스로 "내 분석은 완전하다" 고 선언할 수 있으면
AG-13 이 한 층 위에서 반복될 뿐이다.

### 3.1 S5 Output Contract

| 필드 | 채우는 주체 | 허용 값 | **빈 목록의 뜻** |
|---|---|---|---|
| `shared_factors` | LLM | `factor[]` (side=`both`) | 공통 조건이 하나도 없다. **비정상 신호** — 문턱을 넘어 뽑힌 선례인데 공통 조건이 0이면 검색이 틀렸거나 분석이 실패했다. `applies` 금지 |
| `only_in_request` | LLM | `factor[]` (side=`request`) | 요청에만 있는 조건이 없다는 **주장**. 결정론이 `D_A` 와 대조한다 |
| `only_in_precedent` | LLM | `factor[]` (side=`precedent`) | 선례에만 있는 조건이 없다는 **주장**. 결정론이 `D_B` 와 대조한다 |
| `potential_deciding_factors` | LLM | `factor[]` (다른 목록의 `id` 참조) | 결론을 가를 만한 조건이 없다는 주장. Case A 에서는 정상, Case B 에서는 각 차이마다 `why_not_decisive` 를 요구한다 |
| `metadata_differences` | LLM 이 **제안**, 결정론이 **확정** | `segment[]` | 메타데이터 차이 없음. **모델의 분류는 구속력이 없다**(§3.2) |
| `unresolved_differences` | **결정론** | `segment[]` | 판단 못 한 차이가 없다. 비어 있지 않으면 `applies` 금지 |
| `applicability_basis` | **결정론** | 아래 5값 중 하나 | 비어 있을 수 없다 — 항상 계산된다 |

`applicability_basis` 의 허용 값은 정확히 다섯이다.

    identical_after_metadata   메타데이터를 걷어내면 실질 차이가 없다        → applies
    no_decisive_difference     실질 차이는 있으나 전부 결정적이지 않다        → applies
    decisive_difference        결론을 가를 조건이 있다                      → differs
    unresolved_difference      중요성을 판단하지 못한 차이가 남았다          → unclear
    incomplete_analysis        원문의 실질 차이를 분석이 덮지 못했다          → unclear

**`unclear` 두 값을 굳이 나눈 이유:** 같은 기권이라도 원인이 다르다. 앞은
"모델이 판단을 유보했다", 뒤는 "모델이 놓쳤다" 다. 둘을 한 값으로 뭉치면
AG-13 계열의 실패를 수치로 셀 수 없다.

**`factor` 하나의 형태**

    id                    F1, F2, … (문서 안에서 유일)
    text                  **원문 그대로** 옮긴 구절 — 결정론이 글자 단위로 대조
    side                  request | precedent | both
    span                  정규화 좌표 [시작, 끝] — 커버리지 계산의 단위
    axis                  조건의 축 이름 ("내부망 연결 여부")
    value_in_request      그 축에서 요청이 취하는 값 (없으면 null)
    value_in_precedent    그 축에서 선례가 취하는 값 (없으면 null)
    decisive              true | false  — **모델의 주장**이지 사실이 아니다
    why_not_decisive      decisive=false 인 **실질 차이**에는 **필수**. 없으면 unresolved

`why_not_decisive` 를 필수로 둔 것이 Case B 의 구멍을 막는다. 이것이 없으면
모델은 모든 차이에 `decisive: false` 를 붙여 `applies` 로 빠져나갈 수 있다.

### 3.2 메타데이터는 **결정론이 정한다**

`metadata_differences` 를 모델이 자유롭게 채울 수 있으면 Case B 는 Case A 로
무너진다 — 결정적 조건을 "메타데이터" 라고 부르면 그만이기 때문이다.

그래서 메타데이터는 **선언된 패턴 목록**으로만 인정한다.

    날짜 표기            ’24.3.28. · 2024. 3. 28. · 24년 3월
    일련번호             (일련번호 : 240023) · 일련번호 240057
    요청 주체 표기        여신금융협회 요청 · 은행연합회 요청
    문서 상용구           ※ 로 시작하는 출처 표시 · 페이지 머리말
    조판 잔재            글머리 기호 · 제어문자 · 반복 공백

이 목록은 **코드에 있고 회귀 테스트가 붙는다.** 목록에 없으면 메타데이터가
아니다. 모델이 메타데이터라고 제안해도 목록에 안 걸리면 실질 차이로 남는다.

*(현재 자산 재사용: 인용 대조에 쓰는 정규화가 이미 조판 잔재를 걷어낸다.
같은 정규화를 여기서도 쓴다 — 두 곳이 다르면 좌표가 어긋난다.)*

### 3.3 세 가지 경우

**Case A — 실질적 차이 없음**

메타데이터를 걷어내면 차집합이 빈다. `240023` 이 여기다(날짜·일련번호 줄만
다르다).

    only_in_request / only_in_precedent   해당 조각은 metadata_differences 로 분류
    potential_deciding_factors            **비어 있을 수 있다** — 정상이다
    applicability_basis                   identical_after_metadata
    판정                                  applies **허용**

Case A 에서 `applies` 의 근거는 인용이 아니라 **"차이가 없다" 는 결정론적
사실**이다. 그러므로 인용을 요구하지 않는다(§8 에서 다시 다룬다).

**Case B — 실질적 차이 존재**

`220049` 의 *"내부 업무용 시스템과는 연결되지 않음"* 이 여기다.

    반드시 only_in_request 또는 only_in_precedent 에 포함되어야 한다
    potential_deciding_factors 의 후보로 올라가야 한다
    그 차이가 분석에 없으면 → incomplete_analysis → **applies 금지**

분석에 포함됐다면 두 갈래다.

    decisive: true  가 하나라도 있다        → decisive_difference → differs
    전부 decisive: false 이고
      각각 why_not_decisive 가 있다        → no_decisive_difference → applies 허용
      why_not_decisive 가 없는 것이 있다    → 그 조각은 unresolved 로 내려간다

**Case C — 텍스트 차이는 있으나 중요성이 불명확**

    메타데이터로 임의 분류하지 않는다      §3.2 의 목록에 없으면 메타데이터가 아니다
    potential_deciding_factors 에 올리거나 unresolved_differences 로 남긴다
    applicability_basis                   unresolved_difference
    판정                                  **applies 금지** → unclear (기권 유지)

**설계 결정: Case C 에서 `applies` 를 허용하지 않는다.**

이유는 비대칭이다. 회수는 기권을 없애는 방향이고, 틀리면 오답이 나간다.
반면 기권을 유지하면 잃는 것은 커버리지뿐이다. 흔들릴 때 막는 쪽으로 두는
것은 이 저장소가 이미 쓰고 있는 원칙이다(`applies` 가 아닌 값은 무엇이든
기권 유지 — fail-closed).

**대가도 적는다.** 이 선택은 과잉 기권을 늘린다. 지금도 기권 78건 중 답했으면
맞았을 것이 50건이다. Case C 를 기권으로 보내면 그 수가 더 는다. **그러므로
`unresolved_difference` 로 막힌 건수와 그중 정답이 무엇이었는지를 반드시
따로 세어 보고한다** — 세지 않으면 이 선택이 옳았는지 알 수 없다. 이것은
가정이지 측정이 아니다.

### 3.4 Diff Coverage Gate — 결정론적 판정 규칙

**입력**: 요청 원문 `A`, 선례 원문 `B`, S5 의 LLM 출력.
**첫 구현에서 의미 임베딩을 쓰지 않는다.** 아래는 전부 문자 연산이다.

**0단계 — 정규화와 조각 나누기 (결정론)**

    n(x)    다음을 순서대로 지운다. 인용 대조에 쓰는 함수와 **같은 것**을 쓴다
              ① 불가시문자(ZWNJ·ZWSP·BOM)
              ② 글머리 기호 (□ ○ ◦ ▪ ● · • ▶ ◆ ∙)
              ③ 각주 표지 (인라인 * ＊, 원문자 ◯1 ◯2, 위첨자 숫자)
              ④ 모든 공백
            **글자 자체는 바꾸지 않는다** — 뜻이 바뀐 인용은 걸러져야 하므로.

    seg(x)  n 을 적용하기 **전** 텍스트를 절 단위로 자른다
              경계: 문장 종결(다. / 함. / ? / !) · 줄바꿈 · 열거 기호
            각 조각은 (문자열, span) 을 갖는다. span 은 **n(x) 좌표**의 [시작, 끝)

`n` 에 ③ 을 넣은 이유는 실측에서 나왔다. `220049` 와 선례 `220041` 의
공통 문장이 한쪽은 `클라우드컴퓨팅시스템\n*에`, 다른 쪽은
`클라우드컴퓨팅시스템에` 다. 각주 표지를 안 지우면 **공통 문장이 차이로
잡히고**, 차집합이 부풀어 헛되이 `incomplete_analysis` 가 난다.

**조각 동일성** — 차집합을 계산하려면 "같은 조각" 을 정의해야 한다.

    same(p, q)  ⇔  n(p) = n(q)                          정확 일치
                ∨  jaccard₄(n(p), n(q)) ≥ τ             문자 4-gram 자카드

`τ` 는 **아직 정하지 않는다.** dev 에서 사람이 "같은 조각" 이라고 볼 쌍의
분포를 보고 보정한다 — `DOUBT`/`TRUST` 를 dev leave-one-out 에서 뽑았던
것과 같은 절차다. **τ 를 정하기 전에는 이 게이트를 켜지 않는다.** 문자
4-gram 은 이 저장소가 이미 쓰는 표현이므로 새 기술이 아니다.

**1단계 — 차집합 계산 (결정론)**

    D_A = { p ∈ seg(A) | ¬∃ q ∈ seg(B) : same(p, q) }    요청에만 있는 조각
    D_B = { q ∈ seg(B) | ¬∃ p ∈ seg(A) : same(p, q) }    선례에만 있는 조각

**2단계 — 메타데이터 제거 (결정론)**

    M = { d ∈ D_A ∪ D_B  |  d 가 §3.2 의 선언된 패턴에 걸린다 }
    S = (D_A ∪ D_B) \ M                                    ← **실질 차이**

**3단계 — 커버리지 계산 (결정론) · `covers` 의 정확한 정의**

먼저 factor 의 span 을 **결정론이 확정한다.** 모델이 준 오프셋을 믿지 않는다.

    locate(f)   n(f.text) 를 f.side 문서의 n() 안에서 찾는다
                  0회   → f 는 접지 실패. **폐기**하고 아무것도 덮지 못한다 (V3)
                  1회   → 그 구간이 f.span
                  2회+  → 후보 전부를 들고 간다. trace 에 span_ambiguous 를 남기고
                          아래 계산에서 **s 와 겹침이 가장 큰 것**을 쓴다

세 조건이 **전부** 만족해야 덮은 것이다.

    covers(f, s)  ⇔  side_ok(f, s)  ∧  inside(f,s) ≥ ⌈|n(s)| / 2⌉
                                    ∧  outside(f,s) ≤ inside(f,s)

    side_ok(f, s)      s ∈ D_A  →  f.side = request
                       s ∈ D_B  →  f.side = precedent
                       **f.side = both 인 factor 는 어떤 s 도 덮지 못한다.**
                       s 는 정의상 한쪽에만 있는 조각이기 때문이다.

    inside(f, s)       |f.span ∩ s.span|      겹치는 글자 수
    outside(f, s)      |f.span| − inside      조각 **밖**에서 끌어온 글자 수

세 조건이 각각 무엇을 막는지 적어 둔다.

| 조건 | 막는 것 | 실측 근거 |
|---|---|---|
| `side_ok` | 요청 쪽 조건으로 선례 쪽 차이를 덮었다고 우기는 것 | — |
| `inside ≥ 절반` | 두세 글자만 걸치고 "덮었다" 고 하는 것 | — |
| `outside ≤ inside` | **요청문 전체를 통째로 인용해 모든 조각을 덮는 것** | `250055` 에서 모델이 인용을 요청문 거의 전체로 냈다(88자/89자) |

한 조각을 여러 factor 가 나눠 덮을 수 있다. 그래서 절반 조건은 **합집합**으로,
과다 인용 조건은 **factor 마다** 본다.

    covered(s) ⇔ | ⋃_{f: side_ok(f,s)} (f.span ∩ s.span) | ≥ ⌈|n(s)| / 2⌉
                 ∧ ∀f 그 합집합에 기여한 것: outside(f,s) ≤ inside(f,s)

    C = { s ∈ S | covered(s) }                             ← 덮인 실질 차이
    U = S \ C                                              ← **미커버 실질 차이**

**이 계약에서 데이터로 정하지 않은 값은 `1/2` 하나다.** 「절반 이상」은 자연스러운
다수 기준이지 실측에서 나온 값이 아니다. `MAX_YEAR_GAP` 을 다룬 것과 같이
**그 사실을 여기 적어 두고**, 켜고 난 뒤 `U` 의 분포를 보고 재검토한다.

**4단계 — 미해결 판정 (결정론)**

    R = { s ∈ C  |  s 를 덮은 f 가 decisive=false 인데 why_not_decisive 가 없다 }
    unresolved_differences = U ∪ R

**5단계 — basis 산출 (결정론, 위에서부터 먼저 맞는 줄이 이긴다)**

    G1  shared_factors = ∅                     →  incomplete_analysis      (applies 금지)
    G2  U ≠ ∅                                  →  incomplete_analysis      (applies 금지)
    G3  R ≠ ∅                                  →  unresolved_difference    (applies 금지)
    G4  ∃ f : decisive_confirmed(f)  (§3.5)    →  decisive_difference      (differs)
    G5  S = ∅  ∧  §3.6 의 A1~A4 통과           →  identical_after_metadata (applies)
    G6  그 외 (S ≠ ∅, 전부 커버·전부 설명됨)    →  no_decisive_difference   (applies)

**G4 는 모델의 주장이 아니라 §3.5 의 확정 절차를 통과한 것에만 발화한다.**
**G5 는 `S = ∅` 만으로 발화하지 않는다** — §3.6 의 선례 적격성을 함께 본다.

**한 줄로 적으면 지시하신 그대로다.**

> **텍스트 차집합에 존재하는 비-metadata 차이가 S5 의 분석 결과에 하나도
> 대응되지 않으면 `applies` 를 금지한다** (G2). 대응은 됐으나 "왜 결정적이지
> 않은가" 가 없으면 그 역시 금지한다 (G3).

발화한 줄 번호(`G1`~`G6`)를 `execution_trace` 에 남긴다 — Router 의
`route_reason` 과 같은 규율이다.

**게이트가 하지 않는 일도 적어 둔다.** 이 게이트는 **누락**을 잡지
**오분류**를 잡지 못한다. 모델이 `only_in_request` 에 올려 놓고
`decisive: false` + 그럴듯한 `why_not_decisive` 를 붙이면 G3·G4 를 지나
`no_decisive_difference` 로 통과한다. §14 에 한계로 적었다.

### 3.5 `decisive = true` 확정 계약

모델은 `decisive` 를 **주장**할 뿐이다. 확정은 결정론이 한다. 여섯 조건 중
**D1~D5 가 전부** 만족돼야 `decisive_confirmed` 다.

    D1  실제 차이에 대응한다     ∃ s ∈ S : covers(f, s)
                                 대응이 없으면 **원문에 없는 차이를 지어낸 것**이다.
                                 이 경우 decisive 를 기각하고 trace 에
                                 phantom_factor 로 남긴다.

    D2  한쪽에서 나왔다          f.side ∈ { request, precedent }
                                 `both` 는 정의상 decisive 가 될 수 없다.
                                 **AG-13 이 정확히 이 자리다.**

    D3  원문에 접지된다          locate(f) 가 1회 이상 (V3 와 같은 검사)

    D4  축이 있다                f.axis 가 비어 있지 않다
                                 축 이름이 없으면 "무엇이 갈렸는지" 를 말한 것이
                                 아니라 문장을 하나 고른 것이다.

    D5  축의 양쪽이 확인된다      value_in_request 와 value_in_precedent 가 모두
                                 채워져 있다. **한쪽이 "없음" 인 것도 값이다** —
                                 `220049` 가 바로 그 모양이다(선례에는 DMZ 연동
                                 질의가 있고 요청에는 없다).

    D6  applicability 연결       이 차이가 왜 결론을 가르는가의 **뒷받침**을 찾는다
                                 (a) 명시 규정의 요건에 걸린다        → support = explicit_rule
                                 (b) de facto rule 의 조건에 걸린다   → support = de_facto_rule
                                 (c) 둘 다 아니다                     → support = unsupported

**D6 은 확정 조건이 아니라 `support` 라벨이다.** 그 이유를 적어 둔다.

지금 S2 는 조문 **원문**이 아니라 인용 색인이므로(§1 안 A) (a) 가 자주
비어 있을 것이다. D6 을 필수로 걸면 대부분의 `differs` 가 막히고, 그것은
**기권을 늘리는 방향**이다. 그래서 비대칭으로 둔다.

    differs 를 낼 때    support = unsupported 여도 통과한다
                        선례를 버리는 방향이므로 근거 요구를 낮춰도 안전하다
    applies 를 낼 때    support 와 무관하게 §3.6 을 통과해야 한다
                        답하는 방향이므로 요구를 낮추지 않는다

`support` 분포는 **세어서 보고한다.** `unsupported` 비율이 높으면 그것은
"S2 를 인용 색인으로 둔 선택(§1 안 A)이 부족하다" 는 신호이고, 안 B(법령
원문 수집)로 갈 근거가 된다. 세지 않으면 그 판단을 할 수 없다.

### 3.6 `S = ∅` 의 전제 — "차이가 없다" 와 "이 선례가 적절하다" 는 다르다

`S = ∅` 은 **두 글이 메타데이터를 빼면 같다**는 텍스트 사실이다. 그것은
**이 선례를 따라도 된다**는 뜻이 아니다. 둘을 섞으면 검색이 잘못 물어온
문서를 "차이가 없으니 적용된다" 로 승인하게 된다.

그래서 두 층으로 나눈다.

    applicability_basis        텍스트 사실. S = ∅ 이면 identical_after_metadata
    precedent_admissibility    선례가 근거로 쓸 만한가. **별개의 검사**

`identical_after_metadata` 로 `applies` 를 내려면 **넷이 전부** 필요하다.

    A1  S = ∅                       결정론이 재계산한다. 모델의 말이 아니다
    A2  shared_factors ≠ ∅          공통 조건이 실제로 있다 (G1 과 같은 검사)
    A3  선례가 문턱 위               precedent.score ≥ DOUBT — 기존 자산 그대로
    A4  라벨 일관성                  같은 조건에서 `S = ∅` 인 다른 선례가
                                     **반대 라벨을 갖지 않는다**

**A2 를 굳이 넣은 이유:** `S = ∅` 인데 `shared_factors` 가 비어 있으면 분석이
아무것도 하지 않은 것이다. 텍스트가 같다는 사실만으로 통과시키면 S5 를
건너뛴 것과 같다.

**A4 는 실측에서 나왔다.** `240023` 의 근거 구성을 보면 이렇다.

    240057 (2024)  요청과 날짜·일련번호만 다른 같은 글   라벨 비조치
    230094 (2023)  같은 글                              라벨 **기타**
    230027 (2023)  같은 글                              라벨 **기타**

**같은 요청이 해가 바뀌며 다른 결론을 받았다.** 이것은 "적용되는가" 의 문제가
아니라 **기준이 바뀌었다**는 문제다. A4 가 없으면 `S = ∅` 하나로
`applies → 비조치` 가 나가고, 규제 기준이 바뀌었다는 사실이 조용히 지워진다.

A4 가 걸리면 `applies` 를 내지 않고 **S6 의 새 충돌 종류로 보낸다.**

    C5  temporal_conflict   같은 조건인데 시점에 따라 결론이 다르다

C5 의 처리는 기존 자산을 쓴다 — Router 의 최신성 규칙(R7·`MAX_YEAR_GAP`)이
**요청 시점에 가장 가까운 선례**를 앞세우고, `confidence` 를 낮추며,
`temporal_conflict` 를 trace 에 남긴다. 동률이면 `HUMAN_REVIEW` 다.
근거가 강한데 서로 반대인 경우이므로 §7 의 이관 조건에 정확히 맞는다.

**여기서 드러난 별개의 문제도 적어 둔다 — 미래 선례 누출.**
`240023` 의 1등 선례 `240057` 은 요청보다 **나중**(’24.3.28 요청 / ’24.6.27
선례)이다. dev/test 를 시점이 아니라 무작위로 나눴기 때문이고, 실제 업무에서는
접수 시점에 존재하지 않는 선례다. **최종 Workflow 의 S3 는 요청 시점 이후의
선례를 걸러야 한다.** 지금까지의 E1~E11b 수치는 그 필터 없이 잰 것이므로,
필터를 켜면 달라질 수 있다. **얼마나 달라지는지는 재보지 않았다** — 세어
보기 전에는 수치를 쓰지 않는다.

### 3.7 240023 과 220049 에 적용하면

**`240023` — Case A, 그러나 그것만으로 끝나지 않는다**

    D_A  ※ ’24.3.28. 여신금융협회 요청(일련번호 : 240023)
    D_B  ※ ’24.6.27. 여신금융협회 요청(일련번호 : 240057)
    M    둘 다 [날짜 표기 + 일련번호 + 요청 주체 표기 + ※ 상용구] 에 걸린다
    S    ∅
    U    ∅ · R ∅ · shared_factors 다수 · decisive_confirmed 없음

    §3.6 의 전제를 본다
      A1  S = ∅                                          ✓
      A2  shared_factors ≠ ∅                             ✓
      A3  선례 유사도 0.918 ≥ DOUBT                       ✓
      A4  같은 조건에서 S = ∅ 인 다른 선례의 라벨          ✗
            240057 (2024) 비조치  ·  230094 (2023) 기타  ·  230027 (2023) 기타

    →  A4 불통과. **G5 로 가지 않는다.**
    →  S6 의 C5 temporal_conflict 발화
    →  최신성 규칙이 요청 시점에 가장 가까운 선례를 앞세운다
    →  confidence 를 낮추고 temporal_conflict 를 trace 에 남긴다

**이 건에 대한 설계의 답이 앞 절과 달라졌다는 것을 그대로 적어 둔다.**
§3.4 만 있을 때는 "G5 통과 → applies" 였다. §3.6 의 A4 를 세우고 나니
그 답이 틀렸다 — **같은 요청이 2023년에는 `기타`, 2024년에는 `비조치` 를
받았기 때문이다.** 이것을 `applies` 하나로 뭉개면 "규제 기준이 바뀌었다" 는
사실이 지워진다.

지금의 opposition guard 는 이 건을 반대 근거 2건으로 **뭉뚱그려 막았고**
정답 하나를 잃었다. 이 설계에서도 막히기는 하지만 **막힌 이유가 다르고,
그 이유가 기록된다** — `C5 temporal_conflict`. 그리고 최신성 규칙이 있으므로
답에 도달할 길이 남아 있다. 그 길이 실제로 정답에 닿는지는 **재봐야 안다.**

**`220049` — Case B**

    D_A  "* 금융회사의 내부 업무용 시스템과는 연결되지 않음"
         "* 임직원의 고유식별정보 또는 개인신용정보 일부가 포함"
    D_B  "금융회사가 내부 임직원의 인사정보가 저장된 내부 업무용시스템을
          DMZ 영역의 중계서버(프록시)를 통해 클라우드컴퓨팅시스템에 연동할 경우…"
         "* 임직원의 주민등록번호, 연봉, 근태, 인사평가 등"
    M    ∅  (§3.2 의 어느 패턴에도 안 걸린다)
    S    위 네 조각

    분석이 이것을 덮었다면
      only_in_request     F3 "내부 업무용 시스템과는 연결되지 않음"
                             axis=내부망 연결 여부 · decisive=true
      only_in_precedent   F4 DMZ 중계서버 연동 질의
                             axis=내부망 연결 여부 · decisive=true
      →  G4  decisive_difference  →  **differs**
      →  근거는 F3 (side=request) — §8 의 V7-a E1~E6 통과

    분석이 이것을 놓쳤다면 (= E11b 가 실제로 한 일)
      F 가 shared 조각만 담고 있다  →  U = S ≠ ∅
      →  G2  incomplete_analysis  →  **applies 금지** → unclear

**두 번째 갈래가 요점이다.** 모델이 E11b 와 똑같이 실패해도 결과가
"틀린 `applies`" 가 아니라 **"분석 미완 → 기권"** 이 된다. 손실이지만
오답보다 싸고, 무엇보다 `incomplete_analysis` 로 **세어진다.**

### 3.8 이 단계의 계약

| | |
|---|---|
| **Input** | `structured_request`, 선례 후보 1건의 구조화된 요청, 양쪽 원문, (S2 의 조문) |
| **Output** | §3.1 의 7필드 |
| **주체** | **LLM**(조건 후보·decisive 주장) + **결정론**(차집합·메타데이터 분류·커버리지·basis) |
| **실패 조건** | 스키마 위반 · `factor.text` 가 원문에 없음 · G1·G2·G3 발화 |
| **진행 조건** | basis 가 산출됨 (항상). `applies` 로 진행하려면 basis ∈ {identical_after_metadata, no_decisive_difference} |

**선례의 결론은 프롬프트에 넣지 않는다.** E11b 의 이 설계는 옳았고 그대로
가져간다 — 넣으면 결론에서 거꾸로 판단하는 순환이 생긴다.

## 4. 상태 머신

```
request
  └─ S1 ─► structured_request        스키마 통과 시에만 채워진다
       ├─ S2 ─► explicit_rules       0건 허용
       ├─ S3 ─► precedent_candidates 0건 허용
       └─ S4 ─► de_facto_rule_candidates
            └─ S5 ─► deciding_factors      게이트 통과 시에만
                     applicability_basis    결정론이 G1~G6 로 산출 (LLM 아님)
                     unresolved_differences 게이트가 남긴 미해결 조각
                 └─ S6 ─► conflicts
                      └─ S7 ─► selected_evidence + 경로
                           └─ S8 ─► validation
                                └─ S9 ─► decision | abstention | human_handoff
                                     └─ S10 execution_trace (전 구간 누적)
```

| 상태 | 채워지는 조건 | 비워지는(무효화되는) 조건 |
|---|---|---|
| `request` | 접수 시 | — |
| `structured_request` | S1 스키마 통과 | 누출 마스킹 실패 시 전체 중단 |
| `explicit_rules` | 조문 정규화 성공 | — |
| `precedent_candidates` | 유사도 ≥ `DOUBT` | S8 에서 폐기된 근거는 제외 |
| `de_facto_rule_candidates` | 클래스별 지지도 문턱 통과 | 규칙 충돌 시 사용 불가 표시 |
| `deciding_factors` | S5 의 LLM 부분이 채운다 | `text` 가 원문에 없는 항목은 개별 폐기 |
| `metadata_differences` | 결정론이 §3.2 선언 목록으로 확정 | 목록에 없으면 실질 차이로 되돌린다 |
| `unresolved_differences` | 게이트 4단계 (`U ∪ R`) | 비어야 `applies` 가능 |
| `applicability_basis` | **항상** 산출된다 (G1~G6) | 비워 둘 수 없다 |
| `precedent_admissibility` | S3 직후 · §3.6 의 A3·A4 | `applies` 는 `admissible` 일 때만 |
| `conflicts` | S6 항상 | — |
| `selected_evidence` | S7 이 고른 것 | S8 폐기분 제외 |
| `validation` | S8 항상 | — |
| `decision` | S9 안전 게이트 통과 | 기권/이관 시 **비어 있어야 한다** |
| `abstention` | 결정 표의 기권 줄 발화 | 회수 시 사유와 함께 해제 |
| `human_handoff` | §8 의 이관 조건 | — |
| `execution_trace` | 매 단계 append | 절대 지우지 않는다 |

두 가지를 상태 규칙으로 못 박는다.

- **기권 시 `decision` 은 비어 있고 `provisional` 만 채워진다** (EV-24).
- **회수는 회수만 한다** — 이 워크플로의 어떤 후단계도 새로 기권시키지
  않는다. 그래야 "나빠질 수 없다" 가 구조적으로 보장된다.

## 7. Decision Type — 실제로 필요한 것만

데이터가 지지하는 것과 업무가 요구하는 것을 나눠서 고른다.

| 상태 | 뜻 | 데이터가 지지하는가 |
|---|---|---|
| `NO_ACTION` (비조치) | 요청 행위에 조치를 취하지 않는다 | ✅ 체크박스 라벨 |
| `ACTION` (조치) | 조치 대상이다 | ✅ 라벨 (test 14건뿐) |
| `OTHER` (기타) | 소관 아님·이미 허용·요건 미비 등 | ✅ 라벨 (혼합 범주) |
| `REQUEST_MORE_INFORMATION` | 요청서에 판단에 필요한 조건이 없다 | ❌ **정답이 없다** |
| `ABSTAIN` | 근거가 없거나 충돌한다 | ⚠ 대리 평가만 가능 |
| `HUMAN_REVIEW` | 사람에게 넘긴다 | ⚠ 대리 평가만 가능 |

**`APPROVE`/`REJECT` 를 쓰지 않는다.** `기타` 를 반려로 번역하는 순간 라벨에
없는 뜻이 생긴다. 원 라벨 이름을 유지한다.

**`REQUEST_MORE_INFORMATION` 은 설계에는 넣되 성능 주장에는 쓰지 않는다.**
이 데이터에는 "정보가 부족해 되물었다" 는 정답이 없다. 발화 조건만 결정론적
으로 정의하고(요청에 `decisive` 후보가 0개이면서 선례가 문턱 위), **발화
횟수와 그때의 정답 분포만 보고한다.** 정확도라고 부르지 않는다.

`ABSTAIN` 과 `HUMAN_REVIEW` 의 구분도 결정론으로 둔다.

    ABSTAIN        근거가 없거나 약하다 — 사람이 봐도 자료가 더 필요하다
    HUMAN_REVIEW   근거는 강한데 서로 반대다 (C1·C3·C4) — 사람이 판단할 자료는 있다

## 8. Evidence Contract — "인용은 맞지만 결정적이지 않다" 를 표현한다

AG-13 의 직접적 처방이다. 근거 하나의 계약을 이렇게 둔다.

| 필드 | 뜻 | 검사 주체 |
|---|---|---|
| `text` | 원문에서 그대로 딴 구절 | 결정론 (글자 대조) |
| `source` | 문서·일련번호·조문 | 결정론 |
| `kind` | `explicit_rule` / `precedent` / `de_facto_rule` | 결정론 |
| `role` | `supporting` / `contradicting` / `contextual` | LLM 후보 → 결정론 확정 |
| `factor_id` | 이 근거가 붙은 S5 의 조건 id | 결정론 (S5 출력과 대조) |
| `factor_side` | `request` / `precedent` / `both` | S5 에서 옴 |
| `decisive` | 이 근거가 결론을 뒤집을 수 있는가 | **결정론 (아래 규칙)** |
| `relevance` | 요청 조건과의 겹침 정도 | 결정론 |

**핵심 규칙 — `side = both` 인 조건에 붙은 근거는 `decisive` 가 될 수 없다.**

두 요청에 똑같이 있는 문장은 둘을 가르지 못한다. 정의상 그렇다. 그러므로
`factor_side == both` 인 근거에 `decisive: true` 를 붙일 수 없다.

### V7 — 결정적 조건 접지 검사

`applies` 와 `differs` 는 요구하는 것이 다르다. 하나로 쓰면 Case A 에서
모순이 난다(차이가 없는데 결정적 근거를 내놓으라는 요구가 된다).

    V7-a  basis = decisive_difference (differs)   — 여섯 조건 전부

      E1  결론에 붙은 근거 중 decisive_confirmed 인 것이 **1개 이상**
            §3.5 의 D1~D5 를 통과한 것만 센다. 모델의 decisive 주장이 아니다.
      E2  그 근거의 factor_id 가 **실재하는 factor** 를 가리킨다
            S5 출력에 없는 id 를 가리키면 폐기 (AG-11 계열 — 배선 안 된 참조)
      E3  그 factor 의 side ∈ { request, precedent }
            `both` 는 불통과. **AG-13 이 이 줄에서 잡힌다.**
      E4  근거의 text 가 그 side 원문에 **글자 그대로** 있다   (기존 V3)
            n() 정규화 후 대조. locate 가 0회면 폐기.
      E5  ∃ s ∈ S : covers(factor, s)                        (§3.4 의 covers)
            실제 차집합에 대응하지 않는 근거는 지어낸 차이다.
      E6  **집합 수준 검사** — 결론에 붙은 근거 전체가 `both` 이면 불통과
            { e ∈ selected_evidence | e.factor_side ≠ both } ≠ ∅
            E3 이 근거 하나를 보는 반면 E6 은 근거 **목록**을 본다.
            둘 다 두는 이유: E3 만 있으면 `both` 근거 열 개에 한쪽 근거
            하나를 끼워 넣고 통과할 수 있다. E6 은 그것도 통과시키지만,
            **`both` 만으로 이루어진 목록**은 확실히 막는다.

    V7-b  basis = no_decisive_difference (applies · Case B)
            → 실질 차이 조각 하나하나에 why_not_decisive 가 붙어 있다
            → 그 설명이 가리키는 factor 가 실재한다

    V7-c  basis = identical_after_metadata (applies · Case A)
            → 인용을 요구하지 않는다
            → 대신 **S = ∅ 임을 결정론이 재계산해 확인한다**
              (모델의 말이 아니라 차집합이 근거다)

세 갈래 중 해당하는 것이 만족돼야 결론이 나간다. 어긋나면 S7 로 되돌아가
기권한다.

**"인용은 맞지만 결정적이지 않다" 가 이렇게 표현된다** — `220049` 에서
E11b 가 낸 인용은 `factor_side = both` 이므로 `decisive` 가 될 수 없고,
따라서 **V3 통과 · V7-a 불통과**다. 지금은 이 상태를 나타낼 자리가 없어서
그 실패가 지표에 잡히지 않았다.

## 9. 평가 설계

기존 지표를 버리지 않는다. 축을 나눈다 — n 개의 사건을 하나의 정확도로
뭉치면 무엇이 일어났는지 사라진다는 것을 E11b 에서 확인했다.

| 축 | 지표 | 상태 |
|---|---|---|
| **Retrieval** | Recall@k · nDCG@k · 조문 겹침 재현율 | 새로 필요 |
| | TRAP 구간 비율 | **기존 (§10 고유 지표)** |
| **Applicability** | 판정 정확성 (applies/differs/unclear) | 기존 (E11b, n=5) |
| | **Diff Coverage Rate** ★ | **새로 필요** |
| **Decision** | 매크로 F1 · 커버리지 · AURC | **기존** |
| | TRAP 구간 정확도 | **기존** |
| **Evidence** | 인용 접지율 (V3) | **기존** |
| | **Deciding-Factor Grounding Rate** ★ | **새로 필요** |
| **Safety** | 근거 없는 결론 건수 | 기존 (최종 게이트) |
| | 과신 — 신뢰도 대비 실제 정확도 | 기존 |
| | **부적절한 회수** — 회수 후 오답 | 기존 (E11b) |
| | 기권 정확성 — 기권한 건 중 답했으면 틀렸을 비율 | **기존** (지금 36%) |
| **Workflow** | 완주율 · 경로 분포 · `route_reason` 커버리지 | 기존 |
| | 이관 적정성 | 대리 지표만 |

### 새로 필요한 지표 둘, 그리고 왜 필요한가

**★ Diff Coverage Rate** — `|C| / |S|`. 즉 실질 차이 조각 `S` 중 S5 의
조건이 덮은 것 `C` 의 비율 (§3.4 의 기호 그대로).

*왜 필요한가:* 이것이 없으면 AG-13 을 **수치로 감시할 수 없다.** E11b 에서
그 실패를 발견한 것은 제가 `220049` 한 건에 대해 결정 구절을 미리 지정해
뒀기 때문이고, 그런 수작업은 확장되지 않는다. 차집합은 결정론적으로 계산
되므로 모든 건에서 자동으로 잰다.

**★ Deciding-Factor Grounding Rate** — `differs` 결론에 붙은 근거 중
`factor_side ≠ both` 인 것의 비율 (V7-a 통과율).

*왜 필요한가:* 기존 인용 접지율(V3)은 `220049` 에서 **100% 통과했다.**
인용은 전부 원문에 있었기 때문이다. 즉 기존 지표는 AG-13 을 보지 못한다.
"원문에 있는가" 와 "가를 수 있는가" 는 다른 질문이고, 다른 지표가 필요하다.

### 평가 규율 (기존 유지)

- Wilson 신뢰구간 · 짝지은 부트스트랩 · Holm 보정. `조치` 14건 위의 수치는
  구간을 반드시 함께 적는다.
- 기권은 `provisional` + `abstained` 로 내보낸다 (EV-24).
- 표본이 다르면 나란히 놓지 않는다 (`mismatched-sample` 패턴 가드).
- **실행하지 않은 수치는 쓰지 않는다.**

### 게이트 자체를 감시하는 수치

게이트를 만들면 **게이트가 얼마나 막았는지**를 세야 한다. 안 세면 과잉
기권이 조용히 늘어난다.

    basis 분포          G1~G6 중 무엇이 몇 번 발화했는가
    incomplete_analysis 로 막힌 건수 · 그중 정답이 top-1 라벨과 같았던 비율
    unresolved_difference 로 막힌 건수 · 같은 비율
    support 분포          explicit_rule / de_facto_rule / **unsupported**
                          unsupported 비율이 높으면 S2 를 인용 색인으로 둔
                          선택(§1 안 A)이 부족하다는 신호다
    temporal_conflict     C5 가 발화한 건수

뒤의 두 줄이 **Case C 를 기권으로 보낸 설계 결정의 대가**다(§3.3). 그 비율이
높으면 이 선택은 회수 가능한 건을 버리고 있는 것이다 — H1 에 걸었던 것과
같은 형태의 반증 조건을 미리 걸어 둔다.

## 10. 220049 End-to-End — 현재와 목표

**현재 (실측, `experiments/results/e11b_5cases.json`)**

```
유사도 0.738  →  선례 220041 검색 (라벨 기타)
              →  LLM 에게 요청문 둘을 통째로 제시
              →  겹치는 문장을 quote_a·quote_b 로 인용
              →  applies
              →  opposition guard 발화 (반대 근거 230024)
              →  기권
```

오답은 면했지만 **가드가 우연히 막았다.** 판단 자체는 틀렸고, 같은 상황에서
반대 근거가 없었다면 오답이 나갔을 것이다.

**설계 목표 (구현하지 않았다)**

```
유사도 0.738  →  선례 후보 검색 (+ 조문 겹침으로 재순위)
              →  S1 이 양쪽을 조건 단위로 구조화
              →  S5 가 조건을 관계별로 분해
                   shared_factors     SaaS 인사정보 처리 · 제14조의2 · 제15조
                   only_in_request    "내부 업무용 시스템과는 연결되지 않음"
                   only_in_precedent  DMZ 중계서버 연동 질의
              →  결정론 게이트: M = ∅ · S = 네 조각 · U = ∅ · R = ∅
              →  G4 발화 (decisive=true 존재) → basis = decisive_difference
              →  differs
              →  근거 = F3 (factor_side = request ≠ both) → V7-a 통과
              →  선례를 버리고 다른 근거로 진행 · **불필요한 기권 없이**
```

**이것은 목표이고 아직 재보지 않았다.** S5 도 LLM 을 쓰므로 같은 방식으로
실패할 수 있다. 다른 점은 실패했을 때 **결정론이 그것을 안다**는 것뿐이다 —
차집합은 코드가 계산하므로, 조건 목록이 그것을 덮지 못하면 게이트가 잡는다.
그 경우 결과는 "틀린 `applies`" 가 아니라 "분석 미완 → 기권" 이다.

**AG-13 은 이 설계가 구현되고 재보기 전까지 열린 채로 둔다.**

## 11. 데이터 범위

**새 대규모 코퍼스를 만들지 않는다.** 기존 것으로 되는 것과 안 되는 것을
나눈다.

| 필요 | 기존으로 되는가 |
|---|---|
| 요청문 · 라벨 | ✅ 259건 · dev 85 / test 170 |
| 선례 풀 | ✅ dev 85 |
| de facto rule | ✅ E6 11개 |
| 조건 대조용 쌍 | ✅ 사정거리 22건 + TRAP 15건 |
| **명시 규정 원문** | ❌ **없다** |
| **S5 정답(조건 라벨)** | ❌ **없다** |

### 새 데이터 ① — 법령 조문 원문

- **왜 필요한가:** S2·C3(규정과 선례가 어긋나는 경우)가 성립하지 않는다.
  지금은 근거 위계의 맨 위 칸이 비어 있다.
- **왜 기존으로 안 되는가:** 조문 인용은 `판단이유` 안에 있고 그것은 **답변
  쪽**이다. 판단 대상 사건의 것을 쓰면 순환이다.
- **몇 건인가:** 사례가 인용한 조문의 합집합. 218/259 사례가 조문을
  언급하므로 **수십 개 조문 수준**이고, 사례 수보다 훨씬 적다.
- **대안(먼저 시도):** dev 선례의 인용만으로 **인용 색인**을 만든다(§1 안 A).
  비용 0 이고 순환도 없다. 이것으로 부족한 것이 확인된 뒤에 원문을 가져온다.

### 새 데이터 ② — S5 조건 라벨

- **왜 필요한가:** Diff Coverage Rate 는 자동 계산되지만, "이 조건이 정말
  결정적이었는가" 는 정답이 있어야 잰다.
- **몇 건인가:** **TRAP 구간 15건 + 사정거리 22건에서 중복을 뺀 규모.**
  전수가 아니라 이 두 구간만 — 나머지 구간에서는 조건 대조가 결론을 바꾸지
  않는다.
- **어떻게 만드나:** `판단이유` 에 결론 근거가 서술돼 있다. **dev 에서만**
  그것을 조건으로 정리하면 순환 없이 정답을 만들 수 있다. test 에는 손대지
  않는다.
- **먼저 확인할 것:** 이 라벨링에 들어가는 사람 시간이 얻는 것보다 큰지.
  30~40건 규모이므로 감당 가능하다고 본다.

## 12. 기술 스택 — 문제에서 출발한다

공고에 있다는 이유로 넣지 않는다. 각각 문제 → 대안 → 선택 → 이유 →
예상 효과로 적는다.

### 조문·선례 검색

- **문제:** 지금은 문자 4-gram 하나로 뽑는다. `240047` 에서 공유 각주가
  순위를 만들었다. 조문·구조를 축으로 쓸 수 없다.
- **대안:** (a) 현행 유지 (b) 조문 필드를 붙인 색인 (c) Elasticsearch
- **선택:** **(b) → 필요하면 (c)**
- **이유:** 필요한 것은 "본문 유사도 + 조문 일치 + 필터" 의 결합이다. 코퍼스
  259건에 ES 를 세우는 것은 운영 부담이 이득보다 크다. 다만 **BM25·필드
  부스팅·필터 결합은 ES 가 표준적으로 잘하는 일**이므로, 조문 축이 실제로
  효과가 있다고 확인되면 그때 옮긴다.
- **예상 효과:** `240047` 유형(공유 상용구로 뜬 선례)의 순위 하락. 재보기
  전에는 수치를 적지 않는다.

### 임베딩 / Reranker

- **문제:** 문자 n-gram 은 표현이 다른 같은 뜻을 못 본다.
- **대안:** (a) 현행 L (b) LSA 기반 D — **이미 있다** (c) 사전학습 임베딩
  (d) cross-encoder reranker
- **선택:** **(a)+(b) 유지, (c)(d) 보류**
- **이유:** E8 에서 이미 쟀다 — D 는 `조치` 선례를 6배 더 찾지만 **그중 절반이
  함정**이었다. 즉 검색을 바꿔서 풀 문제가 아니라는 증거가 이미 있다. AG-13 은
  검색이 아니라 **근거 선택**의 실패다. (d) 는 S5 가 붙은 뒤 순위 문제가 남으면
  그때 본다.
- **예상 효과:** 지금 넣으면 효과 없음 — 그래서 안 넣는다.

### LangGraph

- **문제:** 단계가 4개에서 11개로 늘어난다.
- **대안:** (a) 현행 순차 호출 (b) LangGraph
- **선택:** **(a) 유지**
- **이유:** 여전히 분기 있는 무순환 DAG 이고 사람 개입 루프가 없다. 필요한
  것은 결정론적 재현이고 `AgentState` 하나로 입력·중간값·결과·경로가 남는다.
  **다만 `HUMAN_REVIEW` 가 실제로 사람이 개입해 재개하는 흐름이 되면 상태
  직렬화·중단/재개가 필요해지고, 그때가 LangGraph 를 도입할 자리다.**
- **예상 효과:** 지금은 계층만 늘어남.

### PostgreSQL / Docker

- **문제:** 지금은 JSONL 파일과 로컬 실행이다.
- **선택:** **보류.** 데이터가 259건이고 산출물은 파일로 재현된다. 여러
  사용자가 동시에 요청을 넣고 이력을 조회하는 서비스가 되면 그때 필요하다.

## 13. 마지막 질문 여섯

### Q1. 단순 RAG 와 무엇이 다른가

단순 RAG 는 **찾은 것을 근거로 쓴다.** 이 설계는 **찾은 것을 믿어도 되는지
먼저 판단하고, 못 믿으면 답하지 않는다.**

수치로 말하면 이렇다. 최근접 선례를 그대로 따르는 전략(=RAG 의 본질)은
순응 구간에서 정확도 1.000, **함정 구간에서 0.000** 이었다. 함정 구간이
15건 있고 거기서 RAG 는 15개를 전부 틀린다. Router 를 붙이면 그 자리가
2 맞음 / 5 틀림 / 8 기권이 된다.

그리고 이 설계는 한 걸음 더 간다 — **근거가 원문에 있다는 것만으로 통과
시키지 않는다.** `shared` 조건에 붙은 인용은 결정적일 수 없다는 규칙(V7)은
RAG 에 없는 계약이다.

### Q2. 일반적인 Multi-Agent 와 무엇이 다른가

일반적인 multi-agent 는 **여러 LLM 이 서로 이야기하고 합의**한다. 이 설계는
LLM 을 **네 자리에만** 둔다 — 구조화·조건 후보·후보 판정·설명. 경로·결론·
기권·게이트는 전부 결정 표와 결정론적 검사다.

핵심은 **LLM 의 출력을 다른 LLM 이 아니라 결정론이 검사한다**는 것이다.
Diff Coverage Gate 가 그 예다 — 텍스트 차집합은 코드가 계산하고, LLM 이
그것을 덮지 못하면 그 자리에서 막힌다. LLM 심판을 하나 더 두면 AG-13 이
한 층 위에서 반복될 뿐이다.

그리고 **왜 그 경로를 갔는지가 데이터로 남는다** — `route_reason` 에 발화한
줄 번호가 들어간다. 사람의 서술이 아니다.

### Q3. DeFactoRule 의 고유 기술적 기여

넷이고, 넷째가 이번에 생겼다.

1. **TRAP 지표** — "닮은 선례가 있는데 그 선례가 틀린 답을 가리키는" 구간을
   따로 떼어 재는 파티션. 전체 정확도는 이 구간을 감춘다.
2. **보정된 신뢰 구간** — `TRUST` 0.60 / `DOUBT` 0.15 를 dev leave-one-out
   에서 뽑았다. 구간별 오류율 0.062 vs 0.500, 신뢰구간 비중첩. 임의로 고른
   문턱이 아니다.
3. **기권을 벌하지 않는 평가** — 기권을 `predicted: null` 로 내보내면 위험-
   커버리지 곡선이 그것을 전부 오답으로 센다. `provisional` + `abstained`
   분리로 AURC 판정이 뒤집혔다(−0.270 유의 → −0.021 판정 보류). 기권을 다루는
   시스템은 기권을 다루는 지표가 있어야 한다.
4. **결정적 조건 접지 (AG-13 에서 나옴)** — *"인용이 원문에 있다"* 는 근거의
   충분조건이 아니다. **두 사안에 똑같이 있는 문장은 둘을 가를 수 없다.**
   이 자명한 명제를 계약(`shared` ⇒ `decisive` 불가)과 지표(Diff Coverage,
   Deciding-Factor Grounding)로 만든 것이 이 프로젝트의 새 기여다.

넷 다 **실패에서 나왔고 그 실패가 저장소에 번호를 달고 남아 있다** —
EV-24, AG-12, AG-13.

### Q4. 애자일소다 DS팀의 "업무 절차/판단 기준을 AI Agent Workflow 로 구현" 과의 연결

이 도메인이 그 문제의 순수한 형태다. 금융규제 회신 업무에는 **문서화된 절차
(명시 규정)와 문서화되지 않은 실무 기준(선례에서만 드러나는 de facto rule)이
동시에 있고, 담당자는 그 둘을 대조해 판단한다.** 이 설계는 그 절차를 11단계로
분해하고, 각 단계에서 무엇을 LLM 에게 맡기고 무엇을 코드가 붙드는지 정했다.

옮겨 쓸 수 있는 형태로 남는 것 셋.

- **판단 기준의 역추출** — 규정에 없지만 실무가 따르는 기준을 데이터에서
  뽑고, 그것이 새 사건에 전이되는지 검증한다(E6 에서 `조치` 규칙이
  100%→20% 로 무너지는 것을 확인했다. 전이 검증 없이 역추출만 하면 위험하다).
- **언제 답하지 말아야 하는가** — 실무 자동화에서 오답의 비용은 무응답의
  비용보다 크다. 기권 게이트와 이관 조건을 결정론으로 두는 설계가 그것을
  다룬다.
- **근거의 계약** — 실무 판단은 "왜" 가 없으면 쓸 수 없다. `execution_trace`
  와 Evidence Contract 가 그것을 형으로 강제한다.

### Q5. E11b 가 실패한 이유를 최종 Workflow 는 어떻게 해결하려 하는가

**실패의 원인은 질문의 형태였다.** "두 요청의 차이가 결론을 바꿀 만한가" 를
통째로 물으면, 모델은 두 글을 나란히 읽고 **닮은 곳**을 찾는다. 유사도가
높을수록 닮은 곳이 많아지고, 그중 하나를 근거로 집으면 `applies` 가 나온다.

세 겹으로 바꾼다.

1. **질문을 바꾼다.** "닮았는가" 대신 "조건이 어떻게 갈리는가". 출력은
   문장이 아니라 관계가 붙은 조건 집합이고, `only_in_request` /
   `only_in_precedent` 가 **일급 칸**이라 비워 둘 수 없다.
2. **결정론이 누락을 잡는다.** 텍스트 차집합을 코드가 계산하고, 조건 목록이
   그것을 덮지 못하면 `applies` 를 낼 수 없다(Diff Coverage Gate). 이것이
   `240023`(진짜 중복 → 통과)과 `220049`(실질 차이 있음 → 차단)를 가른다 —
   지금의 opposition guard 는 둘을 구분하지 못하고 똑같이 막았다.
3. **근거 계약이 막는다.** `shared` 조건에 붙은 인용은 `decisive` 가 될 수
   없고, 결론은 `decisive` 근거를 요구한다(V7). E11b 가 인용한 문장이
   정확히 `shared` 였다.

**셋 다 아직 재보지 않았다.** S5 도 LLM 이므로 실패할 수 있다. 달라지는 것은
실패의 모양이다 — "틀린 `applies`" 가 아니라 "분석 미완 → 기권" 이 된다.
그것도 손실이지만, 오답보다 싸다.

### Q6. 3개월 안에 어디까지 되는가

기준선을 먼저 적는다. 실험 E1~E11b 완료 · 결정론 파이프라인과 API 서비스
계층 구현 완료 · 실패 레지스트리와 회귀 스위트 운영 중(**정확한 건수는 여기
적지 않는다 — README 의 대조되는 표시가 유일한 출처다**). 이 문서 작성
시점까지 쓴 API 비용은 누적 $4.12 이고, 그중 E11b 가 $0.0674 다.

| 기간 | 무엇 | 근거 |
|---|---|---|
| **1개월** | S1(구조화) · S5(조건 분석) · Diff Coverage Gate · V7 · 지표 둘 | 기존 파이프라인 위에 단계 둘을 얹는 일. 검색·평가·서비스는 그대로 |
| **2개월** | S2 인용 색인 · C3 · S7 결정 표 확장 · TRAP 15건 + 사정거리 22건 재측정 | 조문 축을 붙이는 일. 새 데이터는 dev 인용 색인뿐(비용 0) |
| **3개월** | `HUMAN_REVIEW` 흐름 · S11 감사 대시보드 · 회귀 스위트 확장 | UI 는 §15 대로 채팅창이 아니라 **조건 대조 화면** |

**3개월 안에 안 되는 것도 적는다.**

- **`조치` 구간은 좋아지지 않는다.** test 에 14건뿐이고 사정거리 22건에는
  0건이다. 표본이 늘지 않는 한 이 구간의 개선은 측정 불가다.
- **법령 원문 수집은 3개월 계획에 넣지 않는다.** 인용 색인으로 부족한 것이
  확인된 뒤에 시작한다.
- **전체 성능이 기존 LLM 판정기를 넘는다고 약속하지 않는다.** 현재 AURC 는
  `router` 0.236 대 `sector` 0.124 다. 이 설계의 목표는 그 숫자를 뒤집는 것이
  아니라 **틀릴 때 왜 틀렸는지 말할 수 있는 시스템**을 만드는 것이다.

## 14. 이 설계가 틀릴 수 있는 곳

미리 적어 둔다.

1. **S5 도 LLM 이다.** 조건 분해가 AG-13 과 같은 방식으로 실패할 수 있다.
   게이트가 잡는 것은 **누락**이지 오분류가 아니다. `only_in_request` 를
   적어 놓고 그것을 `decisive` 가 아니라고 판단하면 게이트는 통과한다.
2. **텍스트 차집합이 의미 차이와 같지 않다.** 표현만 다르고 뜻이 같은 조각이
   차집합에 남으면 게이트가 헛발화한다. 메타데이터 필터가 얼마나 잘 되느냐에
   달려 있고, 그것은 재봐야 안다.
3. **단계를 늘리면 오류가 곱해진다.** 4단계에서 11단계가 된다. 각 단계의
   실패율이 낮아도 완주율은 떨어진다 — 그래서 `workflow completion` 을 지표에
   넣었다.
4. **`기타` 는 여전히 혼합 범주다.** 세 검색기 전부에서 함정률이 0.54~0.56
   으로 가장 높았다. 조건 대조가 이 범주를 갈라 줄지는 알 수 없다.
5. **opposition guard 를 떼면 나빠질 수 있다.** E11b 에서 그것이 오답 하나를
   막았다. S5 가 그 일을 대신한다는 것은 **가정이지 측정이 아니다.**
6. **`why_not_decisive` 가 통과 경로가 될 수 있다.** 모델이 실질 차이를
   `only_in_*` 에 올려 놓고 그럴듯한 설명과 함께 `decisive: false` 를 붙이면
   G3·G4 를 지나 `no_decisive_difference` 로 `applies` 가 나간다. 게이트는
   **누락을 잡지 오분류를 잡지 못한다.** 이 경로로 나간 건수를 따로 세야 한다.
7. **메타데이터 패턴 목록이 좁으면 과잉 기권, 넓으면 AG-13 재발.** §3.2 의
   목록은 두 방향으로 다 틀릴 수 있고, 어느 쪽으로 틀렸는지는 `S = ∅` 로
   판정된 건과 `incomplete_analysis` 로 막힌 건을 같이 봐야 안다.
8. **조각 동일성 문턱 `τ` 가 아직 없다.** 정하기 전에는 게이트를 켤 수 없다.
   너무 낮으면 다른 조각을 같다고 보아 `S` 가 줄고(AG-13 재발), 너무 높으면
   같은 조각을 다르다고 보아 `S` 가 부풀어 헛된 `incomplete_analysis` 가 난다.
9. **미래 선례 누출이 지금 데이터에 있다.** `240023` 의 1등 선례는 요청보다
   나중 건이다. dev/test 를 시점이 아니라 무작위로 나눴기 때문이고, 실제
   업무에서는 존재할 수 없는 근거다. S3 에 시점 필터를 넣어야 하며, **넣으면
   기존 수치가 달라질 수 있다.** 얼마나인지는 재보지 않았다.
