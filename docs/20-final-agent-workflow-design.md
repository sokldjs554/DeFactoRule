# 최종 업무 Agent Workflow 설계

**이 문서는 설계만 한다. 코드는 없다.** 여기 적힌 것 중 구현된 것은
"현재 자산" 으로 표시한 것뿐이고, 나머지는 전부 **설계 목표**다. 구현했다고
주장하지 않는다.

기준이 되는 사건은 하나다 — **AG-13**(`surface-match-as-evidence`). E11b 실측
`220049` 에서 모델은 원문에 실재하는 문장을 인용했지만 그 문장은 **두 요청에
똑같이 있는 문장**이었고, 결론을 가른 구절은 건드리지 않았다. 인용이 원문에
있다는 것만으로 근거가 되지 않는다는 뜻이다. 이 문서의 설계는 대부분 그
한 문장에서 나온다.

---

## 0. Agent 의 업무 단위 — 한 문장

> **금융회사가 제출한 규제 예외 요청 한 건에 대해, 인용된 규정과 과거
> 회신 선례를 검토하여 "이 선례가 이 요청에 적용되는가" 를 결정적 조건
> 단위로 대조하고, 근거가 충분하면 결론(비조치/조치/기타)을, 충분하지
> 않으면 추가정보 요청 또는 담당자 이관을 내놓는다. 모든 결론에는 그것을
> 뒤집을 수 있었던 조건과 그 조건의 출처가 붙는다.**

이 문장에서 의도적으로 뺀 것이 있다.

- "승인/반려" 라고 쓰지 않았다. 이 데이터의 라벨은 `비조치`/`조치`/`기타`
  이고 `기타` 는 반려가 아니다(소관 아님·이미 허용됨·요건 미비 등이 섞여
  있다). 없는 의미를 라벨에 씌우지 않는다.
- "정확히 맞힌다" 를 목표로 쓰지 않았다. E1~E11b 에서 반복해서 확인한 것은
  **맞히는 것보다 언제 답하지 말아야 하는지가 이 업무의 값어치**라는 것이다.

### 데이터가 진짜 무엇인지 먼저 적는다

이 저장소의 자료는 **접수 대기 중인 예외 승인 요청 큐가 아니라, 이미 회신이
끝나 공개된 사례집**이다. 그러므로 "실제 업무 요청을 받는다" 는 설계는
사례집의 `요청대상행위` 를 **접수 시점의 요청서로 간주**해 재생하는 것이다.
이 치환을 문서 앞에 적어 두지 않으면 이후의 모든 평가가 과장된다.

    비조치 사례      259건 (요청대상행위 · 판단 · 판단이유)
    라벨             dev 85 / test 170  — 인쇄된 체크박스에서 나온다(순환 없음)
    법령해석         836건 (질의요지 · 회답 · 이유) — **라벨 없음**
    질의–회답 쌍     1,122건
    유도 규칙        11개 (E6, dev 에서 학습 · 명시 규정이 아니다)

## 1. 지금 무엇이 없는지 — 설계의 전제

**명시 규정 원문이 저장소에 없다.** 이것이 이 설계의 가장 큰 제약이다.

    조문(제N조)이 언급된 사례      218 / 259
    그 조문의 **원문**             없음

인용은 대부분 `판단이유` 안에 있다. 그런데 `판단이유` 는 **회신문의 답변
쪽**이다. 판단해야 할 사건의 `판단이유` 를 근거로 쓰면 정답을 보고 답하는
것이고, 이 프로젝트가 W1 게이트부터 막아 온 순환 그 자체다.

그래서 "Explicit Rule Retrieval"(2단계)은 다음 셋 중 하나로만 성립한다.

| 안 | 무엇을 색인하나 | 순환 | 비용 |
|---|---|---|---|
| A. 인용 색인 | **dev 선례의** `판단이유` 에서 조문 인용만 뽑아 색인 | 없음 (dev 만) | 0 |
| B. 법령 원문 | 국가법령정보센터에서 인용된 조문 원문을 수집 | 없음 | 새 데이터 |
| C. 안 함 | 2단계를 비우고 선례만 쓴다 | 없음 | 0 |

**설계는 A 를 기본으로 하고, B 를 조건부로 둔다.** A 는 "이 조문이 걸린
과거 사건들" 이라는 축을 공짜로 만든다 — 그것만으로도 선례 검색이 문자
유사도 하나에 의존하는 현재 구조가 깨진다. B 가 필요한 이유와 규모는 §12 에
적는다. C 는 현재 상태이고, AG-13 은 C 에서 났다.

## 2. Workflow 11단계

각 단계에 Input / Output / 책임 주체 / 실패 조건 / 진행 조건을 적는다.
**책임 주체**는 셋 중 하나로만 표기한다 — `LLM` · `Retriever` · `결정론`.

### S1. Request Structuring

| | |
|---|---|
| **Input** | 요청 원문 (`요청대상행위`) |
| **Output** | `structured_request` — 요청 행위 · 대상 · 인용 조문 · 조건절 목록 · 요청 유형 |
| **주체** | **LLM**(의미 추출) + **결정론**(조문 표기 정규화 · 스키마 검증) |
| **실패 조건** | 스키마 위반 · 요청 행위가 비어 있음 · 인용 조문 표기가 정규형으로 안 떨어짐 |
| **진행 조건** | 스키마 통과 AND 요청 행위 1개 이상 |

조건절을 여기서 뽑는 것이 S5(결정적 조건)의 전제다. 지금 워크플로는 이
단계가 아예 없고 원문을 그대로 n-gram 에 넣는다 — AG-13 의 먼 원인이다.

**누출 차단(현재 자산 재사용):** `요청대상행위` 에 결론 낱말이 남아 있으면
모델은 읽기만 하면 된다. 기존 `LEAK` 마스킹과 그 회귀 검사를 그대로 건다.

### S2. Explicit Rule Retrieval

| | |
|---|---|
| **Input** | `structured_request.인용조문`, 요청 행위 |
| **Output** | `explicit_rules[]` — 조문 식별자 · (원문 또는 인용 맥락) · 출처 · 근거 강도 |
| **주체** | **Retriever** |
| **실패 조건** | 인용 조문이 색인에 없음 · 정규화 실패 |
| **진행 조건** | 항상 진행 (0건이어도 S3 로 간다 — 규정이 안 걸리는 요청이 있다) |

§1 의 안 A 기준으로, 여기서 나오는 것은 **"이 조문이 걸렸던 과거 사건들"**
이지 조문 원문이 아니다. 그 사실을 `근거 강도` 에 명시적으로 담는다.
안 B 를 채택하면 같은 자리에 원문이 들어오고 강도가 올라간다.

### S3. Precedent Retrieval

| | |
|---|---|
| **Input** | `structured_request`, 요청 원문 |
| **Output** | `precedent_candidates[]` — 선례 · 유사도 · 검색기(L/D/H) · 조문 겹침 |
| **주체** | **Retriever** |
| **실패 조건** | 후보 0건 · 유사도 전부 `DOUBT` 미만 |
| **진행 조건** | 항상 진행 (0건이면 S7 이 그것을 근거 없음으로 다룬다) |

**현재 자산 그대로.** L(문자 4-gram IDF)·D(LSA)·H(RRF) 세 검색기와 비교
결과(E8)가 이미 있다. 여기에 S2 의 **조문 겹침**을 세 번째 축으로 더한다 —
문자 유사도만으로 뽑으면 `240047` 처럼 공유 각주가 순위를 만든다.

### S4. De Facto Rule Candidate

| | |
|---|---|
| **Input** | `precedent_candidates`, dev 라벨 |
| **Output** | `de_facto_rule_candidates[]` — 조건 → 결론 · dev 지지도 · dev 정밀도 |
| **주체** | **결정론**(규칙 유도) |
| **실패 조건** | 지지도가 클래스 문턱 미만 · 규칙끼리 반대 결론 |
| **진행 조건** | 항상 진행 |

**현재 자산 그대로** — E6 유도 규칙 11개. 다만 E6 가 남긴 경고를 설계에
새긴다: **`조치` 규칙의 dev→test 전이가 100%→20% 였다.** 그러므로 de facto
rule 은 **단독 결론 근거로 쓰지 않고 S6 의 대조 축으로만 쓴다.**

### S5. Deciding-Factor Analysis ★ 새 단계

이 단계가 이 설계의 핵심이다. **§3 에서 따로 다룬다.**

### S6. Conflict Check

| | |
|---|---|
| **Input** | `explicit_rules`, `de_facto_rule_candidates`, `precedent_candidates`, `deciding_factors` |
| **Output** | `conflicts[]` — 종류 · 관련 근거 id · 심각도 |
| **주체** | **결정론** |
| **실패 조건** | 없음 (검출만 한다) |
| **진행 조건** | 항상 진행 |

검출하는 충돌 네 가지.

    C1  선례끼리 반대 결론          (현재 opposition guard 가 보는 것)
    C2  규칙끼리 반대 결론          (현재 R1)
    C3  명시 규정과 선례가 어긋남    ← 새로 생긴다. 규정이 우선한다
    C4  결정적 조건이 서로 반대를 가리킴  ← S5 가 생겨야 볼 수 있다

C3 는 지금 볼 수 없다. S2 가 없기 때문이다. **근거의 위계를 명시한다** —
명시 규정 > 선례 > de facto rule. AG-12 에서 배운 것(약한 근거가 강한 근거를
덮으면 안 된다)을 위계로 못 박는다.

### S7. Decision / Abstention / Human Handoff

| | |
|---|---|
| **Input** | 위 전부 |
| **Output** | 잠정 결론 + 경로 + 발화한 결정 표의 줄 |
| **주체** | **결정론** (결정 표) |
| **실패 조건** | 어느 줄도 발화하지 않음 = 표가 불완전 |
| **진행 조건** | 항상 S8 로 (기권도 검증을 지난다) |

**현재 자산 확장.** Router 결정 표 R1~R10 을 그대로 두고 줄을 더한다. 원칙
셋은 유지한다 — (1) LLM 은 경로를 고르지 않는다, (2) 발화한 줄 번호를
`route_reason` 에 남긴다, (3) 죽은 줄은 지운다(R4 를 그렇게 지웠다).

### S8. Evidence Validation

| | |
|---|---|
| **Input** | 잠정 결론과 그에 붙은 근거 |
| **Output** | `validation[]` — 검사별 통과 여부 · 폐기된 근거 |
| **주체** | **결정론** |
| **실패 조건** | 차단 검사 불통과 → S7 로 되돌아가 기권 |
| **진행 조건** | 차단 검사 전부 통과 |

현재 V1~V6 에 **V7 을 더한다 — 결정적 조건 접지**(§9). E11a 에서 확인한
불편한 사실도 함께 남긴다: 현재 배선에서 V1·V2·V3·V5 는 **구성상 참**이라
아무것도 막지 못했다(값어치 0). V7 은 그 자리를 메우기 위한 검사이고,
**만들자마자 값어치를 재서 0 이면 그렇게 적는다.**

### S9. Final Decision

| | |
|---|---|
| **Input** | 검증을 통과한 잠정 결론 |
| **Output** | `decision` 또는 `abstention` 또는 `human_handoff` + 신뢰도 |
| **주체** | **결정론** (최종 안전 게이트) |
| **실패 조건** | 근거 없는 결론 · 신뢰도와 근거 강도 불일치 |
| **진행 조건** | — (종점) |

최종 안전 게이트가 마지막으로 보는 것: 결론이 있으면 근거가 있는가, 근거가
`selected_evidence` 안에 실재하는가, 결정적 조건이 하나 이상 붙어 있는가.

### S10. Execution Trace

| | |
|---|---|
| **Input** | 모든 단계의 입출력 |
| **Output** | `execution_trace[]` — 단계 · 요약 · 결정에 영향을 준 값 |
| **주체** | **결정론** |
| **실패 조건** | 단계가 흔적 없이 지나감 |
| **진행 조건** | — |

**현재 자산 그대로.** 소요 시간처럼 실행마다 달라지는 값은 넣지 않는다 —
넣으면 두 실행의 trace 를 비교할 수 없고 회귀 테스트가 못 쓴다.

### S11. Evaluation / Audit

| | |
|---|---|
| **Input** | 예측 레코드 + trace |
| **Output** | 축별 지표 (§10) |
| **주체** | **결정론** |
| **실패 조건** | 표본 불일치 · 기권을 오답으로 인코딩 |
| **진행 조건** | — |

EV-24 를 여기 못 박는다: 기권은 `predicted: null` 이 아니라 `provisional` +
`abstained` 로 나간다. 그러지 않으면 **기권을 보여주려고 만든 지표가 기권을
벌한다.**

## 3. S5 — Deciding-Factor Analysis (AG-13 이 요구한 단계)

### 무엇이 잘못됐는가

E11b 의 applicability 는 두 요청문을 통째로 주고 "차이가 결론을 바꿀
만한가" 를 물었다. 모델은 **둘을 나란히 읽고 닮은 곳을 찾는** 일을 했고,
`220049` 에서 닮은 문장을 찾아 그것을 근거로 냈다. 질문의 형태가 그 답을
유도했다.

### 무엇으로 바꾸는가

**"닮았는가" 를 묻지 않는다. "조건이 어떻게 갈리는가" 를 묻는다.** 출력은
문장이 아니라 **조건 집합**이고, 조건마다 관계가 붙는다.

| 관계 | 뜻 |
|---|---|
| `shared` | 두 요청에 다 있다 |
| `differs` | 둘 다 있는데 값이 다르다 |
| `only_in_request` | **요청에만 있다** |
| `only_in_precedent` | **선례에만 있다** |
| `exception` | 한쪽이 예외 요건에 걸린다 |
| `decisive` | 이 조건이 뒤집히면 결론이 바뀐다 (모델의 주장) |

`only_in_request` / `only_in_precedent` 를 **일급 출력으로 강제**하는 것이
설계의 요점이다. 이 칸이 있으면 모델은 "무엇이 빠졌는지" 를 말해야 하고,
빈칸으로 두면 아래 결정론 게이트가 그것을 잡는다.

### Diff Coverage Gate — 결정론이 LLM 을 검사한다

조건 목록을 LLM 이 만든다면 **S5 도 AG-13 과 같은 방식으로 실패할 수 있다.**
그것을 막는 것은 프롬프트가 아니라 결정론적 대조다.

```
1. 결정론  두 요청문의 텍스트 차집합을 계산한다
             (메타데이터 — 날짜·일련번호·각주 상용구 — 는 제외)
2. 결정론  차집합에 실질 조각이 남아 있는가?
3.   남아 있다  → LLM 이 낸 조건 중 only_in_* 이 그 조각을 덮는가?
                  덮지 못하면 **분석 미완**이다. `applies` 를 낼 수 없다.
4.   남아 있지 않다 → 두 요청은 실질적으로 같은 글이다. `applies` 가능.
```

이 게이트가 두 사건을 어떻게 가르는지가 설계의 시험이다.

| | 텍스트 차집합 | 게이트 판정 |
|---|---|---|
| `240023` (0.918) | 날짜·일련번호 줄뿐 → 메타데이터로 제외 → **빈 집합** | `applies` 허용 |
| `220049` (0.738) | 요청의 *"내부 업무용 시스템과는 연결되지 않음"*, 선례의 DMZ 중계서버 질문 → **실질 조각 있음** | 조건 목록이 이것을 안 덮으면 **`applies` 불가** |

**유사도가 높다는 이유로 막지 않는다.** 막는 것은 "다른 부분이 실재하는데
분석이 그것을 언급하지 않았다" 는 사실이다. 그래서 `240023` 같은 진짜
중복은 통과하고 `220049` 는 걸린다 — 지금의 opposition guard 가 이 둘을
구분하지 못하고 똑같이 막았던 자리다(이익 1 · 손해 1).

### 220049 에서 이 단계가 무엇을 잡아야 하는가

```
shared              금융회사가 SaaS 로 임직원 인사정보를 처리
shared              전자금융감독규정 제14조의2 제3항·제8항 단서 적용 여부
shared              인터넷용 PC·모바일기기로 클라우드 접속 시 제15조 제1항 제3호
only_in_request     "내부 업무용 시스템과는 연결되지 않음"        ← decisive
only_in_precedent   내부 업무용시스템을 DMZ 중계서버로 연동하는 경우  ← decisive
```

**두 `decisive` 는 같은 축의 앞뒷면이다** — 내부망 연결 여부. 선례가 `기타`
가 된 이유가 그 축에 있고, 요청은 그 축에서 반대편에 서 있다. 그러므로
`differs` 이고, 근거는 *"내부 업무용 시스템과는 연결되지 않음"* 이어야 한다.

E11b 는 위 표의 **처음 세 줄만 보고** `applies` 를 냈다.

### 이 단계의 계약

| | |
|---|---|
| **Input** | `structured_request`, 선례 후보 1건의 구조화된 요청, (S2 의 조문) |
| **Output** | `deciding_factors[]` (위 스키마) + `applicability` 후보 판정 |
| **주체** | **LLM**(조건 후보 생성) + **결정론**(Diff Coverage Gate · 스키마 검증 · 인용 대조) |
| **실패 조건** | 스키마 위반 · 인용이 원문에 없음 · **차집합 미커버** · `decisive` 가 0인데 `differs` |
| **진행 조건** | 게이트 통과 AND 모든 인용이 원문에 접지 |

**선례의 결론은 프롬프트에 넣지 않는다.** E11b 의 이 설계는 옳았고 그대로
가져간다 — 넣으면 결론에서 거꾸로 판단하는 순환이 생긴다.

## 4. 상태 머신

```
request
  └─ S1 ─► structured_request        스키마 통과 시에만 채워진다
       ├─ S2 ─► explicit_rules       0건 허용
       ├─ S3 ─► precedent_candidates 0건 허용
       └─ S4 ─► de_facto_rule_candidates
            └─ S5 ─► deciding_factors      게이트 통과 시에만
                     applicability          게이트 실패 시 `incomplete`
                 └─ S6 ─► conflicts
                      └─ S7 ─► selected_evidence + 경로
                           └─ S8 ─► validation
                                └─ S9 ─► decision | abstention | human_handoff
                                     └─ S10 execution_trace (전 구간 누적)
```

| 상태 | 채워지는 조건 | 비워지는(무효화되는) 조건 |
|---|---|---|
| `request` | 접수 시 | — |
| `structured_request` | S1 스키마 통과 | 누출 마스킹 실패 시 전체 중단 |
| `explicit_rules` | 조문 정규화 성공 | — |
| `precedent_candidates` | 유사도 ≥ `DOUBT` | S8 에서 폐기된 근거는 제외 |
| `de_facto_rule_candidates` | 클래스별 지지도 문턱 통과 | 규칙 충돌 시 사용 불가 표시 |
| `deciding_factors` | S5 게이트 통과 | 인용 미접지 항목은 개별 폐기 |
| `applicability` | `deciding_factors` 존재 | 게이트 실패 시 `incomplete` 로 고정 |
| `conflicts` | S6 항상 | — |
| `selected_evidence` | S7 이 고른 것 | S8 폐기분 제외 |
| `validation` | S8 항상 | — |
| `decision` | S9 안전 게이트 통과 | 기권/이관 시 **비어 있어야 한다** |
| `abstention` | 결정 표의 기권 줄 발화 | 회수 시 사유와 함께 해제 |
| `human_handoff` | §8 의 이관 조건 | — |
| `execution_trace` | 매 단계 append | 절대 지우지 않는다 |

두 가지를 상태 규칙으로 못 박는다.

- **기권 시 `decision` 은 비어 있고 `provisional` 만 채워진다** (EV-24).
- **회수는 회수만 한다** — 이 워크플로의 어떤 후단계도 새로 기권시키지
  않는다. 그래야 "나빠질 수 없다" 가 구조적으로 보장된다.

## 7. Decision Type — 실제로 필요한 것만

데이터가 지지하는 것과 업무가 요구하는 것을 나눠서 고른다.

| 상태 | 뜻 | 데이터가 지지하는가 |
|---|---|---|
| `NO_ACTION` (비조치) | 요청 행위에 조치를 취하지 않는다 | ✅ 체크박스 라벨 |
| `ACTION` (조치) | 조치 대상이다 | ✅ 라벨 (test 14건뿐) |
| `OTHER` (기타) | 소관 아님·이미 허용·요건 미비 등 | ✅ 라벨 (혼합 범주) |
| `REQUEST_MORE_INFORMATION` | 요청서에 판단에 필요한 조건이 없다 | ❌ **정답이 없다** |
| `ABSTAIN` | 근거가 없거나 충돌한다 | ⚠ 대리 평가만 가능 |
| `HUMAN_REVIEW` | 사람에게 넘긴다 | ⚠ 대리 평가만 가능 |

**`APPROVE`/`REJECT` 를 쓰지 않는다.** `기타` 를 반려로 번역하는 순간 라벨에
없는 뜻이 생긴다. 원 라벨 이름을 유지한다.

**`REQUEST_MORE_INFORMATION` 은 설계에는 넣되 성능 주장에는 쓰지 않는다.**
이 데이터에는 "정보가 부족해 되물었다" 는 정답이 없다. 발화 조건만 결정론적
으로 정의하고(요청에 `decisive` 후보가 0개이면서 선례가 문턱 위), **발화
횟수와 그때의 정답 분포만 보고한다.** 정확도라고 부르지 않는다.

`ABSTAIN` 과 `HUMAN_REVIEW` 의 구분도 결정론으로 둔다.

    ABSTAIN        근거가 없거나 약하다 — 사람이 봐도 자료가 더 필요하다
    HUMAN_REVIEW   근거는 강한데 서로 반대다 (C1·C3·C4) — 사람이 판단할 자료는 있다

## 8. Evidence Contract — "인용은 맞지만 결정적이지 않다" 를 표현한다

AG-13 의 직접적 처방이다. 근거 하나의 계약을 이렇게 둔다.

| 필드 | 뜻 | 검사 주체 |
|---|---|---|
| `text` | 원문에서 그대로 딴 구절 | 결정론 (글자 대조) |
| `source` | 문서·일련번호·조문 | 결정론 |
| `kind` | `explicit_rule` / `precedent` / `de_facto_rule` | 결정론 |
| `role` | `supporting` / `contradicting` / `contextual` | LLM 후보 → 결정론 확정 |
| `factor_id` | 이 근거가 붙은 결정적 조건 | 결정론 (S5 출력과 대조) |
| `factor_relation` | `shared` / `differs` / `only_in_*` / `exception` | S5 에서 옴 |
| `decisive` | 이 근거가 결론을 뒤집을 수 있는가 | **결정론 (아래 규칙)** |
| `relevance` | 요청 조건과의 겹침 정도 | 결정론 |

**핵심 규칙 — `shared` 관계의 근거는 `decisive` 가 될 수 없다.**

두 요청에 똑같이 있는 문장은 둘을 가르지 못한다. 정의상 그렇다. 그러므로
`factor_relation == shared` 인 근거에 `decisive: true` 를 붙일 수 없고,
`applies` 결론은 **`decisive` 근거를 하나 이상 요구**한다.

이 한 줄이 `220049` 를 잡는다. E11b 가 인용한 문장은 `shared` 이므로
`decisive` 가 될 수 없고, 따라서 그 근거만으로 `applies` 를 낼 수 없다.

이것이 **V7 — 결정적 조건 접지 검사**다.

    V7  결론에 붙은 근거 중 decisive 가 1개 이상인가
        그 decisive 근거의 factor_relation 이 shared 가 아닌가
        그 근거의 text 가 원문에 글자 그대로 있는가   (기존 V3)

세 조건이 전부 만족해야 결론이 나간다. 하나라도 어긋나면 S7 로 되돌아가
기권한다. **"인용은 맞지만 결정적이지 않다" 가 `V3 통과 · V7 불통과` 로
표현된다** — 지금은 이 상태를 나타낼 자리가 없다.

## 9. 평가 설계

기존 지표를 버리지 않는다. 축을 나눈다 — n 개의 사건을 하나의 정확도로
뭉치면 무엇이 일어났는지 사라진다는 것을 E11b 에서 확인했다.

| 축 | 지표 | 상태 |
|---|---|---|
| **Retrieval** | Recall@k · nDCG@k · 조문 겹침 재현율 | 새로 필요 |
| | TRAP 구간 비율 | **기존 (§10 고유 지표)** |
| **Applicability** | 판정 정확성 (applies/differs/unclear) | 기존 (E11b, n=5) |
| | **Diff Coverage Rate** ★ | **새로 필요** |
| **Decision** | 매크로 F1 · 커버리지 · AURC | **기존** |
| | TRAP 구간 정확도 | **기존** |
| **Evidence** | 인용 접지율 (V3) | **기존** |
| | **Deciding-Factor Grounding Rate** ★ | **새로 필요** |
| **Safety** | 근거 없는 결론 건수 | 기존 (최종 게이트) |
| | 과신 — 신뢰도 대비 실제 정확도 | 기존 |
| | **부적절한 회수** — 회수 후 오답 | 기존 (E11b) |
| | 기권 정확성 — 기권한 건 중 답했으면 틀렸을 비율 | **기존** (지금 36%) |
| **Workflow** | 완주율 · 경로 분포 · `route_reason` 커버리지 | 기존 |
| | 이관 적정성 | 대리 지표만 |

### 새로 필요한 지표 둘, 그리고 왜 필요한가

**★ Diff Coverage Rate** — 두 요청의 실질 텍스트 차집합 중, S5 의
`only_in_*` 조건이 덮은 비율.

*왜 필요한가:* 이것이 없으면 AG-13 을 **수치로 감시할 수 없다.** E11b 에서
그 실패를 발견한 것은 제가 `220049` 한 건에 대해 결정 구절을 미리 지정해
뒀기 때문이고, 그런 수작업은 확장되지 않는다. 차집합은 결정론적으로 계산
되므로 모든 건에서 자동으로 잰다.

**★ Deciding-Factor Grounding Rate** — 결론에 붙은 근거 중, `shared` 가
아닌 조건에 접지된 것의 비율.

*왜 필요한가:* 기존 인용 접지율(V3)은 `220049` 에서 **100% 통과했다.**
인용은 전부 원문에 있었기 때문이다. 즉 기존 지표는 AG-13 을 보지 못한다.
"원문에 있는가" 와 "가를 수 있는가" 는 다른 질문이고, 다른 지표가 필요하다.

### 평가 규율 (기존 유지)

- Wilson 신뢰구간 · 짝지은 부트스트랩 · Holm 보정. `조치` 14건 위의 수치는
  구간을 반드시 함께 적는다.
- 기권은 `provisional` + `abstained` 로 내보낸다 (EV-24).
- 표본이 다르면 나란히 놓지 않는다 (`mismatched-sample` 패턴 가드).
- **실행하지 않은 수치는 쓰지 않는다.**

**설계 목표 (구현하지 않았다)**

```
유사도 0.738  →  선례 후보 검색 (+ 조문 겹침으로 재순위)
              →  S1 이 양쪽을 조건 단위로 구조화
              →  S5 가 조건을 관계별로 분해
                   shared            SaaS 인사정보 처리 · 제14조의2 · 제15조
                   only_in_request   "내부 업무용 시스템과는 연결되지 않음"
                   only_in_precedent DMZ 중계서버 연동 질의
              →  결정론 Diff Coverage Gate: 차집합이 덮였는가 → 예
              →  decisive 조건이 반대 축을 가리킴 → differs
              →  근거 = only_in_request 구절 (shared 가 아니므로 V7 통과)
              →  선례를 버리고 다른 근거로 진행 · **불필요한 기권 없이**
```

**이것은 목표이고 아직 재보지 않았다.** S5 도 LLM 을 쓰므로 같은 방식으로
실패할 수 있다. 다른 점은 실패했을 때 **결정론이 그것을 안다**는 것뿐이다 —
차집합은 코드가 계산하므로, 조건 목록이 그것을 덮지 못하면 게이트가 잡는다.
그 경우 결과는 "틀린 `applies`" 가 아니라 "분석 미완 → 기권" 이다.

**AG-13 은 이 설계가 구현되고 재보기 전까지 열린 채로 둔다.**

**새 대규모 코퍼스를 만들지 않는다.** 기존 것으로 되는 것과 안 되는 것을
나눈다.

| 필요 | 기존으로 되는가 |
|---|---|
| 요청문 · 라벨 | ✅ 259건 · dev 85 / test 170 |

### 새 데이터 ① — 법령 조문 원문

- **왜 필요한가:** S2·C3(규정과 선례가 어긋나는 경우)가 성립하지 않는다.
  지금은 근거 위계의 맨 위 칸이 비어 있다.
- **왜 기존으로 안 되는가:** 조문 인용은 `판단이유` 안에 있고 그것은 **답변
  쪽**이다. 판단 대상 사건의 것을 쓰면 순환이다.
- **몇 건인가:** 사례가 인용한 조문의 합집합. 218/259 사례가 조문을
  언급하므로 **수십 개 조문 수준**이고, 사례 수보다 훨씬 적다.
- **대안(먼저 시도):** dev 선례의 인용만으로 **인용 색인**을 만든다(§1 안 A).
  비용 0 이고 순환도 없다. 이것으로 부족한 것이 확인된 뒤에 원문을 가져온다.

### 새 데이터 ② — S5 조건 라벨

- **왜 필요한가:** Diff Coverage Rate 는 자동 계산되지만, "이 조건이 정말
  결정적이었는가" 는 정답이 있어야 잰다.
- **몇 건인가:** **TRAP 구간 15건 + 사정거리 22건에서 중복을 뺀 규모.**
  전수가 아니라 이 두 구간만 — 나머지 구간에서는 조건 대조가 결론을 바꾸지
  않는다.
- **어떻게 만드나:** `판단이유` 에 결론 근거가 서술돼 있다. **dev 에서만**
  그것을 조건으로 정리하면 순환 없이 정답을 만들 수 있다. test 에는 손대지
  않는다.
- **먼저 확인할 것:** 이 라벨링에 들어가는 사람 시간이 얻는 것보다 큰지.
  30~40건 규모이므로 감당 가능하다고 본다.

## 12. 기술 스택 — 문제에서 출발한다

공고에 있다는 이유로 넣지 않는다. 각각 문제 → 대안 → 선택 → 이유 →
예상 효과로 적는다.

### 조문·선례 검색

- **문제:** 지금은 문자 4-gram 하나로 뽑는다. `240047` 에서 공유 각주가
  순위를 만들었다. 조문·구조를 축으로 쓸 수 없다.
- **대안:** (a) 현행 유지 (b) 조문 필드를 붙인 색인 (c) Elasticsearch
- **선택:** **(b) → 필요하면 (c)**
- **이유:** 필요한 것은 "본문 유사도 + 조문 일치 + 필터" 의 결합이다. 코퍼스
  259건에 ES 를 세우는 것은 운영 부담이 이득보다 크다. 다만 **BM25·필드
  부스팅·필터 결합은 ES 가 표준적으로 잘하는 일**이므로, 조문 축이 실제로
  효과가 있다고 확인되면 그때 옮긴다.
- **예상 효과:** `240047` 유형(공유 상용구로 뜬 선례)의 순위 하락. 재보기
  전에는 수치를 적지 않는다.

### 임베딩 / Reranker

- **문제:** 문자 n-gram 은 표현이 다른 같은 뜻을 못 본다.
- **대안:** (a) 현행 L (b) LSA 기반 D — **이미 있다** (c) 사전학습 임베딩
  (d) cross-encoder reranker
- **선택:** **(a)+(b) 유지, (c)(d) 보류**
- **이유:** E8 에서 이미 쟀다 — D 는 `조치` 선례를 6배 더 찾지만 **그중 절반이
  함정**이었다. 즉 검색을 바꿔서 풀 문제가 아니라는 증거가 이미 있다. AG-13 은
  검색이 아니라 **근거 선택**의 실패다. (d) 는 S5 가 붙은 뒤 순위 문제가 남으면
  그때 본다.
- **예상 효과:** 지금 넣으면 효과 없음 — 그래서 안 넣는다.

### LangGraph

- **문제:** 단계가 4개에서 11개로 늘어난다.
- **대안:** (a) 현행 순차 호출 (b) LangGraph
- **선택:** **(a) 유지**
- **이유:** 여전히 분기 있는 무순환 DAG 이고 사람 개입 루프가 없다. 필요한
  것은 결정론적 재현이고 `AgentState` 하나로 입력·중간값·결과·경로가 남는다.
  **다만 `HUMAN_REVIEW` 가 실제로 사람이 개입해 재개하는 흐름이 되면 상태
  직렬화·중단/재개가 필요해지고, 그때가 LangGraph 를 도입할 자리다.**
- **예상 효과:** 지금은 계층만 늘어남.

### PostgreSQL / Docker

- **문제:** 지금은 JSONL 파일과 로컬 실행이다.
- **선택:** **보류.** 데이터가 259건이고 산출물은 파일로 재현된다. 여러
  사용자가 동시에 요청을 넣고 이력을 조회하는 서비스가 되면 그때 필요하다.

### 이미 쓰는 것

FastAPI + Pydantic(형이 계약을 강제한다 — `Evidence.score` 범위 위반을
Pydantic 이 잡은 적이 있다), pytest 회귀, GitHub Actions.

## 13. 마지막 질문 여섯

### Q1. 단순 RAG 와 무엇이 다른가

단순 RAG 는 **찾은 것을 근거로 쓴다.** 이 설계는 **찾은 것을 믿어도 되는지
먼저 판단하고, 못 믿으면 답하지 않는다.**

수치로 말하면 이렇다. 최근접 선례를 그대로 따르는 전략(=RAG 의 본질)은
순응 구간에서 정확도 1.000, **함정 구간에서 0.000** 이었다. 함정 구간이
15건 있고 거기서 RAG 는 15개를 전부 틀린다. Router 를 붙이면 그 자리가
2 맞음 / 5 틀림 / 8 기권이 된다.

그리고 이 설계는 한 걸음 더 간다 — **근거가 원문에 있다는 것만으로 통과
시키지 않는다.** `shared` 조건에 붙은 인용은 결정적일 수 없다는 규칙(V7)은
RAG 에 없는 계약이다.

### Q2. 일반적인 Multi-Agent 와 무엇이 다른가

일반적인 multi-agent 는 **여러 LLM 이 서로 이야기하고 합의**한다. 이 설계는
LLM 을 **네 자리에만** 둔다 — 구조화·조건 후보·후보 판정·설명. 경로·결론·
기권·게이트는 전부 결정 표와 결정론적 검사다.

핵심은 **LLM 의 출력을 다른 LLM 이 아니라 결정론이 검사한다**는 것이다.
Diff Coverage Gate 가 그 예다 — 텍스트 차집합은 코드가 계산하고, LLM 이
그것을 덮지 못하면 그 자리에서 막힌다. LLM 심판을 하나 더 두면 AG-13 이
한 층 위에서 반복될 뿐이다.

그리고 **왜 그 경로를 갔는지가 데이터로 남는다** — `route_reason` 에 발화한
줄 번호가 들어간다. 사람의 서술이 아니다.

### Q3. DeFactoRule 의 고유 기술적 기여

넷이고, 넷째가 이번에 생겼다.

1. **TRAP 지표** — "닮은 선례가 있는데 그 선례가 틀린 답을 가리키는" 구간을
   따로 떼어 재는 파티션. 전체 정확도는 이 구간을 감춘다.
2. **보정된 신뢰 구간** — `TRUST` 0.60 / `DOUBT` 0.15 를 dev leave-one-out
   에서 뽑았다. 구간별 오류율 0.062 vs 0.500, 신뢰구간 비중첩. 임의로 고른
   문턱이 아니다.
3. **기권을 벌하지 않는 평가** — 기권을 `predicted: null` 로 내보내면 위험-
   커버리지 곡선이 그것을 전부 오답으로 센다. `provisional` + `abstained`
   분리로 AURC 판정이 뒤집혔다(−0.270 유의 → −0.021 판정 보류). 기권을 다루는
   시스템은 기권을 다루는 지표가 있어야 한다.
4. **결정적 조건 접지 (AG-13 에서 나옴)** — *"인용이 원문에 있다"* 는 근거의
   충분조건이 아니다. **두 사안에 똑같이 있는 문장은 둘을 가를 수 없다.**
   이 자명한 명제를 계약(`shared` ⇒ `decisive` 불가)과 지표(Diff Coverage,
   Deciding-Factor Grounding)로 만든 것이 이 프로젝트의 새 기여다.

넷 다 **실패에서 나왔고 그 실패가 저장소에 번호를 달고 남아 있다** —
EV-24, AG-12, AG-13.

### Q4. 애자일소다 DS팀의 "업무 절차/판단 기준을 AI Agent Workflow 로 구현" 과의 연결

이 도메인이 그 문제의 순수한 형태다. 금융규제 회신 업무에는 **문서화된 절차
(명시 규정)와 문서화되지 않은 실무 기준(선례에서만 드러나는 de facto rule)이
동시에 있고, 담당자는 그 둘을 대조해 판단한다.** 이 설계는 그 절차를 11단계로
분해하고, 각 단계에서 무엇을 LLM 에게 맡기고 무엇을 코드가 붙드는지 정했다.

옮겨 쓸 수 있는 형태로 남는 것 셋.

- **판단 기준의 역추출** — 규정에 없지만 실무가 따르는 기준을 데이터에서
  뽑고, 그것이 새 사건에 전이되는지 검증한다(E6 에서 `조치` 규칙이
  100%→20% 로 무너지는 것을 확인했다. 전이 검증 없이 역추출만 하면 위험하다).
- **언제 답하지 말아야 하는가** — 실무 자동화에서 오답의 비용은 무응답의
  비용보다 크다. 기권 게이트와 이관 조건을 결정론으로 두는 설계가 그것을
  다룬다.
- **근거의 계약** — 실무 판단은 "왜" 가 없으면 쓸 수 없다. `execution_trace`
  와 Evidence Contract 가 그것을 형으로 강제한다.

### Q5. E11b 가 실패한 이유를 최종 Workflow 는 어떻게 해결하려 하는가

**실패의 원인은 질문의 형태였다.** "두 요청의 차이가 결론을 바꿀 만한가" 를
통째로 물으면, 모델은 두 글을 나란히 읽고 **닮은 곳**을 찾는다. 유사도가
높을수록 닮은 곳이 많아지고, 그중 하나를 근거로 집으면 `applies` 가 나온다.

세 겹으로 바꾼다.

1. **질문을 바꾼다.** "닮았는가" 대신 "조건이 어떻게 갈리는가". 출력은
   문장이 아니라 관계가 붙은 조건 집합이고, `only_in_request` /
   `only_in_precedent` 가 **일급 칸**이라 비워 둘 수 없다.
2. **결정론이 누락을 잡는다.** 텍스트 차집합을 코드가 계산하고, 조건 목록이
   그것을 덮지 못하면 `applies` 를 낼 수 없다(Diff Coverage Gate). 이것이
   `240023`(진짜 중복 → 통과)과 `220049`(실질 차이 있음 → 차단)를 가른다 —
   지금의 opposition guard 는 둘을 구분하지 못하고 똑같이 막았다.
3. **근거 계약이 막는다.** `shared` 조건에 붙은 인용은 `decisive` 가 될 수
   없고, 결론은 `decisive` 근거를 요구한다(V7). E11b 가 인용한 문장이
   정확히 `shared` 였다.

**셋 다 아직 재보지 않았다.** S5 도 LLM 이므로 실패할 수 있다. 달라지는 것은
실패의 모양이다 — "틀린 `applies`" 가 아니라 "분석 미완 → 기권" 이 된다.
그것도 손실이지만, 오답보다 싸다.

### Q6. 3개월 안에 어디까지 되는가

기준선을 먼저 적는다. 실험 E1~E11b 완료 · 결정론 파이프라인과 API 서비스
계층 구현 완료 · 실패 레지스트리와 회귀 스위트 운영 중(**정확한 건수는 여기
적지 않는다 — README 의 대조되는 표시가 유일한 출처다**). 이 문서 작성
시점까지 쓴 API 비용은 누적 $4.12 이고, 그중 E11b 가 $0.0674 다.

| 기간 | 무엇 | 근거 |
|---|---|---|
| **1개월** | S1(구조화) · S5(조건 분석) · Diff Coverage Gate · V7 · 지표 둘 | 기존 파이프라인 위에 단계 둘을 얹는 일. 검색·평가·서비스는 그대로 |
| **2개월** | S2 인용 색인 · C3 · S7 결정 표 확장 · TRAP 15건 + 사정거리 22건 재측정 | 조문 축을 붙이는 일. 새 데이터는 dev 인용 색인뿐(비용 0) |
| **3개월** | `HUMAN_REVIEW` 흐름 · S11 감사 대시보드 · 회귀 스위트 확장 | UI 는 §15 대로 채팅창이 아니라 **조건 대조 화면** |

**3개월 안에 안 되는 것도 적는다.**

- **`조치` 구간은 좋아지지 않는다.** test 에 14건뿐이고 사정거리 22건에는
  0건이다. 표본이 늘지 않는 한 이 구간의 개선은 측정 불가다.
- **법령 원문 수집은 3개월 계획에 넣지 않는다.** 인용 색인으로 부족한 것이
  확인된 뒤에 시작한다.
- **전체 성능이 기존 LLM 판정기를 넘는다고 약속하지 않는다.** 현재 AURC 는
  `router` 0.236 대 `sector` 0.124 다. 이 설계의 목표는 그 숫자를 뒤집는 것이
  아니라 **틀릴 때 왜 틀렸는지 말할 수 있는 시스템**을 만드는 것이다.

## 14. 이 설계가 틀릴 수 있는 곳

미리 적어 둔다.

1. **S5 도 LLM 이다.** 조건 분해가 AG-13 과 같은 방식으로 실패할 수 있다.
   게이트가 잡는 것은 **누락**이지 오분류가 아니다. `only_in_request` 를
   적어 놓고 그것을 `decisive` 가 아니라고 판단하면 게이트는 통과한다.
2. **텍스트 차집합이 의미 차이와 같지 않다.** 표현만 다르고 뜻이 같은 조각이
   차집합에 남으면 게이트가 헛발화한다. 메타데이터 필터가 얼마나 잘 되느냐에
   달려 있고, 그것은 재봐야 안다.
3. **단계를 늘리면 오류가 곱해진다.** 4단계에서 11단계가 된다. 각 단계의
   실패율이 낮아도 완주율은 떨어진다 — 그래서 `workflow completion` 을 지표에
   넣었다.
4. **`기타` 는 여전히 혼합 범주다.** 세 검색기 전부에서 함정률이 0.54~0.56
   으로 가장 높았다. 조건 대조가 이 범주를 갈라 줄지는 알 수 없다.
5. **opposition guard 를 떼면 나빠질 수 있다.** E11b 에서 그것이 오답 하나를
   막았다. S5 가 그 일을 대신한다는 것은 **가정이지 측정이 아니다.**
